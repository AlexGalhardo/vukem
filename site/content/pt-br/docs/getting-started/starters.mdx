Um <Term tip="Um projeto pronto que o vukem new copia para uma pasta nova: rotas, controllers, views, migrations e testes que já funcionam juntos.">starter</Term> é o projeto que o `vukem new` escreve para você. Todo starter é um app funcionando, com testes, então você começa de algo que já roda em vez de uma pasta vazia. Esta página compara os starters e mostra o que cada um contém.

Você vai aprender:

- quais são os cinco starters e como escolher entre eles
- as flags que escolhem um starter e o gerenciador de pacotes
- o que todo starter tem em comum: SQLite, um CRUD de exemplo, testes e um `Dockerfile`
- o que há de especial em HTMX com Vite, templ, Inertia, Minimal e API
- quais complementos você pode instalar por cima depois

## A ideia

Escolher um starter é como escolher o tipo de casa antes de construir. Todos têm a mesma fundação (rotas, validação, a camada de banco de dados, sessões, testes). Eles diferem em **quem desenha as páginas**:

- **O servidor** (HTMX, templ): o Go gera o HTML. O navegador recebe páginas prontas. O [htmx](https://htmx.org) troca partes da página sem recarregá-la inteira.
- **O navegador** (Inertia): um componente React, Vue ou Svelte desenha a página. O Go envia os dados para ele como JSON, mas você continua escrevendo controllers e rotas clássicos, sem uma API separada.
- **Ninguém** (API): o app responde só JSON, para um app mobile, outro servidor ou um frontend separado.

Se você está começando no desenvolvimento web, escolha o starter padrão **HTMX**: ele tem menos peças móveis e toda página é um template HTML simples.

## Início rápido

```bash
vukem new blog                  # HTMX + html/template (default)
vukem new blog --templ          # HTMX + templ components
vukem new blog --inertia react  # Inertia + React (also: vue, svelte)
vukem new shop --api            # JSON-only REST API
vukem new site --minimal        # HTMX without a database
vukem new blog --pm bun         # bun install instead of npm install
vukem new blog --no-install     # skip installing frontend dependencies
```

Em um terminal, sem flag de stack, o `vukem new` pergunta qual stack você quer; em scripts e CI ele escolhe HTMX. Só uma entre `--api`, `--templ` e `--inertia` pode ser usada, e `--minimal` não pode ser combinada com nenhuma delas:

```text
usage error: --minimal is an HTMX starter: drop --api, --templ and --inertia
```

## Comparação

| Starter | Flag | Páginas desenhadas por | Views ficam em | Build do frontend | Node.js ou Bun |
| --- | --- | --- | --- | --- | --- |
| HTMX (padrão) | nenhuma | Go, `html/template` | `resources/views/*.html` | htmx 4 (incluído no projeto), Vite 8, Tailwind CSS v4 | só para builds do Vite |
| HTMX + templ | `--templ` | Go, componentes [templ](https://templ.guide) | `resources/views/*.templ` (pacote `views`) | igual ao HTMX | só para builds do Vite |
| Inertia | `--inertia react\|vue\|svelte` | React, Vue ou Svelte | `resources/js/pages` | Vite 8, TypeScript, Tailwind CSS v4 | obrigatório |
| Minimal | `--minimal` | Go, `html/template` | `resources/views` | igual ao HTMX | só para builds do Vite |
| API | `--api` | ninguém (JSON) | nenhum | nenhum | não usado |

### O que todo starter tem em comum

- **SQLite, migrations e um CRUD de exemplo** de posts, com o driver em Go puro, uma factory e um seeder (todos menos o Minimal).
- **Testes** que passam com `go test ./...` em um projeto novo, sem Node.js.
- **Uma `APP_KEY` nova** no `.env`, copiado de `.env.example`.
- **Um `Dockerfile` de produção** e um `.dockerignore`. Os starters web compilam os assets do Vite com o gerenciador de pacotes escolhido em um primeiro estágio; depois, todo starter compila um binário Go estático com as tags de `.buildtags` e o executa como usuário sem privilégios de root no Alpine, com `APP_ENV=production`, `HOST=0.0.0.0`, `PORT=3000` e `LOG_FORMAT=json`. O `.dockerignore` mantém os arquivos `.env`, `node_modules` e `storage/` fora da imagem. O Railway e outras plataformas fazem o build sem configuração extra: veja [Docker e Railway](/docs/deployment/docker-and-railway).
- **`govulncheck`** como ferramenta Go: `go tool govulncheck ./...` verifica as suas dependências.

O gerenciador de pacotes vem de `--pm` (`npm`, `bun`, `pnpm` ou `yarn`; padrão `npm`). Comandos posteriores, como `vukem serve` e `vukem build`, detectam o gerenciador pelo lockfile (`bun.lock`, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`) e usam o npm quando não encontram nenhum.

## HTMX com Vite

O starter padrão gera as páginas com o [`html/template`](https://pkg.go.dev/html/template) do Go, que escapa todo valor para que a entrada do usuário não consiga injetar HTML. Ele inclui o **htmx 4.0.0** em `resources/public/js/htmx.min.js` (fixado pelo SHA-256 nos testes da CLI), servido pelo middleware de arquivos estáticos, e compila CSS e scripts com Vite 8 e Tailwind CSS v4 (`@tailwindcss/vite`):

```text
package.json, vite.config.ts
resources/css/app.css       @import "tailwindcss" + starter styles
resources/js/app.ts         the page script
resources/vite/vukem.js     writes public/hot while the dev server runs
resources/public/build/     vite build output, embedded in the binary
```

O layout carrega os assets com `{{ vite "resources/css/app.css" "resources/js/app.ts" }}` ([Vite](/docs/frontend/vite)). Sem servidor de desenvolvimento e sem build, a tag gera um comentário HTML em desenvolvimento (`<!-- vite: no dev server and no build; run npm run dev -->`), então os testes Go nunca precisam do Node. As views do starter não têm scripts inline nem handlers de evento, por isso rodam sob a Content Security Policy padrão. Veja [HTMX](/docs/frontend/htmx) para os helpers de requisição e resposta.

Além do CRUD de posts, este starter tem um exemplo de uploads (`/uploads`).

## templ

`vukem new app --templ` é o starter HTMX com as mesmas páginas e testes escritos como componentes [templ](https://templ.guide). O templ transforma arquivos `.templ` em código Go, então um erro de digitação em uma view vira erro de compilação em vez de erro em tempo de execução.

- O templ é fixado como ferramenta Go (uma linha `tool` no `go.mod`); rode-o com `go tool templ generate`.
- Os arquivos gerados `*_templ.go` são commitados, então `go build` e `go test` funcionam sem rodar o templ.
- O `vukem serve` roda `go tool templ generate` antes de cada build quando existem arquivos `.templ`, e fica observando esses arquivos; o `vukem build` gera antes do build do Vite.
- `resources/views/helpers.go` encapsula os helpers do contexto (`route`, `asset`, `viteTags`, `script`, `flash`, `old`, `fieldError`, `csrfField`). Os scripts passam por helpers que adicionam o nonce da CSP, então os componentes não têm tags `<script>` cruas.

```go title="app/controllers/post_controller.go"
return c.View(
	views.PostsIndex(posts),
	web.Partial(views.PostList(posts)),
)
```

O `web.Partial` gera só o fragmento em requisições parciais do htmx e a página inteira nos demais casos. Os componentes leem os dados da requisição por meio de `web.FlashFrom(ctx, key)`, `web.OldInput(ctx, field)`, `web.ErrorsFrom(ctx)`, `csrf.Token(ctx)` e `middleware.CSPNonce(ctx)`.

<Callout type="info">
O `vukem install:auth` escreve páginas `html/template` e, por enquanto, recusa projetos templ.
</Callout>

## Inertia (React, Vue, Svelte)

O [Inertia](https://inertiajs.com) permite escrever páginas como componentes React, Vue ou Svelte mantendo as rotas e os controllers no servidor: um controller chama `inertia.Render` com o nome de um componente e as props dele, e o navegador o desenha.

```bash
vukem new app --inertia react         # or vue, svelte
vukem install:inertia --force --vue   # convert an existing HTMX starter
```

O app recebe:

- `vukem.WithInertia(inertia.Config{})` em `bootstrap/app.go` e controllers que chamam `inertia.Render`;
- a view raiz `resources/views/app.html`, páginas TypeScript em `resources/js/pages` (incluindo uma página `Error` para respostas de erro), um layout padrão em `resources/js/layouts` e componentes compartilhados em `resources/js/components`;
- testes que usam `AssertInertia`;
- `npm run typecheck`, que roda `tsc` (React), `vue-tsc` (Vue) ou `svelte-check` (Svelte).

A estilização é só com Tailwind (`resources/css/app.css`), com o modo escuro controlado por uma classe `dark` em `<html>`. `resources/js/app.tsx` (ou `app.ts`) aplica a escolha salva (`localStorage.theme` = `"dark"` ou `"light"`) ou a preferência do sistema ao carregar, então um botão de tema só precisa alternar a classe e salvá-la. As views não têm scripts inline, por causa da CSP. O `<html lang>` segue o idioma da requisição. O `vukem install:auth` em um app Inertia adiciona as páginas `Auth/*` e `Dashboard`. Veja [Inertia](/docs/frontend/inertia).

## Minimal

`vukem new site --minimal` é o starter HTMX para um app sem estado: a página inicial, o layout, o htmx incluído e o Vite, sem `database/`, models, posts ou uploads, e sem `DATABASE_URL`. Sessões, cache, fila e limites de requisição mantêm os padrões cookie, memory e sync, que não precisam de banco de dados.

O arquivo `.buildtags` dele contém `vukem_nosqlite`, então `vukem build` e `vukem serve` deixam o driver SQLite fora do binário (cerca de 4 MB a menos). Abrir um banco SQLite em um build assim falha com um erro que cita a tag. O `Dockerfile` do starter também lê o `.buildtags`; um Dockerfile escrito à mão precisa passar as tags por conta própria (`go build -tags vukem_nosqlite ./cmd/app`). Os testes rodam com um simples `go test ./...`.

Para adicionar um banco de dados depois, apague a tag do `.buildtags` (ou configure outro driver) e rode `vukem install:auth` ou `vukem make:migration` normalmente.

## API

`vukem new shop --api` é um app só de JSON, sem views, sessões ou Node.js:

- rotas `/api/v1` em `routes/api.go` e `routes/posts.go`, atrás do `middleware.JSONOnly()`;
- tokens de API: `POST /api/v1/tokens` emite um, e `GET /api/v1/me` e `DELETE /api/v1/tokens/current` exigem um token;
- um recurso de posts que qualquer pessoa pode ler e só quem tem token pode alterar;
- CORS a partir de `CORS_ALLOWED_ORIGINS` (separadas por vírgula; vazio não permite nenhuma origem) e limites de requisição: 120 por minuto por IP, 60 por token e 5 pedidos de token por minuto por IP;
- erros problem+json e testes para tokens e posts.

Veja [APIs REST](/docs/rest-apis/overview) e [Tokens de API](/docs/security/api-tokens).

## Complementos

Estes scaffolds funcionam por cima de um starter, a qualquer momento:

| Comando | Adiciona |
| --- | --- |
| `vukem install:auth [--social …] [--2fa]` | [Autenticação](/docs/security/authentication), [login social](/docs/security/social-login), [dois fatores](/docs/security/two-factor) |
| `vukem install:admin` | [Painel admin](/docs/digging-deeper/admin) em `/admin` (precisa do `install:auth`) |
| `vukem install:flags` | [Feature flags](/docs/digging-deeper/feature-flags), ligadas e desligadas no painel admin |
| `vukem install:billing` | [Assinaturas Stripe](/docs/digging-deeper/billing) |
| `vukem install:api` | Rotas `/api/v1` autenticadas por token, CORS e limites de requisição |
| `vukem install:inertia --force --react\|--vue\|--svelte` | Transforma o starter HTMX em Inertia |
| `vukem boost:install` | Diretrizes, skills e um servidor MCP para agentes de código com IA |

A [referência da CLI](/docs/cli/overview#installers) lista todas as flags.
