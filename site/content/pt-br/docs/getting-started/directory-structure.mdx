Um projeto Vukem é um módulo Go comum com uma organização convencional. Saber onde cada coisa fica permite encontrar qualquer arquivo em segundos e permite que os geradores coloquem arquivos novos no lugar certo. Esta página percorre o starter HTMX pasta por pasta e depois mapeia os pacotes do próprio framework.

Você vai aprender:

- para que serve cada pasta e arquivo de um projeto novo
- como o app é montado em `bootstrap/` com código Go comum
- como os geradores registram o que criam, e o que acontece quando não conseguem
- quais pastas são geradas ou ignoradas pelo Git
- qual pacote do framework importar para cada funcionalidade

## A ideia

Pense em um projeto como uma casa. `cmd/app` é a porta da frente: o programa começa ali. `bootstrap/` é o quadro de luz: ele liga todos os cômodos. `routes/` é a planta da casa, `app/` guarda os cômodos onde o trabalho acontece, `database/` é o porão, `resources/` a decoração, e `tests/` o inspetor que confere se tudo funciona.

Nada é ligado por mágica. Se um controller, uma migration ou um provider é usado, existe uma linha de código Go, que você pode ler, listando esse item.

## Uma aplicação

`vukem new todo` (o starter HTMX) cria:

```text
todo/
├── cmd/app/main.go          the program: vukem.Main(bootstrap.New)
├── bootstrap/
│   ├── app.go               New(opts...): wires the whole app
│   ├── providers.go         Providers(): make:provider appends
│   └── commands.go          Commands(): make:command appends
├── routes/
│   ├── web.go               Web(r, app): the browser routes
│   ├── registry.go          All(): route files, install:* appends
│   └── schedule.go          Schedule(s, app): scheduled tasks
├── app/
│   ├── controllers/         Home, PostController, UploadController
│   ├── models/              Post (embeds orm.Model)
│   ├── requests/            input structs and their z schemas
│   ├── jobs/registry.go     queued jobs: make:job appends
│   └── listeners/registry.go  event listeners: make:listener appends
├── database/
│   ├── migrations/          timestamped migrations + registry.go
│   ├── factories/           fake data for tests (post_factory.go)
│   └── seeders/             db:seed data + registry.go
├── resources/
│   ├── resources.go         embeds views/ and public/
│   ├── views/               layouts/, partials/, components/,
│   │                        posts/, uploads/, home.html
│   ├── public/              js/htmx.min.js, robots.txt, build/
│   ├── css/app.css          Tailwind entry point
│   ├── js/app.ts            page script
│   └── vite/                the Vite hot-file plugin
├── storage/                 SQLite database, local files (ignored)
├── tests/                   home, posts and uploads tests
├── .env, .env.example       configuration (.env is ignored)
├── Dockerfile, .dockerignore  the production image
├── package.json, vite.config.ts  the frontend build
├── README.md
└── go.mod, go.sum
```

### `cmd/app`

```go title="cmd/app/main.go"
package main

import (
	"os"

	vukem "github.com/AlexGalhardo/vukem"

	"example.com/todo/bootstrap"
)

func main() { os.Exit(vukem.Main(bootstrap.New)) }
```

O programa inteiro é uma linha. O `vukem.Main` carrega a configuração, trata o `Ctrl+C` e roda o `serve` ou o comando do app passado no primeiro argumento (`migrate`, `route:list`, …). A CLI `vukem` compila este programa para rodar os comandos do app; em produção, você executa o binário diretamente. Veja [Ciclo de vida da aplicação](/docs/architecture/lifecycle#creating-the-app).

### `bootstrap/`

`bootstrap.New` é o único lugar que lista tudo o que o app usa. O `cmd/app` o chama, e os testes também:

```go title="bootstrap/app.go"
func New(opts ...vukem.Option) (*vukem.App, error) {
	base := []vukem.Option{
		vukem.WithProviders(Providers()...),
		vukem.WithMigrations(migrations.All()),
		vukem.WithSeeders(seeders.All()...),
		vukem.WithListeners(listeners.All()...),
		vukem.WithJobsFunc(jobs.All),
		vukem.WithSchedule(routes.Schedule),
		vukem.WithViews(resources.Views()),
		vukem.WithVite(resources.Public()),
	}

	for _, fn := range routes.All() {
		base = append(base, vukem.WithRoutes(fn))
	}

	app, err := vukem.New(append(base, opts...)...)
	if err != nil {
		return nil, err
	}

	app.AddCommand(Commands()...)

	return app, nil
}
```

As `opts` de quem chama vêm **por último**, para que o `vukem.Main` e o `vukemtest.New` possam sobrescrever o que precisam (de onde vem a configuração, que tipo de execução é esta).

### `routes/`

- `web.go` instala o `vukem.DefaultMiddleware`, serve `resources/public` em `/`, abre o banco de dados com `app.DB()` e registra as rotas. É ali que você adiciona `r.Resource("tasks", …)` em [Seu primeiro app](/docs/first-app).
- `registry.go` lista os arquivos de rotas, em ordem. O `install:auth`, o `install:api` e outros instaladores acrescentam os seus (`routes/auth.go`, `routes/api.go`).
- `schedule.go` declara as tarefas agendadas ([Agendador](/docs/digging-deeper/scheduler)).

### `app/`

O código da sua aplicação, um pacote para cada tipo de coisa: `controllers` (handlers agrupados por recurso), `models` (linhas do banco de dados), `requests` (entrada validada), `jobs` e `listeners`. Os geradores criam mais pastas quando você precisa: `app/mail`, `app/events`, `app/policies`, `app/middleware`, `app/resources`, `app/commands`, `app/providers`.

### `database/`

- `migrations/`: um arquivo por mudança no schema, com nome `YYYYMMDDHHMMSS_descricao.go`, mais o `registry.go`, cuja função `All()` as retorna em ordem.
- `factories/`: construtores de models falsos para testes e seeders ([Factories e seeders](/docs/database/factories-seeders)).
- `seeders/`: dados que o `vukem db:seed` insere, listados em `seeders/registry.go`.

### `resources/`

Tudo o que não é código Go: views HTML, CSS, scripts e arquivos públicos. O `resources.go` embute `views/` e `public/` no binário com [`go:embed`](https://pkg.go.dev/embed), então a produção não precisa de nenhum arquivo ao lado dele:

```go title="resources/resources.go"
//go:embed views all:public
var embedded embed.FS
```

Durante o desenvolvimento, os arquivos **do disco** são usados no lugar, então uma edição em um template aparece ao atualizar a página. Com `APP_ENV=production` no ambiente do processo, a cópia embutida é sempre usada, mesmo quando existe uma pasta `resources/` ao lado do binário.

### `storage/` e `tests/`

`storage/` guarda o arquivo SQLite (`storage/database.sqlite`, vindo de `DATABASE_URL`) e os uploads locais. Tudo nela, exceto o `.gitkeep`, é ignorado pelo Git. `tests/` guarda testes de integração que montam o app real com o `vukemtest` ([Testes](/docs/testing/overview)).

### Pastas geradas e ignoradas

| Caminho | Criado por | No Git |
| --- | --- | --- |
| `.vukem/` | A CLI: builds do app em cache para os comandos do app e o `vukem serve` | Não |
| `bin/` | `vukem build` (o binário de produção) | Não |
| `node_modules/` | npm, bun, pnpm ou yarn | Não |
| `resources/public/build/` | `vite build` | Não (a imagem faz o próprio build) |
| `resources/public/hot` | O servidor de desenvolvimento do Vite, enquanto roda | Não |
| `storage/*` | O app (banco de dados, arquivos) | Não, exceto `.gitkeep` |

## Como os geradores ligam o código

O registro é Go comum: uma função retorna um slice, e o gerador acrescenta um elemento a ele. Por exemplo, depois de `vukem make:migration create_tags_table`:

```go title="database/migrations/registry.go"
func All() []schema.Migration {
	return []schema.Migration{
		m20260101000000CreatePostsTable(),
		m20261018003311CreateTasksTable(),
		m20261018101500CreateTagsTable(),
	}
}
```

| Arquivo | Função | Acrescentado por |
| --- | --- | --- |
| `bootstrap/providers.go` | `Providers()` | `make:provider` |
| `bootstrap/commands.go` | `Commands()` | `make:command` |
| `database/migrations/registry.go` | `All()` | `make:migration`, `make:model -m` |
| `database/seeders/registry.go` | `All()` | `make:seeder` |
| `app/jobs/registry.go` | `All()` | `make:job` |
| `app/listeners/registry.go` | `All()` | `make:listener` |
| `app/policies/registry.go` | `All()` | `make:policy` |
| `routes/registry.go` | `All()` | `install:*` |

Os geradores editam esses arquivos pela árvore sintática do Go (não por busca de texto), adicionam os imports necessários e nunca acrescentam o mesmo elemento duas vezes. Se você reestruturar uma dessas funções de modo que o formato `return []T{…}` desapareça, o gerador não tenta adivinhar: ele mostra a linha para você adicionar à mão. Não existe registro via `init()` nem descoberta baseada em reflection. Veja [CLI](/docs/cli/overview#generators).

## O framework

O módulo `github.com/AlexGalhardo/vukem` é dividido em pacotes pequenos, cada um com um único propósito. Você importa só os que usa. O pacote do contexto da requisição se chama `web` para nunca esconder a variável convencional `ctx context.Context`.

| Pacote | Propósito |
| --- | --- |
| `vukem` (raiz) | `App`, opções, providers, runners, comandos, `DefaultMiddleware`, `Main` |
| `config` | Carregador de `.env`, `Load[T]`, `Secret`, `APP_KEY` |
| `router` | Wrapper do ServeMux: grupos, nomes, recursos, geração de URLs |
| `web` | `*web.Ctx`: entrada, respostas, redirecionamentos, renderização, o handler de erros |
| `errs` | `HTTPError`, `ValidationError`, erros sentinela |
| `middleware` | Recover, request id, logger, CORS, arquivos estáticos, cabeçalhos de segurança, gzip… |
| `z` | Schemas de validação no estilo Zod |
| `session`, `csrf` | Sessões com mensagens flash e entrada antiga; proteção contra requisições de outra origem |
| `database`, `orm`, `schema` | Conexões (SQLite embutido), o query builder genérico, migrations |
| `view`, `htmx` | Engine de `html/template`; helpers de requisição e resposta do htmx 4 |
| `vukemtest` | Cliente de testes em processo e asserções de banco de dados |
| `cmd/vukem` | A CLI |

| Mais pacotes | Propósito |
| --- | --- |
| `api`, `ratelimit` | Envelopes REST, convenções de query, handlers tipados, chaves de idempotência, cabeçalhos de depreciação; limite de requisições com GCRA |
| `openapi`, `apidocs` | Geração e validação de OpenAPI 3.1, geração de código TypeScript/Zod, referência de API Scalar |
| `queue`, `queue/queuetest`, `schedule` | Jobs tipados e drivers, a suíte de conformidade de drivers, o agendador cron |
| `auth`, `auth/hash`, `auth/jwt`, `auth/totp` | Guards e tokens, hash de senhas, JWT e refresh tokens, dois fatores com TOTP |
| `authz`, `social`, `signed` | Gates e policies, login social, URLs assinadas |
| `mail`, `cache`, `storage`, `events` | Transportes de e-mail, stores de cache, discos, eventos tipados |
| `logging`, `logging/telegram` | Deduplicação de erros repetidos, logs no Telegram |
| `factory`, `database/dbtest` | Factories de models, a suíte de conformidade de dialetos |
| `httpclient`, `webhook`, `security` | Cliente HTTP protegido contra SSRF, assinaturas de webhook, eventos de segurança |
| `vite`, `inertia` | Tags de assets do Vite; o adaptador do Inertia v3 |
| `crypt`, `i18n`, `sse`, `broadcast` | Criptografia, traduções, server-sent events, canais em tempo real |
| `upload`, `export`, `uuid`, `flags` | Uploads em streaming e retomáveis, downloads CSV/JSON/NDJSON, UUID v4/v7, feature flags |
| `admin`, `devtools` | Painel admin; painel de desenvolvimento |

Algumas integrações são **módulos separados**, então as dependências delas só são baixadas quando você faz `go get` delas:

| Módulo | Propósito |
| --- | --- |
| `drivers/postgres`, `drivers/mysql` | PostgreSQL, MySQL e MariaDB |
| `drivers/redis`, `drivers/mongo` | Redis/Valkey, MongoDB |
| `drivers/s3`, `drivers/websocket`, `drivers/otel` | Armazenamento S3, WebSockets, OpenTelemetry |
| `contrib/graphql`, `contrib/grpc` | Servidor GraphQL, gRPC com connect-go |
| `contrib/stripe`, `contrib/imaging` | Cliente Stripe, miniaturas de imagens |

Cada pacote tem a sua referência no [pkg.go.dev](https://pkg.go.dev/github.com/AlexGalhardo/vukem).
