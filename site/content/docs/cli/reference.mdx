This is the manual for the `vukem` command. It lists every command, every flag, what each one writes to disk, the errors you may hit and how to fix them. Each command has a one-line purpose, a usage line, arguments, flags, and two examples: a realistic one and an advanced one. All output shown was captured from the real command.

For a guided tour with explanations and analogies, read the [CLI overview](/docs/cli/overview). Use this page when you already know what you want and need the exact syntax.

You will find:

- A cheat sheet of all commands
- The global flags, environment variables and exit codes
- Common workflows, end to end
- Links to one reference page per command group

## Global flags

These work on the `vukem` binary itself, before any command.

| Flag | What it does |
| --- | --- |
| `-h`, `--help`, `help`, `list` | Print the command list. Same as running `vukem` with no arguments. |
| `help <command>` | Print the usage line, description and flags of one global command. It exits 2 for an unknown name. |
| `<command> -h` | Same as `help <command>`. For an app command it prints the flags of that command only. |
| `-v`, `--version`, `version` | Print `vukem <version>`. A build from a checkout prints `devel`. |

Per-command rules:

- Flags use Go's [`flag`](https://pkg.go.dev/flag) package: `-force` and `--force` are the same. `--event=X` and `--event X` are the same.
- On **global** commands flags may come before or after the arguments: `vukem make:model Comment -m` equals `vukem make:model -m Comment`.
- On **app** commands flags must come **before** positional arguments. `db:seed` is the exception: it reads seeder names first, then flags.
- `--` ends flag parsing.
- Boolean flags do not combine: write `-m -f -c`, not `-mfc`.
- There is no `--env`, `--quiet` or `--no-color` flag. Output is plain text with no colour.

## Environment variables

The global CLI reads almost nothing from the environment:

| Variable | Read by | Effect |
| --- | --- | --- |
| `PATH` | all | Finds `go`, `git`, `npm`, `bun`, `pnpm`, `yarn`, `buf`, `protoc`, `node` |
| `CGO_ENABLED` | `build`, delegated builds | A value you set wins; otherwise builds run with `CGO_ENABLED=0` |

Everything else is read by **your app**, from the process environment or the `.env` file in the project root. The ones the CLI commands rely on:

| Variable | Default | Used by |
| --- | --- | --- |
| `APP_ENV` | `development` | Destructive commands need `-force` when it is `production` |
| `APP_DEBUG` | `false` | Must be `false` when `APP_ENV=production`, or every app command fails to boot |
| `APP_KEY` | none | Sessions and encryption. Written by `key:generate`, `new` |
| `APP_PREVIOUS_KEYS` | none | Old keys kept by `key:rotate` |
| `HOST`, `PORT` | `localhost`, `3000` | `serve`, `about` |
| `DATABASE_URL` | `file:storage/database.sqlite` | `migrate*`, `db:*` |
| `QUEUE_CONNECTION`, `QUEUE_NAMES`, `QUEUE_CONCURRENCY` | `sync`, `default`, `4` | `queue:*` |
| `SCHEDULE_TIMEZONE` | `UTC` | `schedule:*` |
| `OPENAPI_PREFIX` | none | Default for `-prefix` in `openapi:export` and `codegen:*` |
| `SHUTDOWN_TIMEOUT` | `15s` | How long `queue:work` waits for running jobs after Ctrl+C |

See [Configuration](/docs/configuration) for the full list.

<Callout type="tip" title="Git Bash on Windows">
Git Bash rewrites an argument that starts with `/` into a Windows path, so `-prefix /api` becomes `C:/Program Files/Git/api`. Write `-prefix //api`, or set `MSYS_NO_PATHCONV=1` for the command. PowerShell and cmd are not affected.
</Callout>

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Failure. The message starts with `error:` for global commands. |
| `2` | Usage error: unknown command, missing or extra argument, bad flag value. Global commands also print `Run 'vukem list' for the available commands.` |

A delegated app command returns its own exit code unchanged. A bare `vukem <unknown>` is delegated too, so inside a project it prints the app's command list and exits 2.

## How commands are found

1. If the name is a **global** command, `vukem` runs it.
2. Otherwise `vukem` builds `cmd/app` into `.vukem/bin/app` and runs it with the same arguments, standard streams and environment. It rebuilds only when a `.go`, `.templ`, `go.mod`, `go.sum` or `.buildtags` file is newer than the binary.
3. Outside a project you get `unknown command "migrate" (app commands need a Vukem project with cmd/app)`.

You may skip step 2 and run the binary yourself: `go run ./cmd/app migrate`.

## Common workflows

### New API project

```bash
vukem new shop --api --module github.com/acme/shop
cd shop
vukem migrate
vukem serve
```

```text
Migrated: 20260101000000_create_posts_table
Migrated: 20261024221606_create_users_table
Migrated: 20261024221607_create_auth_tables
```

Then `curl localhost:3000/up` answers `{"status":"ok"}`. Check the routes with `vukem route:list`.

### Add a resource end to end

A `Comment` that belongs to the blog:

```bash
vukem make:model Comment -m -f -c
vukem make:request StoreComment
vukem make:policy Comment
vukem make:test Comments
vukem migrate
```

Fill the migration, the model fields and the controller, register the routes in `routes/`, then run `go test ./...`. For an API, use `make:resource Comment` for the JSON shape and `vukem codegen:client` for a client. See [reference: make](/docs/cli/reference-make).

### Seed and migrate

```bash
vukem make:seeder Post
vukem migrate:fresh
vukem db:seed
```

`migrate:fresh` drops every table and migrates again, `db:seed` fills them. In production add `-force` on purpose and only after reading [the guard](/docs/cli/reference-database#the-production-guard).

### Build for production

```bash
vukem codegen:types -prefix /api -o resources/js/types.ts
vukem build -o bin/shop
export APP_ENV=production APP_DEBUG=false MAIL_MAILER=log
./bin/shop migrate
./bin/shop
```

`vukem build` runs `templ generate` and `vite build` when the project has them, then `go build -trimpath -ldflags="-s -w"` with `CGO_ENABLED=0`. The binary contains every app command, so a server without the `vukem` CLI still runs `./bin/shop migrate`. In production the app refuses to boot without `MAIL_MAILER` (`smtp`, `resend`, `mailtrap` or `log`). See [Single binary](/docs/deployment/single-binary).
