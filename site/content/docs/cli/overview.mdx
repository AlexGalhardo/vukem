`vukem` is the command you type in the terminal to work on a Vukem project. It creates new projects, writes boilerplate files for you, runs the app while you code and builds the final binary. Instead of copying a controller from an old project and renaming everything by hand, you run `vukem make:controller Post` and get a correct, formatted file.

This page is the guided tour: every command, with explanations and the same **blog** project as running example. For a man-page style manual with every flag, error and environment variable, see the [CLI reference](/docs/cli/reference).

You will learn:

- How the global `vukem` command and your app's own binary split the work
- How flags, help and exit codes work for every command
- What `new`, `serve`, `build` and the `install:*` commands do, step by step
- Which file each `make:*` generator writes and where it registers it
- How to customise the generated code with your own stubs
- Which commands run *inside* your app (`migrate`, `route:list`, `queue:work`)

## The idea: two binaries

Think of a car workshop. The **mechanic's toolbox** (`vukem`) can build, open and tune any car, but it does not drive. The **car's own dashboard** (your app binary) knows its engine, its fuel and its passengers. Vukem has both:

| Binary | Installed by | Knows your app? | Commands |
| --- | --- | --- | --- |
| `vukem` (global) | `go install` | No: it only reads and writes files | `new`, `serve`, `build`, `version`, `doctor`, `install:*`, `boost:install`, `key:*`, `down`, `up`, `make:*`, `codegen:rpc` |
| App binary (`cmd/app`) | Built from your project | Yes: it boots your app | `serve` (default), `migrate*`, `db:*`, `route:list`, `queue:*`, `schedule:*`, `openapi:export`, `codegen:types`, `codegen:routes`, `codegen:client`, `about`, `key:generate`, your own commands |

The global CLI never imports your code. When it needs Go, it runs the standard toolchain (`go build`, `go mod tidy`, `go get`). When you type a command it does not own, it **delegates** it: it builds `cmd/app` and runs it with the same arguments. That is why `vukem migrate` works from the project root, like `php artisan migrate` in Laravel.

<Callout type="info">
Each command and its flags are read with Go's standard [`flag`](https://pkg.go.dev/flag) package. A flag may be written with one or two dashes: `-force` and `--force` are the same flag.
</Callout>

## How every command reads its input

These rules apply to all commands of the global CLI.

- **Help.** `vukem help <command>` and `vukem <command> -h` print the usage line, the description and every flag with its default. `vukem list`, `vukem help`, `vukem -h` and `vukem --help` print the command list.
- **Version.** `vukem version`, `vukem --version` and `vukem -v` print the version. A binary built from a checkout prints `devel`.
- **Flags anywhere.** Flags may come before or after the arguments: `vukem make:model Comment -m -c` equals `vukem make:model -m -c Comment`. A flag that takes a value takes the next word (`--event PostPublished`) or the text after `=` (`--event=PostPublished`).
- **`--` stops flags.** Everything after `--` is an argument, even if it starts with a dash.
- **One flag per dash.** Boolean flags do not combine: write `-m -f -c`, not `-mfc`.
- **Names.** Generators accept any casing (`blog_post`, `blog-post`, `BlogPost`) and turn it into the right form for each place: `BlogPost` for the Go type, `blog_post` for the file name.

### Exit codes

The [exit code](https://pkg.go.dev/os#Exit) tells scripts and CI whether a command worked:

| Code | Meaning | Example |
| --- | --- | --- |
| `0` | Success | The file was created |
| `1` | Failure; the message starts with `error:` | `error: app/models/post.go already exists (use --force to overwrite)` |
| `2` | Usage error: unknown command, missing argument, bad flag | `usage error: --event is required` |

A usage error also prints `Run 'vukem list' for the available commands.` A delegated app command returns its own exit code unchanged.

## Project commands

### `vukem new`

`vukem new <name>` creates a project in a new folder from the starter embedded in the CLI. Without a stack flag, on a terminal, it asks which stack you want; without a terminal (CI, scripts) it picks HTMX.

```bash
vukem new blog --inertia react --pm bun
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--module` | string | the project name | Go [module path](https://go.dev/ref/mod#module-path) written to `go.mod` (`github.com/you/blog`) |
| `--api` | bool | `false` | JSON API starter: tokens, `/api/v1`, no views or sessions |
| `--templ` | bool | `false` | HTMX starter with [templ](https://templ.guide) components instead of `html/template` views |
| `--inertia` | string | none | Inertia starter with `react`, `vue` or `svelte` |
| `--minimal` | bool | `false` | HTMX starter without a database: no posts, uploads, migrations or SQLite driver |
| `--pm` | string | first of `bun`, `npm`, `pnpm`, `yarn` on `PATH` | JavaScript package manager: `npm`, `bun`, `pnpm` or `yarn` |
| `--no-install` | bool | `false` | Skip installing the frontend dependencies |
| `--framework` | string | none | Path to a local Vukem checkout to use instead of a release |
| `--standards` | bool | `false` | markdownlint and a `lint:md` script, `CHANGELOG.md` with `.config/cliff.toml`, Conventional Commits git hooks, a SemVer version ([project standards](#project-standards)) |
| `--license` | string | none | `mit`: `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` and `SECURITY.md` |
| `--ci` | bool | `false` | `.github/workflows/ci.yml` and `.github/dependabot.yml` |
| `--deploy` | string | none | `railway`: `.railway/railway.ts` ([Railway](/docs/deployment/docker-and-railway#deploy-on-railway)) |
| `--docker` | bool | `false` | `compose.yaml` running the app, PostgreSQL and a mail catcher ([local stack](/docs/deployment/docker-and-railway#the-local-stack-with-compose)) |

Rules: the name must start with a letter and contain only letters, digits, `-`, `_` and `.`. The folder must not exist. `--api`, `--templ` and `--inertia` are exclusive (`usage error: choose one of --api, --templ or --inertia`), and `--minimal` refuses all three. `--license` and `--deploy` take one value each and are checked before anything is written (`usage error: --deploy must be railway, not "fly"`).

What happens, in order:

1. The starter files are written (`gitignore` becomes `.gitignore`), then reshaped for the chosen stack. See [Starters](/docs/starters) for what each stack contains.
2. A production `Dockerfile` and `.dockerignore` are written for the stack and package manager ([Docker and Railway](/docs/deployment/docker-and-railway)).
3. `.editorconfig` and `.gitattributes` are written, plus whatever the [project standards](#project-standards) flags asked for.
4. The framework is required: the release that matches your CLI version, or `latest` for a `devel` build. With `--framework`, a `replace` directive points at your checkout instead.
5. [`govulncheck`](https://go.dev/doc/tutorial/govulncheck) is pinned as a [Go tool](https://go.dev/doc/modules/managing-dependencies#tools) (`go tool govulncheck ./...`). The templ stack also pins templ and generates the components.
6. `go mod tidy` runs, and a new `APP_KEY` is written to `.env` (copied from `.env.example`).
7. `git init` runs when Git is installed; a failure only warns. With `--standards` it then sets `core.hooksPath` to `.githooks`, so the hooks work in that clone without a hook manager.
8. Every stack except `--api` installs the frontend dependencies. A missing package manager or a failed install only warns, since the Go app runs without built assets in development.

`--minimal` also writes a `.buildtags` file containing `vukem_nosqlite`, which leaves the SQLite driver out of every build ([build tags](#build-tags)).

Then it prints the next steps: `.env`, the database choice, migrations, tests, the mail setup that verification and reset emails need, `vukem serve` and the deploy, each with the page that explains it. `README.md` lists every documentation section.

#### Project standards

Every project gets two files nobody has to decide about: `.editorconfig` (tabs of width 4, spaces for YAML, Markdown and JavaScript) and `.gitattributes` (LF everywhere, Windows clones included). Both only describe the indentation and line endings the starter already uses.

Everything else is a decision, so it is a flag. A scaffold that writes a licence, a CI pipeline and a platform configuration nobody asked for is its own kind of mess.

| Flag | Writes | Choose it when |
| --- | --- | --- |
| `--standards` | `.markdownlint-cli2.jsonc` and a `lint:md` script (with `markdownlint-cli2` pinned in `package.json`, which an `--api` project gets for this), `CHANGELOG.md` ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/) with `[Unreleased]`), `.config/cliff.toml`, `.githooks/commit-msg` and `.githooks/pre-commit`, and `"version": "0.1.0"` | the repository is maintained: reviewed commits, a changelog and tagged [SemVer](https://semver.org/spec/v2.0.0.html) releases |
| `--license mit` | `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md` | you are publishing it. The copyright holder comes from `--module` when it is a `github.com/owner/repo` path |
| `--ci` | `.github/workflows/ci.yml` (gofmt, `go vet`, `go test -race`, `go tool govulncheck`, `docker build`, and markdownlint with `--standards`) and `.github/dependabot.yml` | GitHub is the gate. Third-party actions are pinned to a commit SHA, `checkout` runs with `persist-credentials: false`, and each job declares the narrowest `permissions` |
| `--deploy railway` | `.railway/railway.ts` | Railway is the target |
| `--docker` | `compose.yaml` and its `.env` block | you want PostgreSQL and a mail catcher locally without installing either |

The git hooks need no Node and no hook manager: `commit-msg` checks the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) header with the shell Git already runs, and `pre-commit` runs `gofmt` and `go vet` on the staged Go files. In a clone that `vukem new` did not make, enable them once:

```bash
git config core.hooksPath .githooks
```

### `vukem serve`

`vukem serve` runs your app while you code. It builds `cmd/app`, starts it, and rebuilds and restarts it when a source file changes.

```bash
vukem serve
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--poll` | duration | `500ms` | How often to check the files for changes ([duration format](https://pkg.go.dev/time#ParseDuration): `1s`, `250ms`) |
| `--no-vite` | bool | `false` | Do not start the Vite dev server |

Under the hood:

- **What it watches.** Files ending in `.go` or `.templ`, plus `go.mod`, `go.sum`, `.buildtags` and `.env`. It skips hidden folders and `node_modules`, `vendor`, `storage`, `bin`, `dist`, `public` and `tmp`. Generated `*_templ.go` files are ignored, so a templ change rebuilds once.
- **Polling.** It compares modification times every `--poll` interval. No file-system notification library is involved, so it behaves the same on Windows, macOS and Linux.
- **templ.** When `.templ` files exist, `go tool templ generate` runs before each build.
- **Safe swaps.** It builds to `.vukem/serve/app-next`, stops the old process, then renames the new file into place. That works on Windows, where a running `.exe` cannot be overwritten.
- **Broken code.** A failed build prints the compiler errors (`vukem serve: build failed, keeping the previous version`) and the old version keeps answering.
- **Templates.** Views reload inside the app on every request in development, so editing an HTML template needs no rebuild.
- **Vite.** When `vite.config.ts`, `.js` or `.mjs` exists, `<pm> run dev` runs alongside. On exit, `resources/public/hot` is removed so pages do not point at a dead dev server.

<Callout type="warning" title="No graceful shutdown in development">
`serve` kills the old process before starting the new one; it does not wait for running requests or jobs. Use it for development only.
</Callout>

### `vukem build`

`vukem build` produces the production binary.

```bash
vukem build -o bin/blog
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-o` | string | `bin/app` (`bin\app.exe` on Windows) | Output path of the binary |

Steps:

1. `go tool templ generate` when `.templ` files exist.
2. When a `vite.config.*` exists: it checks `node_modules` exists (`frontend dependencies missing: run npm install first`), then runs `vite build` through the package manager (`npm exec -- vite build`, `bun x vite build`, `pnpm exec vite build` or `yarn exec vite build`).
3. `go build -trimpath -ldflags="-s -w"` of `./cmd/app` with `CGO_ENABLED=0` (like the production `Dockerfile`; a `CGO_ENABLED` you set yourself wins), plus the [build tags](#build-tags). `-trimpath` removes your local paths from the binary; `-s -w` drops debug symbols to make it smaller.

It prints `built bin/blog`. See [Single binary](/docs/deployment/single-binary) for what the binary embeds.

### Package manager detection

`serve`, `build` and `install:inertia` pick the package manager in this order:

1. The `packageManager` field of `package.json` (`"bun@1.3.0"` means Bun). `vukem new` writes it, so a new project keeps the manager it was created with.
2. The lockfile in the project:

   | Lockfile | Package manager |
   | --- | --- |
   | `bun.lock`, `bun.lockb` | Bun |
   | `pnpm-lock.yaml` | pnpm |
   | `yarn.lock` | Yarn |
   | `package-lock.json` | npm |

3. The first of `bun`, `npm`, `pnpm` and `yarn` found on your `PATH`, and `npm` when none is.

There is nothing to configure. `vukem new` takes `--pm` instead (falling back to step 3), because a new project has no `package.json` or lockfile yet.

### Build tags

A `.buildtags` file at the project root lists [Go build tags](https://pkg.go.dev/cmd/go#hdr-Build_constraints), one per line or comma-separated, with `#` comments. Every build the CLI runs (`build`, `serve` and delegated app commands) passes them as `go build -tags`.

```text title=".buildtags"
# Leave the SQLite driver out of the binary.
vukem_nosqlite
```

A tag may contain only letters, digits, `_` and `.`; anything else fails with `.buildtags: invalid build tag "..."`.

## Installers

The `install:*` commands copy **your own code** into the project: routes, controllers, pages, migrations and tests that you are free to edit. They are not hidden library calls. Each one checks every destination first, so nothing is written when a file already exists, unless you pass `--force`. Then it registers the new parts, appends the new keys to `.env.example` and runs `go mod tidy`.

| Command | Flags | Adds | Read more |
| --- | --- | --- | --- |
| `install:auth` | `--social`, `--2fa`, `--passkeys`, `--locales`, `--force` | Login, registration, email verification, password reset | [Authentication](/docs/security/authentication) |
| `install:api` | `--force` | API tokens, `/api/v1`, CORS, rate limiting | [REST APIs](/docs/rest-apis/overview) |
| `install:admin` | `--force` | Admin panel at `/admin` | [Admin](/docs/digging-deeper/admin) |
| `install:flags` | `--force` | Feature flags | [Feature flags](/docs/digging-deeper/feature-flags) |
| `install:billing` | `--force`, `--plans` | Stripe subscriptions | [Billing](/docs/digging-deeper/billing) |
| `install:inertia` | `--react`, `--vue`, `--svelte`, `--force`, `--no-install` | Inertia pages instead of HTMX | [Inertia](/docs/frontend/inertia) |
| `boost:install` | none | Guidelines and an MCP server for AI coding agents | [below](#vukem-boostinstall) |

### `vukem install:auth`

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--social` | string | none | Also add [social login](/docs/security/social-login) for a comma-separated list: `github`, `gitlab`, `discord`, `google`, `microsoft`, `linkedin`, `apple` (`x` is refused: X sends no email) |
| `--2fa` | bool | `false` | Also add [two-factor authentication](/docs/security/two-factor) (TOTP) |
| `--passkeys` | bool | `false` | Also add [passkey sign-in](/docs/security/passkeys) (WebAuthn) |
| `--locales` | string | the project's locales, else `en` | Message catalogs to write, comma separated (`en,es,pt-BR` ship catalogs); `en` is always written |
| `--force` | bool | `false` | Overwrite existing files |

- It writes the shared core (users, accounts, tokens, mails) once; `app/accounts/accounts.go` marks it as installed.
- Pages follow your frontend: `html/template` pages for HTMX, or React, Vue or Svelte pages when `package.json` lists an Inertia adapter.
- Run it again with only `--social`, `--2fa` or `--passkeys` on a project that has auth: it adds that part and leaves the rest alone.
- `--social` appends `SOCIAL_<NAME>_CLIENT_ID` and `SOCIAL_<NAME>_CLIENT_SECRET` to `.env.example`; Apple gets `SOCIAL_APPLE_CLIENT_ID`, `SOCIAL_APPLE_TEAM_ID`, `SOCIAL_APPLE_KEY_ID` and `SOCIAL_APPLE_PRIVATE_KEY_PATH`.
- A templ project is refused: `install:auth writes html/template pages; templ projects are not supported yet`.

### `vukem install:api`

Adds `POST /api/v1/tokens`, `GET /api/v1/me` and `DELETE /api/v1/tokens/current`, the auth core when missing, and `CORS_ALLOWED_ORIGINS` in `.env.example`. With two-factor authentication installed, issuing a token also asks for the code. Flags: `--force`, `--plans pro,business` (the plans on sale, `basic,pro` by default).

### `vukem install:admin`

Needs `install:auth` (`app/accounts/accounts.go`) and a web project (`routes/web.go`). It adds `routes/admin.go`, `app/admin/`, an audit-log migration, a test, and `ADMIN_EMAILS` in `.env.example`. Flag: `--force`. Next, run `vukem make:admin-resource Post` for each model.

### `vukem install:flags`

Needs `bootstrap/app.go` and `database/migrations/registry.go` (flag values live in the database, so `--minimal` projects are refused). It writes `app/features/features.go`, a `create_feature_flags_table` migration, and adds `vukem.WithFlags(features.All()...)` to `bootstrap/app.go`.

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--force` | bool | `false` | Rewrite the feature flags migration in place |

It is safe to re-run: `app/features/features.go` holds your flags and is **never** overwritten, not even with `--force` (it prints `kept app/features/features.go`). An existing feature flags migration is reused instead of adding a second one.

### `vukem install:billing`

Needs `install:auth` first (`install:billing bills the users of install:auth: run vukem install:auth first`). It writes the plans config, billing migration, Checkout and Billing Portal routes, the `POST /stripe/webhook` handler and tests, for HTMX or Inertia. It appends `STRIPE_KEY`, `STRIPE_WEBHOOK_SECRET`, one `STRIPE_PRICE_<PLAN>` per plan and `STRIPE_CURRENCIES` to `.env.example`, and requires `github.com/AlexGalhardo/vukem/contrib/stripe` at the latest release when your `vukem` CLI was built (a `replace` to your checkout when the framework itself is replaced). Flag: `--force`.

### `vukem install:inertia`

Turns an HTMX starter into an Inertia app. It **deletes** the HTMX pages, layouts, partials, components, upload demo and `resources/js/app.ts`, writes the Inertia pages, controllers and tests, adds `vukem.WithInertia(inertia.Config{})` after `vukem.WithVite(...)` in `bootstrap/app.go`, runs `go mod tidy` and installs the frontend dependencies. It checks that `bootstrap/app.go` can be patched before deleting anything: without the `vukem.WithVite(resources.Public())` line it fails and leaves the project as it was.

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--force` | bool | `false` | Required: confirms the HTMX pages, controllers and tests are replaced |
| `--react` | bool | `true` when none is set | React pages |
| `--vue` | bool | `false` | Vue pages |
| `--svelte` | bool | `false` | Svelte pages |
| `--no-install` | bool | `false` | Skip installing frontend dependencies |

A project that already calls `WithInertia` is refused (`this project already uses Inertia`). Commit your work before running it.

### `vukem boost:install`

Prepares the project for AI coding agents, in the style of Laravel Boost. It takes no flags and is safe to re-run.

- Writes Vukem guidelines into `AGENTS.md` between `<!-- vukem-boost:start -->` and `<!-- vukem-boost:end -->`; text outside the markers is kept.
- Adds `@AGENTS.md` to `CLAUDE.md` and writes skills to `.claude/skills/vukem-*` (CLI, database, frontend, HTTP, testing, validation).
- Registers the `vukem-boost` MCP server (`go run ./cmd/app boost:mcp`) in `.mcp.json`, and in `.cursor/mcp.json` and `.vscode/mcp.json` when those folders exist.

Every JSON file is checked before anything is written, so a broken one stops it: `.mcp.json is not valid JSON (fix or remove it first)`.

## Keys and maintenance mode

### `vukem key:generate`

Writes a new random `APP_KEY` to `.env`. If `.env` is missing, it starts from `.env.example`. The key signs sessions and encrypts data ([Encryption](/docs/security/encryption)).

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--show` | bool | `false` | Print the key instead of writing `.env` |
| `--force` | bool | `false` | Replace an existing non-empty `APP_KEY` |

Without `--force`, an existing key stops it: `APP_KEY is already set in .env (use --force to replace it; existing sessions and encrypted data become unreadable)`.

### `vukem key:rotate`

Writes a new `APP_KEY` and moves the old one to the front of `APP_PREVIOUS_KEYS`, so old sessions and encrypted values still open ([key rotation](/docs/security/encryption)). It takes no flags or arguments and never prints a key.

- It refuses a missing `.env`, an empty `APP_KEY`, and any malformed current or previous key, since a bad previous key would stop the app from booting.
- It keeps `export`, indentation, inline comments and CRLF line endings.
- It writes through a synced temporary file, then renames it, so a crash never leaves a half-written `.env`. A symlinked `.env` stays a symlink.
- It warns on stderr when more than 3 previous keys remain: each one can still forge sessions and signed links.

### `vukem down` and `vukem up`

`vukem down` puts the app in maintenance mode by writing `storage/framework/down`. The `middleware.Maintenance` middleware then answers every request with `503 Service Unavailable`, using the `errors/503` view or a problem+json body; `/up` keeps answering for health checks. `vukem up` deletes the file. A running app picks up both without a restart.

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--secret` | string | none | Visitors of `/<secret>` get a signed bypass cookie and see the live site |
| `--with-secret` | bool | `false` | Generate a random secret and print the bypass path |
| `--retry` | duration | none | `Retry-After` sent with the 503, such as `60s` |

```bash
vukem down --with-secret --retry 60s
```

```text
The application is in maintenance mode (vukem up brings it back).
Bypass: open /<secret> once to get a cookie that lets you in.
```

The secret is stored hashed. An unreadable state file keeps the app down rather than up.

## Generators

Each `make:*` command renders a template, formats Go output with [`go/format`](https://pkg.go.dev/go/format) (like `gofmt`), and writes the file. Many also **register** the new code by appending it to a list your app reads at startup.

| Command | Writes | Registers in |
| --- | --- | --- |
| `make:controller <Name>` | `app/controllers/<name>_controller.go` | — |
| `make:model <Name>` | `app/models/<name>.go` | — |
| `make:migration <name>` | `database/migrations/<timestamp>_<name>.go` | `All()` in `database/migrations/registry.go` |
| `make:middleware <Name>` | `app/middleware/<name>.go` | — (you add it with `r.Use`) |
| `make:request <Name>` | `app/requests/<name>.go` | — |
| `make:command <Name>` | `app/commands/<name>.go` | `Commands()` in `bootstrap/commands.go` |
| `make:provider <Name>` | `app/providers/<name>_provider.go` | `Providers()` in `bootstrap/providers.go` |
| `make:resource <Name>` | `app/resources/<name>.go` | — |
| `make:factory <Name>` | `database/factories/<name>_factory.go` | — |
| `make:seeder <Name> [--app]` | `database/seeders/<name>_seeder.go` | `All()` in `database/seeders/registry.go`; with `--app`, an `AppSeeder` registered in `AllApp()` |
| `make:event <Name>` | `app/events/<name>.go` | — |
| `make:listener <Name>` | `app/listeners/<name>.go` | `All()` in `app/listeners/registry.go` |
| `make:job <Name>` | `app/jobs/<name>.go` | `All()` in `app/jobs/registry.go` |
| `make:mail <Name> [--react]` | `app/mail/<name>.go` and `resources/views/mail/<name>.html` (`--react`: `resources/js/emails/<name>.tsx`) | — |
| `make:policy <Name>` | `app/policies/<name>_policy.go` | `All()` in `app/policies/registry.go` |
| `make:admin-resource <Model>` | `app/admin/<model>.go` and `tests/admin_<model>_test.go` | `Resources()` and `Policies()` in `app/admin/registry.go` |
| `make:test <Name>` | `tests/<name>_test.go` | — |
| `make:proto <Name>` | `proto/<name>/v1/<name>.proto` | — ([gRPC](#grpc-code-generation)) |

Every generator takes `--force` (overwrite an existing file) and exactly one name.

### Rules every generator follows

- **No silent overwrite.** An existing file fails with `<path> already exists (use --force to overwrite)`. Generators that write several files (`make:model -m -f -c`) check them all first, so a clash writes nothing.
- **Optional suffixes.** A conventional suffix is stripped from the name: `PostController`, `BillingProvider`, `SendReportsCommand`, `PostSeeder`, `PostPolicy`, `WelcomeMail`, `PostPublishedEvent`, `NotifyListener`, `SendDigestJob`, `PostResource`, `PostFactory`, `PostsTest` and `BlogService` (for `make:proto`) all work.
- **Needs `go.mod`.** Generators read the module path from `go.mod`; outside a project you get `no go.mod here: run vukem inside a project`.
- **Registration edits the syntax tree.** The CLI parses the registry file with Go's [`go/parser`](https://pkg.go.dev/go/parser), finds the slice the function returns, appends the new entry and its import, and formats the file. Running it twice registers once.
- **Missing policies registry.** Starters ship no `app/policies/registry.go`; the first `make:policy` creates it with an empty `All()`. The policy takes `*models.User`: without one (no `install:auth` yet), the CLI prints a note.
- **Manual fallback.** If you restructured the file (or it does not exist), the file is still created and the CLI prints the line to add:

```text
could not update app/policies/registry.go automatically; add this to All():

	authz.For[*models.Post](PostPolicy{}),
```

### Generator flags

Only these generators have flags besides `--force`:

| Command | Flag | Type | Default | What it does |
| --- | --- | --- | --- | --- |
| `make:controller` | `--resource` | bool | `false` | The seven resource actions: `Index`, `Create`, `Store`, `Show`, `Edit`, `Update`, `Destroy` |
| `make:controller` | `--api` | bool | `false` | The five JSON actions: `Index`, `Store`, `Show`, `Update`, `Destroy` |
| `make:model` | `-m` | bool | `false` | Also create a `create_<table>_table` migration |
| `make:model` | `-f` | bool | `false` | Also create a factory |
| `make:model` | `-c` | bool | `false` | Also create a resource controller (seven actions) |
| `make:listener` | `--event` | string | none | Required: the event type it handles |
| `make:listener` | `--async` | bool | `false` | Run in the background; errors are logged |
| `make:listener` | `--queued` | bool | `false` | Run as a queue job: retried, survives restarts |
| `make:proto` | `--force` | bool | `false` | Overwrite only the `.proto`; `buf.yaml` and `buf.gen.yaml` are never replaced |

Without `--resource` or `--api`, a controller gets one `Index` action.

### Examples from the blog

A middleware is a plain `func(http.Handler) http.Handler`, the standard [`net/http`](https://pkg.go.dev/net/http#Handler) shape:

```bash
vukem make:middleware EnsureAdmin
```

```go title="app/middleware/ensure_admin.go"
package middleware

import "net/http"

// EnsureAdmin wraps handlers; register it with r.Use, group.Use or
// route.Use.
func EnsureAdmin(next http.Handler) http.Handler {
	return http.HandlerFunc(
		func(w http.ResponseWriter, r *http.Request) {
			next.ServeHTTP(w, r)
		},
	)
}
```

A command is created **and** registered:

```bash
vukem make:command SendReports
```

```text
created app/commands/send_reports.go
created app/commands/doc.go
updated bootstrap/commands.go
```

```go title="bootstrap/commands.go"
package bootstrap

import (
	"blog/app/commands"

	vukem "github.com/AlexGalhardo/vukem"
)

// Commands lists the application commands; vukem make:command appends
// here.
func Commands() []vukem.Command {
	return []vukem.Command{
		commands.SendReports(),
	}
}
```

Now `vukem send-reports` runs it. See [Application lifecycle](/docs/architecture/lifecycle) for how commands run.

A listener's registration depends on its flag:

| Command | Line added to `All()` |
| --- | --- |
| `make:listener NotifyFollowers --event PostPublished` | `events.On(NotifyFollowers)` |
| `... --async` | `events.OnAsync(NotifyFollowers)` |
| `... --queued` | `events.OnQueued("notify_followers", NotifyFollowers)` |

`--async` and `--queued` together fail with `usage error: --async and --queued are exclusive`, before any file is written. See [Events](/docs/digging-deeper/events).

`make:job` registers `queue.Handle(HandleSendDigest(app))` when `app/jobs/registry.go` declares `func All(app *vukem.App)`, so the handler can use your app's services; older registries get `queue.Handle(HandleSendDigest)`. See [Queues](/docs/digging-deeper/queue).

`make:admin-resource` needs the admin panel (`app/admin/registry.go`) and an existing `type <Model> struct` in `app/models`. When `app/requests` declares `var <Model>Schema`, the resource validates its forms with it.

### Migration names choose the template

`make:migration` turns the name into snake case and picks a body from its shape:

| Name | Body |
| --- | --- |
| `create_comments_table` | `s.Create("comments", ...)` with `t.ID()` and `t.Timestamps()`; `Down` drops the table |
| `add_slug_to_posts_table`, `remove_x_from_posts_table`, `index_x_on_posts_table`, `alter_posts_table`, `change_posts_table`, `update_posts_table` | `s.Table("posts", ...)` in `Up` and `Down`, empty for you to fill |
| anything else | `Up` and `Down` that return `nil` |

The file name and ID use the UTC time: `20260101120000_add_slug_to_posts_table`. The function is `m20260101120000AddSlugToPostsTable()`. See [Migrations](/docs/database/migrations).

### Custom stubs

The templates are [`text/template`](https://pkg.go.dev/text/template) files embedded in the CLI. To change what a generator writes, put a file with the same name in your project's `stubs/` folder; it wins over the embedded one.

| Stub | Used by |
| --- | --- |
| `controller.go.tmpl`, `model.go.tmpl`, `migration.go.tmpl`, `middleware.go.tmpl`, `request.go.tmpl` | The matching `make:*` |
| `command.go.tmpl`, `provider.go.tmpl`, `resource.go.tmpl`, `factory.go.tmpl`, `seeder.go.tmpl` | The matching `make:*` |
| `seeder_app.go.tmpl` | `make:seeder --app` |
| `event.go.tmpl`, `listener.go.tmpl`, `job.go.tmpl`, `policy.go.tmpl`, `test.go.tmpl` | The matching `make:*` |
| `mail.go.tmpl`, `mail.html.tmpl`, `mail_react.go.tmpl`, `mail.tsx.tmpl`, `mail_go.ts.tmpl` | `make:mail` |
| `admin_resource.go.tmpl`, `admin_resource_test.go.tmpl` | `make:admin-resource` |
| `service.proto.tmpl`, `buf.yaml.tmpl`, `buf.gen.yaml.tmpl` | `make:proto` |

The data a stub can read, for the name `BlogPost`:

| Field | Value | Set for |
| --- | --- | --- |
| `.Name` | `BlogPost` | all |
| `.Snake` | `blog_post` | all |
| `.Kebab` | `blog-post` | all |
| `.Camel` | `blogPost` | all |
| `.Plural` | `blog_posts` | all |
| `.Module` | `blog` (from `go.mod`) | all |
| `.Table`, `.Timestamp`, `.ID`, `.Func`, `.Create`, `.Alter` | table, time, ID, function name, kind | migrations |
| `.Resource`, `.API` | which actions | controllers |
| `.Event` | `PostPublished` | listeners |
| `.App` | the registry takes the app | jobs |
| `.Slug`, `.HasRequest` | URL segment, schema exists | admin resources |
| `.GoPkg`, `.ProtobufVersion`, `.ConnectVersion` | `blogpostv1`, plugin versions | proto |

A field the data does not have is an error (`missingkey=error`), not an empty string. A `.go.tmpl` stub that produces invalid Go fails with `stub <name> produced invalid Go`. The `install:*` scaffolds are not stubs and cannot be overridden. There is no command yet to copy the embedded stubs; take them from `internal/cli/stubs` in the Vukem repository.

## gRPC code generation

`vukem make:proto Blog` writes `proto/blog/v1/blog.proto` (package `blog.v1`, one `GetBlog` RPC), plus `buf.yaml` and `buf.gen.yaml` when they do not exist yet. It then prints the `go get -tool` lines for the code generators.

`vukem codegen:rpc` turns the `.proto` files into Go and connect-go code:

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `--protoc` | bool | `false` | Use `protoc` even when `buf.gen.yaml` exists |
| `-proto` | string | `proto` | Folder of the `.proto` files (protoc mode) |
| `-out` | string | `gen` | Output folder (protoc mode) |

1. It refuses to run until `protoc-gen-go` and `protoc-gen-connect-go` are `tool` lines in `go.mod`, and prints the `go get -tool` commands to add them.
2. With `buf.gen.yaml`: `go tool buf generate` when buf is a tool of the module, else `buf generate` from your `PATH`.
3. Otherwise `protoc` with the plugins from `go tool -n`, `paths=source_relative`.

See [gRPC](/docs/rest-apis/grpc) for the full workflow.

## App commands

Any command the global CLI does not own runs inside your app:

```bash
vukem migrate
vukem migrate:status --json
vukem route:list
vukem queue:work --queue high,default
vukem openapi:export > openapi.json
vukem send-reports
```

`vukem` builds `cmd/app` into `.vukem/bin/app` and runs it with the same arguments, input and output. It rebuilds only when a `.go`, `.templ`, `go.mod`, `go.sum` or `.buildtags` file is newer than the binary, so repeated commands start at once. A rebuild runs `templ generate` first in templ projects, like `vukem serve`. Outside a project you get `unknown command "migrate" (app commands need a Vukem project with cmd/app)`. Running the binary yourself works too: `go run ./cmd/app migrate`.

Unlike the global CLI, app commands use the plain `flag` package, so **flags go before positional arguments**. `db:seed` is the exception: it reads seeder names first, then flags (`db:seed UsersSeeder -force`), because the flags it accepts depend on the seeders you name.

| Command | Flags | What it does |
| --- | --- | --- |
| `serve` | none | Runs the HTTP server and scheduler; the default when no command is given |
| `about` | `-json` | Shows application, environment and security settings, secrets redacted |
| `migrate` | none | Runs pending migrations |
| `migrate:rollback` | `-step N` | Rolls back the last batch, or the last N migrations |
| `migrate:reset` | `-force` | Rolls back every migration |
| `migrate:fresh` | `-force` | Drops all tables and re-runs every migration |
| `migrate:status` | `-json` | Shows which migrations ran |
| `db:seed` | `-class Name` (repeatable), `-force` | Runs every seeder, or the named ones in order ([Seeders](/docs/database/factories-seeders)) |
| `db:wipe` | `-force` | Drops every table |
| `route:list` | `-json` | Lists the registered routes |
| `queue:work` | `-queue`, `-concurrency`, `-sleep 1s`, `-once`, `-stop-when-empty` | Processes jobs until stopped ([Queues](/docs/digging-deeper/queue)) |
| `queue:failed` | `-json` | Lists failed jobs |
| `queue:retry` | IDs or `all` | Re-queues failed jobs |
| `queue:forget` | IDs or `all` | Deletes failed jobs |
| `schedule:run` | none | Runs the tasks due now; call it every minute from cron ([Scheduler](/docs/digging-deeper/scheduler)) |
| `schedule:work` | none | Runs the scheduler in the foreground |
| `schedule:list` | none | Lists the tasks and their next run |
| `cache:prune` | none | Deletes expired database cache entries |
| `session:prune` | none | Deletes expired database sessions |
| `openapi:export` | `-prefix` | Prints the OpenAPI 3.1 document ([OpenAPI](/docs/rest-apis/openapi)) |
| `codegen:types` | `-zod`, `-o file`, `-prefix` | TypeScript types, plus Zod schemas with `-zod` |
| `codegen:client` | `-lang ts\|go`, `-o file`, `-package apiclient` | A typed API client ([Client generation](/docs/rest-apis/client-generation)) |
| `codegen:routes` | `-o resources/js/routes.ts` | Typed frontend routes ([Inertia](/docs/frontend/inertia)) |
| `ssr:start` | `-bundle`, `-runtime node`, `-restart-delay 1s` | Runs the Inertia SSR server and restarts it on crash |
| `ssr:check` | `-url http://127.0.0.1:13714` | Exits 1 unless the SSR server answers `/health` |
| `boost:mcp` | none | The MCP server for coding agents, over stdio |
| `key:generate` | none | Prints a new `APP_KEY`; never writes `.env` |
| `openapi:serve` | `-addr` | Previews the API reference; only when you register `apidocs.Command()` |

`-o -` prints a codegen result to stdout. `openapi:export` and the three `codegen:*` commands run in **warmup** mode: they register routes but open no database and boot no provider, so `APP_KEY` is optional. Destructive commands (`migrate:reset`, `migrate:fresh`, `db:seed`, `db:wipe`) need `-force` when `APP_ENV=production`. Add your own with `vukem make:command`.

### `APP_KEY` without the global CLI

Docker images and CI runners usually ship only your compiled binary. Its own `key:generate` **prints** a key and never touches `.env`. It runs before the app boots, so it works even when no `APP_KEY` exists yet:

```bash
./app key:generate
export APP_KEY="$(./app key:generate)"
docker run --rm my-app key:generate
```

Only the key goes to stdout; errors and help go to stderr, so a typo never ends up inside `APP_KEY`. The built-in `key:generate` always wins over an app command with the same name. Note the difference: `vukem key:generate` (the global CLI) writes `.env`, but `vukem` never delegates that name, so use the binary directly to print a key.

## Common mistakes

**Running a project command outside the project.**

```bash
# Wrong: in your home folder
vukem serve
```

```text
error: no cmd/app in this directory: run vukem inside a Vukem project
```

Right: `cd blog` first. The same goes for generators (`no go.mod here`).

**Expecting a generator to replace your file.**

```bash
# Wrong: post.go already exists
vukem make:model Post
```

```text
error: app/models/post.go already exists (use --force to overwrite)
```

Right: pick a new name, or pass `--force` once you have committed your changes.

**Forgetting the event of a listener.**

```bash
# Wrong
vukem make:listener NotifyFollowers
# Right
vukem make:listener NotifyFollowers --event PostPublished
```

The first prints `usage error: --event is required` and exits with code 2.

**Wiping a production database by accident.**

```bash
# With APP_ENV=production
vukem migrate:fresh
```

```text
refusing to run a destructive command in production without --force
```

Right: check you are on the server you mean, then run `vukem migrate:fresh -force`. The same guard protects `migrate:reset`, `db:seed` and `db:wipe`.
