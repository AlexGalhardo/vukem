These are the commands that create a project, run it while you code and build it for production. They are **global** commands: they work on files and call the Go toolchain, and they never import your code. Back to the [command cheat sheet](/docs/cli/reference).

## `vukem new`

Create a project in a new folder from the starter embedded in the CLI.

**Usage**

```text
vukem new [flags] <name>
```

**Arguments**

| Argument | Required | Meaning |
| --- | --- | --- |
| `<name>` | yes | Folder, `APP_NAME` and the `vukem.WithName` default in `bootstrap/app.go`. Starts with a letter; letters, digits, `-`, `_` and `.` only. The folder must not exist. |

**Flags**

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-module` | string | the project name | Go [module path](https://go.dev/ref/mod#module-path) in `go.mod`. Also gives the copyright holder of `-license` when it is `github.com/owner/repo`. |
| `-api` | bool | `false` | JSON API starter: tokens, `/api/v1`, no views, no sessions, no frontend. |
| `-templ` | bool | `false` | HTMX starter with [templ](https://templ.guide) components instead of `html/template`. Pins templ as a Go tool and generates the components. |
| `-inertia` | string | none | Inertia starter. Value: `react`, `vue` or `svelte`. |
| `-minimal` | bool | `false` | HTMX starter without a database: no posts, uploads, migrations or SQLite driver. Writes `.buildtags` with `vukem_nosqlite`. |
| `-pm` | string | see below | JavaScript package manager: `npm`, `bun`, `pnpm` or `yarn`. |
| `-assets-image` | string | the package manager's image | Assets-stage base image only: an exact tag or a `sha256` digest. The runtime stays Alpine. An error on `-api`, which has no assets stage. |
| `-no-install` | bool | `false` | Do not install frontend dependencies. |
| `-framework` | string | none | Path to a local Vukem checkout. Adds a `replace` directive instead of requiring a release. |
| `-standards` | bool | `false` | `.markdownlint-cli2.jsonc`, `lint:md` and `secrets:scan` scripts, `CHANGELOG.md`, `.config/cliff.toml`, `.githooks/commit-msg` and `pre-commit` (secret scan, `gofmt`, `go vet`), `.betterleaks.toml`, version `0.1.0`, and on a stack with front-end assets `biome.json` (Biome v2, 2-space, double quotes) with `lint:js` and `format` scripts and an exact-version `@biomejs/biome` devDependency. Sets `core.hooksPath` to `.githooks`. See [Secret scanning](/docs/security/secret-scanning). |
| `-license` | string | none | `mit`: `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, and the GitHub issue and pull request templates. |
| `-ci` | bool | `false` | `.github/workflows/ci.yml` (with a pinned Betterleaks secret-scanning job), `.github/workflows/release.yml`, `scripts/release-notes.go`, `.github/dependabot.yml` and `.betterleaks.toml`. `release.yml` publishes the matching `CHANGELOG.md` section, then pushes the image to GHCR and attests the build. It fails when that section is missing or empty, before either publish. GoReleaser runs only when `.config/goreleaser.yaml` or `.goreleaser.yaml` exists. Also writes `.github/pull_request_template.md`, the `.github/ISSUE_TEMPLATE/` forms and, for a `github.com/<owner>/<repo>` module path, `.github/CODEOWNERS`. |
| `-deploy` | string | none | `railway`: `.railway/railway.ts`. |
| `-docker` | bool | `false` | `compose.yaml` with the app, PostgreSQL and a mail catcher, plus its `.env` block. Every published port (3000, 5432, 8025) is bound to `127.0.0.1`, so the stack is not reachable from the network. |

**Interactions and conflicts**

- `-api`, `-templ` and `-inertia` are exclusive. `-minimal` refuses all three.
- With none of them, on a terminal, `new` asks which stack you want. Without a terminal (CI, a pipe) it picks HTMX.
- `-pm` default: when you omit it, `new` uses the first of `bun`, `npm`, `pnpm`, `yarn` found on `PATH`. The choice is written to `package.json` as `packageManager`, and later commands (`serve`, `build`) follow it.
- `-api` has no frontend, so `-pm` and `-no-install` change nothing for it.
- `-inertia`, `-license` and `-deploy` values are validated before anything is written.
- `-standards`, `-license`, `-ci`, `-deploy` and `-docker` are opt-in. Nothing in this group is written by default, but on a terminal `new` asks two questions it has no flag for yet: *Add best-practice project configs?* (yes, the default, is `-standards` and `-ci`) and *Is this an open source project?* (no is the default; yes is `-license mit`). A flag answers its own question, so `-standards` or `-ci` skips the first and `-license` skips the second, and without a terminal nothing is asked.

**Environment**: `PATH` (finds `go`, `git`, the package manager). It writes `APP_KEY` into the new `.env`.

**What it writes, in order**

1. The starter files for the stack (`gitignore` becomes `.gitignore`).
2. `Dockerfile` and `.dockerignore` for the stack and package manager. `-assets-image` replaces only the assets-stage `FROM`.
3. `.editorconfig` and `.gitattributes`, then the optional files above.
4. `go.mod` requiring the framework release that matches the CLI (the latest for a `devel` build), or a `replace` with `-framework`. It pins `govulncheck` as a Go tool.
5. `go mod tidy`, then `.env` copied from `.env.example` with a new `APP_KEY`.
6. `git init` when Git is installed (a failure only warns).
7. The frontend dependencies, except for `-api` or `-no-install`. A missing package manager or a failed install only warns.

**Errors**

| Message | Exit | Fix |
| --- | --- | --- |
| `usage error: expected exactly one project name` | 2 | Pass one name. |
| `usage error: invalid project name "1bad" (letters, digits, '-', '_' and '.')` | 2 | Start with a letter. |
| `error: blog already exists` | 1 | Pick another name or remove the folder. |
| `usage error: choose one of --api, --templ or --inertia` | 2 | Keep one stack flag. |
| `usage error: --minimal is an HTMX starter: drop --api, --templ and --inertia` | 2 | Drop the extra flag. |
| `usage error: --inertia must be react, vue or svelte, not "angular"` | 2 | Use a listed framework. |
| `usage error: --license must be one of mit, not "gpl"` | 2 | Only `mit` exists. |
| `usage error: --deploy must be railway, not "fly"` | 2 | Only `railway` exists. |
| `usage error: unknown package manager "foo" (want bun, npm, pnpm, yarn)` | 2 | Use a listed manager. |
| `go: ... reading ...\go.mod: open ...` | 1 | `-framework` must point to a folder with the framework's `go.mod`. |

**Example: a blog**

```bash
vukem new blog
cd blog
```

```text
created .editorconfig
created .gitattributes
APP_KEY written to .env

Created blog (htmx 4.0.0, Tailwind, SQLite). Next:

  1. cd blog
  2. read .env: APP_KEY is set; APP_URL, the database and mail live here
  3. pick a database: SQLite is the default, and PostgreSQL, MySQL or MongoDB
     need their driver in bootstrap/app.go
  4. apply the migrations: vukem migrate
  ...
  7. start the app: vukem serve, then open http://localhost:3000
  8. deploy the Dockerfile, or vukem build for a single binary
```

Output is shortened here. The real command also prints the documentation link for each step.

**Example: an API with project standards**

```bash
vukem new shop --api --module github.com/acme/shop --standards --license mit --ci
```

This creates a JSON API project whose module is `github.com/acme/shop`, with a changelog, Conventional Commits hooks, an MIT licence and a GitHub Actions pipeline.

## `vukem serve`

Run the app while you code. It builds `cmd/app`, starts it, and rebuilds and restarts it when a source file changes.

**Usage**

```text
vukem serve [flags]
```

**Arguments**: none.

**Flags**

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-poll` | duration | `500ms` | How often to check files for changes. Go [duration](https://pkg.go.dev/time#ParseDuration): `250ms`, `1s`. |
| `-no-vite` | bool | `false` | Do not start the Vite dev server. |
| `-no-codegen` | bool | `false` | Do not run `vukem codegen` after each successful build. |

**Interactions**

- Vite starts only when `vite.config.ts`, `.js` or `.mjs` exists. The package manager comes from `package.json`, then the lockfile.
- `.templ` files make `go tool templ generate` run before each build.
- `-no-vite` is useful when you run Vite in another terminal.
- After each successful build it runs `vukem codegen`, which refreshes `routes.ts` and the API clients that exist; a failure is printed and the app still starts. `-no-codegen` skips it.

**Environment**: your app's `.env` and process environment (`PORT`, `HOST`, `APP_ENV`, ...). `.env` is also watched.

**What it watches**: `.go` and `.templ` files, `go.mod`, `go.sum`, `.buildtags` and `.env`. It skips hidden folders, `node_modules`, `vendor`, `storage`, `bin`, `dist`, `public` and `tmp`, and generated `*_templ.go` files.

**Files it creates**: `.vukem/serve/app-next` (the next build, renamed over the running binary after the old process stops). Add `.vukem/` to `.gitignore`; the starters do. It removes `resources/public/hot` on exit.

**Errors**

| Message | Fix |
| --- | --- |
| `error: no cmd/app in this directory: run vukem inside a Vukem project` | `cd` into the project root. |
| `vukem serve: build failed, keeping the previous version` | Read the compiler errors above it. The old version keeps answering. Save a fixed file to rebuild. |
| `error obtaining VCS status: exit status 128` above a failed build | Go stamps the build with Git data and Git failed (broken or unowned repository). Fix the repository or its `safe.directory`. |

Ctrl+C stops it. There is no graceful shutdown of the old process on a rebuild, so use `serve` for development only.

**Example**

```bash
vukem serve
```

```text
time=2026-10-24T19:17:12.787-03:00 level=INFO msg="http server starting" addr=localhost:3000 env=development
```

**Advanced: slower polling, no Vite**

```bash
vukem serve -poll 2s -no-vite
```

Checks files every 2 seconds, which saves CPU on large trees or network drives, and leaves the frontend to a Vite you started yourself.

## `vukem studio`

Open vukem-studio, the read-only data browser of the project's database. The browser is its own module (`contrib/studio`, experimental): the CLI installs the pinned release into `.vukem/bin` with `go install` the first time and runs it.

**Usage**

```text
vukem studio [flags]
```

**Arguments**: none.

**Flags**

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-bin` | string | none | Run this vukem-studio binary and skip the install (to develop Studio itself). |
| `-dir` | string | the project directory | Project whose `.env` and database are read. |
| `-port` | int | `4984` | Port on `127.0.0.1`; `0` picks a free one. |
| `-no-open` | bool | `false` | Do not open the browser. |
| `-allow-production` | bool | `false` | Run even with `APP_ENV=production` (an unset `APP_ENV` counts as production). |
| `-database-url` | string | `DATABASE_URL` | Use this database instead. |
| `-version` | bool | `false` | Print the vukem-studio version and exit. |
| `-write` | bool | `false` | Enable editing of documents and keys (see below). Without it nothing can change data. |
| `-refresh` | duration | `2s` | Interval of the live refresh; a negative value turns it off; the minimum is `500ms`. |
| `-mongo-url` | string | `MONGO_URL` | Use this MongoDB URL. |
| `-mongo-database` | string | `MONGO_DATABASE` | The MongoDB database when the URL has none. |
| `-redis-url` | string | `REDIS_URL` | Use this Redis URL. |
| `-mongo-watch` | bool | `false` | Reserved: change streams instead of polling are not implemented yet (Studio polls). |
| `-redis-notify` | bool | `false` | Reserved: keyspace notifications instead of polling are not implemented yet (Studio polls). |

**Sources**: the SQL database from `DATABASE_URL`, MongoDB from `MONGO_URL` (and `MONGO_DATABASE`) and Redis from `REDIS_URL`; a source that is not configured is not shown. A page refreshes itself when its data changes (the server polls every `-refresh` and sends a server-sent event only on a change; at most 8 streams at a time).

**Editing** (`-write`): documents can be inserted, replaced and deleted, and Redis strings, hash fields and TTLs edited, with a typed confirmation for every deletion (the document's `_id` or the key name). Every write is logged on stderr (source, action, target and result; never the values). With `-write` and `APP_ENV=production` you still need `-allow-production`. The MongoDB console refuses `$where`, `$function` and `$accumulator` always, and `$out` and `$merge` without `-write`. The Redis console runs only the commands on an allow-list (reads always, writes with `-write`); `KEYS`, `FLUSHALL`, `CONFIG`, `EVAL` and the rest are refused. Keys are browsed with `SCAN`, never `KEYS`.

**Security**: it listens on loopback only and answers 403 to any other peer, to a request with a proxy header, and to a `Host` that is not a loopback name. The start URL carries a random token that is traded for an `HttpOnly`, `SameSite=Strict` cookie. Every response has a strict Content Security Policy. Nothing writes to the database. Passwords and URLs never appear in the output.

```text
vukem-studio v0.1.0 (read-only)
  sql   sqlite  storage/database.sqlite
  open  http://127.0.0.1:4984/?token=...
Press Ctrl+C to stop.
```

**Exit codes**: `0` stopped with Ctrl+C, `1` an error, `2` bad usage or a refusal (production without `-allow-production`).

## `vukem build`

Produce the production binary.

**Usage**

```text
vukem build [flags]
```

**Arguments**: none.

**Flags**

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-o` | string | `bin/app` (`bin\app.exe` on Windows) | Output path of the binary. |
| `-ldflags` | string | none | Extra linker flags, appended to `-s -w`, for example `-X main.version=v1.2.3`. |
| `-ssr` | bool | `false` | Also build the Inertia SSR bundle with `vite build --ssr`. Fails with `-ssr needs a Vite project (vite.config.ts, .js or .mjs)` without a Vite config. |

**Steps**

1. `go tool templ generate` when `.templ` files exist.
2. When a `vite.config.*` exists: checks `node_modules`, then runs `vite build` through the package manager (`npm exec -- vite build`, `bun x vite build`, `pnpm exec vite build`, `yarn exec vite build`); with `-ssr`, then `vite build --ssr`.
3. `go build -trimpath -ldflags="-s -w"` of `./cmd/app` (plus your `-ldflags`) with `CGO_ENABLED=0` and the tags from `.buildtags`.

To stamp the release into the binary, declare `var version = "dev"` in `cmd/app/main.go`, pass it to `vukem.WithVersion(version)`, and build with `vukem build -ldflags "-X main.version=$(git describe --tags)"`. `GET /up` then reports it (see [Health checks](/docs/architecture/lifecycle#health-checks)).

**Environment**: `CGO_ENABLED` (your value wins). `PATH`.

**Files it creates**: the binary, plus the generated `*_templ.go` files and the Vite output when the project has templ or Vite.

**Build tags**: `.buildtags` lists tags, one per line or comma-separated, with `#` comments. A tag may contain only letters, digits, `_` and `.`; otherwise `.buildtags: invalid build tag "..."`. The same tags apply to `serve` and to every delegated app command.

**Errors**

| Message | Fix |
| --- | --- |
| `error: no cmd/app in this directory: run vukem inside a Vukem project` | Run it in the project root. |
| `error: frontend dependencies missing: run bun install first` | Install the dependencies. The command names the package manager the project uses. |
| Compiler errors | Fix the Go code. |

**Example**

```bash
vukem build -o bin/shop
```

```text
built bin/shop
```

For the `shop` API project the binary is about 18 MB and contains every app command (`./bin/shop migrate:status`).

**Advanced: build without SQLite**

```bash
echo vukem_nosqlite > .buildtags
vukem build -o bin/blog
```

The SQLite driver is left out of the binary. Use it with PostgreSQL or MySQL in `DATABASE_URL`.

## `vukem doctor`

Report optional tools and the facts you need before a deploy: the CLI version next to the Go runtime, whether Go or Bun is installed, whether the Go version satisfies the `go.mod` minimum, which lockfile is present, whether `APP_KEY` is set, whether `APP_ENV` is one of `development`, `test` and `production`, whether the SQLite directory is writable, `PORT` and proxy settings, and the Vite manifest.

The report says `app_key: set` or `app_key: missing`. It never prints the key, other env values, or database credentials.

**Usage**

```text
vukem doctor
vukem doctor --json
vukem doctor --strict
```

| Flag | Default | Result |
| --- | --- | --- |
| (none) | informative | Print the report and exit 0, even when a project check failed |
| `--json` | off | One JSON object on stdout (`cli`, `runtime`, `upgrade`, `tools`, `checks`) |
| `--strict` | off | Exit 1 when a project check has status `fail` |

A missing optional tool does not fail `--strict`. CI that does not use Betterleaks, LilyPond, or FFmpeg stays green. Core lists only Betterleaks. An application registers its own tools in `.vukem/doctor.json`; those names are not built into Vukem.

```json
{
  "tools": [
    {
      "name": "lilypond",
      "why": "engraving scores",
      "install": "https://lilypond.org/download.html"
    }
  ]
}
```

```text
betterleaks: 1.9.0 (/usr/local/bin/betterleaks)
cli: v0.38.0
runtime: go1.27.2
upgrade: https://vukem.dev/docs/cli/reference-new#upgrading-a-starter
go_version: go go1.27.4 satisfies go.mod go1.27.4
app_key: set
app_env: development
database: sqlite directory is writable
```

In production a missing `resources/public/build/.vite/manifest.json` is a failed check. In any other `APP_ENV` it is a warning, and warnings do not fail `--strict`.

## Upgrading a starter

`vukem doctor` prints the CLI revision and the Go runtime on consecutive lines, then the `upgrade` URL. That pair is the set you tested. A newer CLI is not a promise that an older revision still matches today's images or examples. The assets image pins `oven/bun:1.4.4-alpine` and the Node image pins an exact tag; the workflow audit installs Bun `1.4.4`. When those pins change, the changelog for the CLI revision names the new tags. Do not read a future tag back onto an old revision.

No command rewrites a project in place: `vukem upgrade` reports and never overwrites a file (below). `vukem new` refuses a folder that already exists. `install:*` and `make:*` refuse a file that already exists unless you pass `--force`. A file you edited stays as you left it. To take a scaffold change, read the changelog for the `cli` revision, apply that diff yourself, and run the checks that revision's workflow runs (`go test`, `govulncheck`, and the lockfile audit when the project has one). `--force` replaces the file. It is the explicit overwrite, not the upgrade path.

## `vukem upgrade`

Compare the project with this CLI. It reports; it never overwrites a project file.

```text
vukem upgrade [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-check` | bool | `false` | Write nothing and run no `go` command. Exit 1 when the project is behind the CLI, 0 otherwise. Safe in CI. |
| `-json` | bool | `false` | Print the report as JSON: `framework` (`required`, `cli`, `state`), `modules` and `scaffold.differ`. |

The report has three parts:

- **framework**: the `github.com/AlexGalhardo/vukem` version in `go.mod` against the CLI's, as `up_to_date`, `behind`, `ahead`, `replaced` (a `replace` to a local checkout) or `devel` (the CLI is a development build). The check needs no network.
- **modules**: the `drivers/*` and `contrib/*` modules the project requires, with their versions. They are listed, not compared: each has its own version line.
- **scaffold**: the files that exist both in the project and in the starter this CLI would generate, and differ (line endings ignored). `go.mod`, `go.sum`, `README.md`, `.env.example` and `storage/` are skipped. A file you edited, or that an `install:*` overlay replaced (`routes/web.go` on an Inertia project), shows up here; that is information, not an error, so a file difference never fails `--check`.

Without `-check`, `vukem upgrade` also writes the current starter to `.vukem/upgrade/starter/` (already in the starter's `.gitignore`) so you can compare a file with `git diff --no-index .vukem/upgrade/starter/<file> <file>`, and when the project is behind it runs `go get github.com/AlexGalhardo/vukem@<cli version>` and `go mod tidy`. Those two commands and `.vukem/upgrade/` are the only things it writes.

```bash
vukem upgrade -check
```

```text
framework: v0.38.0 in go.mod, CLI is v0.40.0 (behind)
scaffold: 2 file(s) differ from the v0.40.0 starter
  Dockerfile
  vite.config.ts
docs: https://vukem.dev/docs/cli/reference-new#upgrading-a-starter
```

## `vukem list` and `vukem help`

Show what exists.

**Usage**

```text
vukem list
vukem help [<command>]
vukem <command> -h
```

| Form | Result |
| --- | --- |
| `vukem`, `vukem list`, `vukem help`, `vukem -h`, `vukem --help` | The global commands grouped by namespace (`install`, `boost`, `key`, `make`, `codegen`), then a note that other commands run in the app. |
| `vukem help <command>` | Usage line, description and flags of a global command. |
| `vukem <command> -h` | The same, and exit 0. |
| `vukem help nope` | `usage error: unknown command "nope"`, exit 2. |

`list` does not list app commands such as `migrate`. To list those, run any unknown name inside a project:

```bash
vukem help-me
```

The app prints `unknown command "help-me"`, then every app command with its description, and the exit code is 2.

**Example**

```bash
vukem help make:model
```

```text
Usage: vukem make:model [flags] <Name>

Create a model (with -m, -f, -c)

Flags:
  -c	also create a resource controller
  -f	also create a factory
  -force
    	overwrite existing files
  -m	also create a create_<table>_table migration
```

**Known limits**: `help <command> <extra>` ignores the extra word. `vukem new --pm foo` asks the stack question before it reports the bad package manager.
