This page covers the commands you use while an app runs and while you ship it: keys, maintenance mode, inspection, queues, the scheduler, OpenAPI and client generation. The first group is **global**; the rest are **app** commands, which `vukem` builds from `cmd/app` and runs for you. Back to the [command cheat sheet](/docs/cli/reference).

For app commands, flags go **before** positional arguments, and the app boots first (a boot error such as `vukem: APP_DEBUG must be false when APP_ENV=production` exits with 1). `openapi:export`, `codegen:types`, `codegen:routes`, `codegen:client` and `view:check` run in **warmup** mode instead: they register the routes but open no database, boot no provider and do not need `APP_KEY`.

## `vukem hash:make`

Print the argon2id hash of a password, in the format the session guard verifies.

```text
vukem hash:make [-env NAME] [-stdin]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-env` | string | `PASSWORD` | The environment variable that holds the password. |
| `-stdin` | bool | `false` | Read the password from the first line of stdin instead. |

**Interactions**

- The password is never read from arguments: a positional argument is a usage error, so it stays out of the shell history and the process list.
- Only the hash is printed. An empty password is an error.
- It boots the app like any app command, so `APP_KEY` must be set.

```bash
PASSWORD='the new password' ./app hash:make
```

## `vukem key:generate`

Write a new random `APP_KEY` to `.env`. **Global.**

```text
vukem key:generate [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-show` | bool | `false` | Print the key and write nothing. |
| `-force` | bool | `false` | Replace an existing non-empty `APP_KEY`. |
| `-if-missing` | bool | `false` | Write `.env` when `APP_KEY` is empty. Never print the key. Refuses `-show` and `-force`. |

If `.env` is missing, it starts from `.env.example`. `.env` is read like the app's configuration loader reads it: an `export APP_KEY=...` line, spaces around `=` and quoted values are understood, so such a key counts as set and an empty quoted value counts as empty. The key signs sessions and encrypts data ([Encryption](/docs/security/encryption)).

```bash
vukem key:generate
```

```text
error: APP_KEY is already set in .env (use --force to replace it; existing sessions and encrypted data become unreadable)
```

Exit 1, nothing changed. Replacing a key logs every user out and makes encrypted values unreadable. Use [`key:rotate`](#vukem-keyrotate) instead on a live app.

```bash
vukem key:generate -show
vukem key:generate -force
```

```text
base64:Ile84lRsqMKmNobqAgxgW3HTUvtSMIFjSguzeIVXSKI=
APP_KEY written to .env
```

**Without the CLI** (a Docker image or CI runner with only your binary): `./app key:generate` prints a key to standard output and never writes `.env`, unless you pass `--if-missing`: it then writes `.env` only when `APP_KEY` is empty, prints nothing on standard output and reports on standard error. Only the key goes to standard output, so `export APP_KEY="$(./app key:generate)"` is safe. This built-in wins over an app command with the same name, and `vukem key:generate` itself is never delegated.

## `vukem key:rotate`

Write a new `APP_KEY` and move the old one to the front of `APP_PREVIOUS_KEYS`, so old sessions and encrypted values still open. **Global.**

```text
vukem key:rotate
```

No flags. An argument is a usage error (`usage error: key:rotate takes no arguments`, exit 2).

- It never prints a key.
- It refuses a missing `.env`, an empty `APP_KEY` and any malformed current or previous key, because a bad previous key would stop the app from booting.
- It keeps `export`, indentation, inline comments and CRLF line endings, writes through a synced temporary file and renames it, and keeps a symlinked `.env` a symlink.
- It warns on standard error when more than 3 previous keys remain: each one can still forge sessions and signed links.

```bash
vukem key:rotate
```

```text
APP_KEY rotated in .env; the old key is now first in APP_PREVIOUS_KEYS.
Restart the app. Remove the old key from APP_PREVIOUS_KEYS once the sessions and links
it signed have expired and encrypted columns are re-saved (https://vukem.dev/docs/security/encryption).
```

Restart the app afterwards: a running process keeps the old key in memory.

## `vukem down` and `vukem up`

Put the app in maintenance mode, and bring it back. **Global.**

```text
vukem down [flags]
vukem up
```

`down` writes `storage/framework/down`. The `middleware.Maintenance` middleware, which both default stacks include, then answers every request with `503 Service Unavailable` and a `Retry-After` header (an `errors/503` view, or problem+json for APIs). `/up` keeps answering so health checks pass. `up` deletes the file. A running app notices both without a restart.

| Flag (`down`) | Type | Default | What it does |
| --- | --- | --- | --- |
| `-secret` | string | none | Visitors of `/<secret>` get a signed bypass cookie and see the live site. |
| `-with-secret` | bool | `false` | Generate a random secret and print the bypass path. Use it instead of `-secret`. |
| `-retry` | duration | none | `Retry-After` sent with the 503, such as `60s`. |

`up` has no flags. The secret is stored hashed. An unreadable state file keeps the app **down**: it fails closed.

```bash
vukem down
vukem up
vukem up
```

```text
The application is in maintenance mode (vukem up brings it back).
The application is live.
The application is live.
```

Running `up` on a live app is harmless.

**Advanced: let yourself in while it is down**

```bash
vukem down -secret abc -retry 60s
```

```text
The application is in maintenance mode (vukem up brings it back).
Bypass: open /abc once to get a cookie that lets you in.
```

With `-with-secret` the same line shows a random value, for example `/R7WGCWCMG4OVUASTHHEQVI6HWZ`.

## `vukem route:list`

List the registered routes. **App.**

```text
vukem route:list [-json] [-method VERB] [-path TEXT] [-name TEXT]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-json` | bool | `false` | Print a JSON array of routes with their middleware. |
| `-method` | string | empty | Only routes with this HTTP method, compared without case. `ANY` matches routes registered with `Any`. |
| `-path` | string | empty | Only routes whose host and path contain this text. |
| `-name` | string | empty | Only routes whose name contains this text. |

The filters combine and also apply to `-json`. When no route matches, the command prints `No routes match.` and exits with 0. A `SUMMARY` column appears when a listed route carries a one-line summary (typed API routes do, from `api.Op.Summary`; any route doc can implement `router.Summarizer`).

```bash
vukem route:list
```

```text
METHOD  PATH                    NAME                   MIDDLEWARE
GET     /up                     vukem.health           middleware.BodyLimit
POST    /api/v1/tokens          api.v1.tokens.store    middleware.BodyLimit, middleware.JSONOnly, ratelimit.Middleware, ratelimit.Middleware
GET     /api/v1/me              api.v1.me              middleware.BodyLimit, middleware.JSONOnly, ratelimit.Middleware, auth.Required, ratelimit.Middleware, auth.Ability
GET     /api/v1/posts           api.v1.posts.index     middleware.BodyLimit, middleware.JSONOnly
```

The output is cut to four rows here. Use it to check which middleware guards a route, and `-json` with `jq` in scripts.

## `vukem queue:work`

Process queued jobs until stopped. **App.**

```text
vukem queue:work [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-queue` | string | `QUEUE_NAMES` (`default`) | Queues in priority order, comma-separated: `high,default`. |
| `-concurrency` | int | `QUEUE_CONCURRENCY` (`4`) | Parallel workers. |
| `-sleep` | duration | `1s` | Wait when the queue is empty. |
| `-once` | bool | `false` | Process one job and exit. Implies concurrency 1 and `-stop-when-empty`. |
| `-stop-when-empty` | bool | `false` | Exit when no job is available. |

Environment: `QUEUE_CONNECTION` (`sync`, `memory` or `database`; default `sync`), `QUEUE_NAMES`, `QUEUE_CONCURRENCY`, `QUEUE_LIMITS` (per-queue caps, `ingest=2`), `QUEUE_TABLE` (`jobs`), `QUEUE_FAILED_TABLE` (`failed_jobs`), `QUEUE_IN_SERVE` (`true`: `serve` also runs a worker), `SHUTDOWN_TIMEOUT` (`15s`), `MAIL_MAILER` (required in production, since queued mail is sent by the worker).

Ctrl+C stops it and waits up to `SHUTDOWN_TIMEOUT` for running jobs.

**Errors**

| Message | Fix |
| --- | --- |
| `vukem: QUEUE_CONNECTION=sync runs jobs during Dispatch, so queue:work has nothing to process (use QUEUE_CONNECTION=database for a separate worker)` | Set `QUEUE_CONNECTION=database` (and run `vukem migrate` first). |
| `vukem: unknown QUEUE_CONNECTION "x" (sync, memory, database)` | Use a listed value. |

```bash
QUEUE_CONNECTION=database vukem queue:work -stop-when-empty -sleep 100ms
```

```text
time=2026-10-24T19:15:38.912-03:00 level=INFO msg="queue worker started" queues=[default] concurrency=4
```

It exits 0 once the queue is empty. Use this form in a deploy script or a test.

**Advanced: two queues, high priority first**

```bash
vukem queue:work -queue high,default -concurrency 8
```

## `vukem queue:failed`

List failed jobs, newest first. **App.** Flags: `-json` (bool, default `false`) and `-limit` (int, default `100`; `0` lists all). `-limit` bounds the query on the database driver; drivers that cannot page ignore it.

```bash
QUEUE_CONNECTION=database vukem queue:failed
```

```text
ID  QUEUE  KIND  ATTEMPTS  FAILED AT  ERROR
```

The table is empty when nothing failed. With `QUEUE_CONNECTION=sync` or `memory` there is no failed store:

```text
vukem: QUEUE_CONNECTION=sync returns job errors to Dispatch and keeps no failed jobs: vukem: the queue driver does not keep failed jobs (use QUEUE_CONNECTION=database)
```

Exit 1.

## `vukem queue:retry` and `vukem queue:forget`

Re-queue, or delete, failed jobs. **App.**

```text
vukem queue:retry <id>... | all
vukem queue:forget <id>... | all
```

No flags. Arguments: one or more job IDs from `queue:failed`, or the word `all`. Without one: `queue:retry needs job IDs or "all"` (exit 1).

```bash
QUEUE_CONNECTION=database vukem queue:retry all
QUEUE_CONNECTION=database vukem queue:forget all
```

```text
0 failed job(s) re-queued
0 failed job(s) deleted
```

`forget` is permanent.

## `vukem schedule:run`, `schedule:work`, `schedule:list`

The scheduler runs tasks declared in `routes/schedule.go`. **App.** None of the three has flags.

| Command | What it does |
| --- | --- |
| `schedule:run` | Runs the tasks due at the current minute, then exits. Call it every minute from cron. |
| `schedule:work` | Runs the scheduler in the foreground until stopped. Pair it with `SCHEDULE_IN_SERVE=false` on `serve`. Needs `MAIL_MAILER` in production. |
| `schedule:list` | Prints each task, its cron expression and the next run. |

Environment: `SCHEDULE_TIMEZONE` (default `UTC`), `SCHEDULE_IN_SERVE` (default `true`: `serve` runs the scheduler too). An invalid timezone is a boot error: `vukem: SCHEDULE_TIMEZONE: ...`.

```bash
vukem schedule:list
```

```text
no scheduled tasks (declare them in routes/schedule.go)
```

Exit 1 when there are no tasks. With tasks it prints `TASK  EXPRESSION  NEXT RUN`. `schedule:run` with nothing due prints nothing and exits 0. A cron line: `* * * * * cd /srv/blog && ./bin/blog schedule:run`.

## `vukem cache:prune` and `vukem session:prune`

Delete expired database cache entries, or expired database sessions. **App.** No flags. The app already schedules both hourly when the store is the database.

```bash
vukem session:prune
vukem cache:prune
```

```text
Sessions are not stored in the database: nothing to prune.
The cache does not keep expired entries: nothing to prune.
```

Those lines are what the default `cookie` sessions and `memory` cache print. With `SESSION_DRIVER=database` or `CACHE_STORE=database` you get `Pruned N expired sessions.` and `Pruned N expired cache entries.`.

## `vukem api:fuzz`

Run Schemathesis in Docker against the running app, from the OpenAPI document. **App**, full boot (the credential hook may use the database).

```text
vukem api:fuzz [-prefix /api/v1] [-url http://127.0.0.1:3000] [-dry-run] [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-prefix` | string | `OPENAPI_PREFIX` | Scan only routes under this path prefix. |
| `-url` | string | `http://127.0.0.1:$PORT` | Base URL of the running app. |
| `-image` | string | `schemathesis/schemathesis:4.29.0@sha256:5586e94460479271714d47613175b3620c44b38b3e1babc936636108f1672a9e` | Schemathesis image, pinned by digest. |
| `-report-dir` | string | `reports/schemathesis` | Directory for the JUnit and cassette reports. |
| `-docker` | string | `docker` | Docker executable. |
| `-max-examples` | int | `50` | Generated cases per operation. |
| `-workers` | int | `1` | Parallel Schemathesis workers. |
| `-rate-limit-bypass` | bool | `true` | Send a distinct `X-Forwarded-For` per call. |
| `-dry-run` | bool | `false` | Print the docker command and config; run nothing. |

The credential hook and the generated config are on [Fuzz testing](/docs/rest-apis/fuzz-testing).

## `vukem codegen:types`

Generate TypeScript types for every schema and operation (`<Op>Body`, `<Op>Query`, `<Op>Response`). **App**, warmup mode.

```text
vukem codegen:types [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-zod` | bool | `false` | Also emit Zod 4 schemas (`<Name>Schema`, `<Op>BodySchema`). |
| `-o` | string | stdout | Write to this file. Parent folders are created. `-` or no `-o` prints to stdout. |
| `-prefix` | string | `OPENAPI_PREFIX` | Keep only routes under this path prefix. |

```bash
vukem codegen:types -prefix //api -o resources/js/types.ts
```

The command prints nothing when it writes a file. Without `-o` the code goes to stdout:

```bash
vukem codegen:types -zod -prefix /api/v1
```

```text
export type PostsStoreBody = unknown;

export type PostsUpdateBody = unknown;

export type TokensStoreBody = unknown;
```

The output is the last lines of the real result. It shares the errors of `openapi:export`.

The types follow the JSON each route declares, not every Go struct in the module. A field is optional (`?`) unless validation marks it required. A pointer is also `| null`, so `*string` with `omitempty` is `name?: string | null`. A slice is an array (`tags?: string[]`). An `enum` tag or `validate:"oneof=draft live"` becomes `"draft" | "live"`. A `map[string][]string` field is `errors?: Record<string, string[]>`, which is also the shape on the shared problem response. There is no `types:generate` command: this one is `codegen:types`. It does not invent domain rules. A hand-written `types.ts` remains valid; generate when you want CI to diff the route contracts.

## `vukem view:check`

Check the typed `html/template` views against the Go types they receive, the registered routes and the htmx `#id` targets. **App**, warmup mode, opens no connections. The views come from `vukem.WithViewPages`; without any, the command fails with `view:check: no typed views: list them with vukem.WithViewPages`.

```text
vukem view:check [-strict] [-json]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-strict` | bool | `false` | Also list unchecked expressions (`V008`) and views without a declaration (`V007`), as warnings that do not change the exit code, and make a missing htmx target (`V005`) an error. |
| `-json` | bool | `false` | Print the problems as a JSON array. |

```text
posts/index.html:15:49: V002: field or method "Titel" not found in models.Post
posts/index.html:9:18: V003: route "posts.indx" is not registered
posts/index.html:9:92: V005: hx-target "#post-lst": no element with that id in this view
view:check: 3 problem(s) in 1 view(s)
```

Problems go to stdout, one per line as `file:line:col: code: message` (warnings carry `warning:` before the code and never change the exit code); the summary goes to stderr and the exit code is 1 when there are errors. A `#id` that an `hx-*` attribute points to but the view does not define (`V005`) is a warning unless you pass `-strict`. `vukem serve` runs the check after every rebuild and only prints the problems as a warning. See [htmx](/docs/frontend/htmx#typed-views-and-viewcheck) for the codes and for what is not checked.

## `vukem codegen:client`

Generate a typed API client from the OpenAPI document. **App**, warmup mode.

```text
vukem codegen:client [flags]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-lang` | string | `ts` | `ts` (a `createClient` function) or `go` (a standard-library `Client`). |
| `-o` | string | `resources/js/api.ts` or `internal/apiclient/client.go` | Output file. `-` prints to stdout. |
| `-package` | string | `apiclient` | Go package name. `-lang go` only. |
| `-prefix` | string | `OPENAPI_PREFIX` | Keep only routes under this path prefix, so page routes stay out of the client. |

| Message | Fix |
| --- | --- |
| `codegen:client: unknown -lang "rust" (want ts or go)` | Use `ts` or `go`. |
| `openapi: duplicate operationId ...` | Same as `openapi:export`: pass `-prefix`. |

```bash
vukem codegen:client -prefix /api -o -
```

```text
export function createClient(options: ClientOptions = {}): Client {
  const request = requester(options);

  return {
    me: () => request<unknown>("GET", "/api/v1/me"),
    postsDestroy: (args) => request<unknown>("DELETE", "/api/v1/posts/{post}", args),
    postsIndex: () => request<unknown>("GET", "/api/v1/posts"),
    ...
  };
}
```

**Advanced: a Go client**

```bash
vukem codegen:client -lang go -package shopclient -prefix /api -o internal/shopclient/client.go
```

The Go client has one method per operation, for example `func (c *Client) TokensDestroy(ctx context.Context) error`. See [Client generation](/docs/rest-apis/client-generation).

## `vukem ssr:start` and `vukem ssr:check`

Run and probe the Inertia server-side rendering server. **App.**

```text
vukem ssr:start [flags]
vukem ssr:check [-url URL]
```

| Command | Flag | Type | Default | What it does |
| --- | --- | --- | --- | --- |
| `ssr:start` | `-bundle` | string | `bootstrap/ssr/ssr.js` | SSR bundle built by `vite build --ssr`. |
| `ssr:start` | `-runtime` | string | `node` | JavaScript runtime that runs the bundle. |
| `ssr:start` | `-restart-delay` | duration | `1s` | Wait before restarting a crashed server. |
| `ssr:check` | `-url` | string | `http://127.0.0.1:13714` | SSR server URL. |

`ssr:start` restarts the server when it crashes and returns when it is stopped (Ctrl+C) or exits cleanly after serving (`POST /shutdown`). A bundle that exits cleanly within 2 seconds never started a server, so `ssr:start` fails instead of exiting 0 in silence:

```text
ssr:start: the SSR bundle did not start a server (call createInertiaApp at the top level of resources/js/ssr.ts(x), do not export it, and rebuild): bootstrap/ssr/ssr.js exited at once
```

`ssr:check` requests `/health` and exits 0 on success, 1 otherwise:

```bash
vukem ssr:check
```

```text
ssr:check: Get "http://127.0.0.1:13714/health": dial tcp 127.0.0.1:13714: connectex: ...
```

The message comes from the operating system and varies. Start `ssr:start` first, then check. See [Inertia](/docs/frontend/inertia).

### One container: `serve -with-ssr`

When the Node SSR server runs in the same container as the app, `serve -with-ssr` starts it as part of the app process instead of a second command. It runs the same supervisor as `ssr:start`, as the `ssr` runner, so it stops with the app on shutdown.

```bash
./bin/app serve -with-ssr
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-with-ssr` | bool | `false` | Run and supervise the SSR server next to the app. |
| `-ssr-bundle` | string | `bootstrap/ssr/ssr.js` | SSR bundle built by `vukem build -ssr` (or `vite build --ssr`). |
| `-ssr-runtime` | string | `node` | JavaScript runtime that runs the bundle. |
| `-ssr-restart-delay` | duration | `1s` | Wait before restarting the server. |

Two differences from `ssr:start`: the server is restarted after **any** exit, a clean one included, because the app keeps rendering pages; and a missing bundle stops `serve` at boot with `serve -with-ssr: SSR bundle bootstrap/ssr/ssr.js not found (run npm run build)`. Pair it with `SSRConfig.Strict` to report the server in readiness (see [Strict SSR](/docs/frontend/inertia#strict-ssr)).

## `vukem ssg:generate`

Write static HTML by calling the app's HTTP handler in process. **App.** This does not run the Inertia SSR server, and it does not crawl registered routes. Only each `-path` is rendered. See [Static site generation](/docs/digging-deeper/static-site-generation).

```text
vukem ssg:generate [-out dir] [-no-clean] -path /page [-path /other]
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-out` | string | `dist` | Directory to write into. Created when it is missing; replaced when empty or marked `.vukem-ssg`, otherwise refused. |
| `-no-clean` | bool | `false` | Write in place and keep files from earlier runs. |
| `-path` | string |  | Absolute URL path to prerender. Repeat the flag. At least one is required. |

`/` becomes `index.html`. `/about` becomes `about/index.html`. A missing `-path` or an extra argument is a usage error and exits 2. A path such as `../` or `https://example.com/x`, or a response that is not 200, exits 1 and writes nothing for that page.

```bash
vukem ssg:generate -out dist -path / -path /about
```

```text
wrote index.html (4 bytes)
wrote about/index.html (5 bytes)
```

## `vukem bench`

Load test one URL and report throughput and latency percentiles. **Global**: it needs no project and starts nothing; point it at an app that is already running.

```text
vukem bench [flags] <url>
```

| Flag | Type | Default | What it does |
| --- | --- | --- | --- |
| `-c` | int | `10` | Closed model: concurrent workers, each sending in a loop. |
| `-rate` | string |  | Open model: arrival rate such as `200/s` or `3000/1m`. Disables `-c`; using both is a usage error. |
| `-d` | duration | `10s` | How long to run. At most `1h`. |
| `-n` | uint | `0` | Stop after this many requests. `0` means no limit. The run ends at `-d` or `-n`, whichever comes first. |
| `-m` | string | `GET` | HTTP method. |
| `-H` | string |  | Request header `"Name: value"`. Repeat the flag. |
| `-body` | string |  | Request body. |
| `-body-file` | string |  | Read the request body from a file in the project directory. Exclusive with `-body`. |
| `-timeout` | duration | `30s` | Per-request timeout. At most `5m`. |
| `-connections` | int | `0` | Idle connections kept per host. `0` keeps at least 100. |
| `-max-workers` | int | `1000` | Open model: cap on requests in flight. Arrivals past it are dropped and counted, not queued. At most `10000`. |
| `-no-keepalive` | bool | `false` | Open a new connection per request. At a high rate this can run out of ephemeral ports, which shows as `other` errors. |
| `-http2` | bool | `false` | Negotiate HTTP/2 over TLS. |
| `-allow-remote` | string |  | Allow a host that is not loopback. Repeat the flag. See below. |
| `-json` | bool | `false` | Print the summary as JSON (`schema_version` 1, durations in nanoseconds) instead of text. |
| `-o` | string |  | Also write the JSON summary to this file. |
| `-quiet` | bool | `false` | No progress line. The line is printed once a second, to stderr, only on a terminal. |

**Open and closed model.** With `-c` the workers send one request after another, so a slow server slows the generator down and hides its own slowness. With `-rate` requests arrive at a constant rate whether or not earlier ones finished, and `http_req_duration` runs from the instant a request was due, so a late generator or a saturated server shows in the latency.

**Targets.** Only `http` and `https` URLs without credentials, and only loopback hosts (`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`). Any other host is refused with exit code 2 unless `-allow-remote <host>` names it exactly (case-insensitive, no port). The flag states that you own the target; it is not a check, so a name can still resolve to any address. The host is checked for every request. Redirects are never followed: a `302` is a successful response. A status of `400` or more, or a transport error, counts as failed.

**Output.** The text report lists `http_reqs`, `http_req_failed`, `http_req_duration`, `http_req_waiting`, `http_req_connecting`, `data_received`, `data_sent`, `dropped_iterations`, the status codes, the error classes (`timeout`, `connection refused`, `eof`, `other`; never the raw message) and a latency histogram. Ctrl+C stops the load and prints the report so far with a `note` line and `"interrupted": true` in JSON; the exit code stays 0. The numbers depend on the machine, and the generator shares its CPU with a target on the same host.

```bash
vukem serve &
vukem bench -c 10 -d 10s http://localhost:3000/
vukem bench -rate 500/s -d 30s -json -o result.json http://127.0.0.1:3000/posts
```

If `localhost` fails with `connection refused` while the app listens, the app may be on IPv4 only: use `127.0.0.1`.

## `vukem boost:mcp`

A Model Context Protocol server over standard input and output, for coding agents. **App.** No flags. `vukem boost:install` registers it for you; you do not run it by hand. Tools: `application_info`, `list_routes`, `list_commands`, `database_schema`, `database_query` (one read-only statement, at most 100 rows), `get_absolute_url`, `search_docs`.

## Your own commands

`vukem make:command SendReports` adds an app command. It runs like any other:

```bash
vukem send-reports a b
```

```text
send-reports ran with [a b]
```

Commands run in the `console` environment, after the app boots. Unknown names print the app's command list and exit 2.
