---
title: Pagination and query conventions
description: Answer list endpoints in pages — offset and cursor envelopes, plus allowlisted filter, sort, fields and include parameters that reject anything unknown with a 400.
---

A list endpoint should never send a client ten thousand rows at once. **Pagination** cuts a list into pages, and **query conventions** let the client ask for exactly the slice it wants — "only the tasks that are done, newest first, 20 per page" — with the same parameter names on every endpoint.

Vukem gives you both in the `api` package: `api.Query` reads `?filter`, `?sort`, `?fields`, `?include`, `?page`, `?per_page` and `?cursor` from the URL and applies them to an ORM query, and `api.Page`, `api.Cursor` and `api.Collection` write the JSON envelope.

You will learn:

- The difference between offset pages and cursor pages, and when to use each.
- How to allowlist filters, sorts, fields and includes, and why anything else is a `400`.
- The exact JSON envelopes Vukem writes, links included.
- The limits that stop a request from overloading the database.
- How pagination works inside a typed handler.

## The idea

Picture a long book. There are two ways to tell a friend where to continue reading:

- **"Go to page 7."** That is **offset pagination**: skip 6 × 20 rows, then read 20. It is simple, shows a total ("page 7 of 23") and lets the client jump anywhere. But the database still walks past every skipped row, and if someone inserts a row at the top while you read, every page shifts by one.
- **"Continue after the bookmark."** That is **cursor (keyset) pagination**: the server hands back a bookmark — the last id it sent — and the next request asks for rows _after_ it. No row is skipped twice, there is no `COUNT`, and deep pages are as fast as the first. You cannot jump to page 7, though.

| | Offset (`?page=`) | Cursor (`?cursor=`) |
| --- | --- | --- |
| Shows a total | yes (`meta.total`, `meta.last_page`) | no |
| Jump to any page | yes | no, only "next" |
| Cost of deep pages | grows with the offset | constant |
| Stable while rows are inserted | no | yes |
| Order | any allowlisted sort | the primary key only |
| Use it for | admin tables, search results | feeds, sync jobs, infinite scroll |

The running example is the task list API from the [REST APIs overview](/docs/rest-apis/overview): `GET /api/v1/tasks` lists the caller's tasks.

## Quick start

<Steps>
<Step title="Write the list handler">

```go title="app/controllers/apiv1/tasks.go"
func (t *Tasks) Index(c *web.Ctx) error {
	req, err := api.Query(c, orm.QueryOf[models.Task](t.db),
		api.Filters("status"),
		api.Sorts("title", "created_at", "-id"),
		api.PerPage(20, 100),
	)
	if err != nil {
		// An unknown column is a 400 problem+json.
		return err
	}

	page, err := req.Paginate(c.Context())
	if err != nil {
		return err
	}

	return api.Page(c, page, resources.Task)
}
```

</Step>

r.Group("/api/v1", func(g *router.Group) {

</Step>

`curl` needs the URL in single quotes because `[` and `]` mean something to the shell. No `?sort` was sent, so the default (`-id`, the last entry of `api.Sorts`) applies. The links keep every parameter of the request, re-encoded (`[` becomes `%5B`) and sorted by name.

## Query conventions

`api.Query[T](c, q, opts...)` takes the request, an `orm.Query[T]` and a list of options. Each option **allowlists** one convention: a column or relation that is not in the list cannot be used, whatever the URL says. This is the most important rule of the page — request input never chooses a column freely, so a client can neither sort by `password_hash` nor probe columns you did not mean to expose.

```go title="app/controllers/apiv1/tasks.go"
req, err := api.Query(c, orm.QueryOf[models.Task](t.db),
	// ?filter[status]=todo,done&filter[done]=true
	api.Filters("status", "done"),
	// ?sort=-created_at,title (default: the last entry)
	api.Sorts("title", "created_at", "-id"),
	// ?fields=id,title
	api.Fields("id", "title", "status"),
	// ?include=user
	api.Includes("user"),
	// ?page=2&per_page=50 (default 20, capped at 100)
	api.PerPage(20, 100),
	// ?page above 500 is a 400
	api.MaxPage(500),
	// at most 20 values in one filter
	api.MaxFilterValues(20),
)
```

`api.Query` returns an `api.Request[T]`:

| Field | Type | What it holds |
| --- | --- | --- |
| `Query` | `orm.Query[T]` | your query with the filters, sorts, fields and relation includes applied |
| `Page` | `int` | the requested page, at least 1 |
| `PerPage` | `int` | the page size, between 1 and the maximum |
| `Cursor` | `string` | the raw `?cursor=` value (empty for the first page) |
| `Includes` | `[]string` | the allowlisted include names the client sent, as sent |

`req.Paginate(ctx)` runs `req.Query.Paginate(ctx, req.Page, req.PerPage)` for you, and `req.CursorPaginate(ctx, dir)` runs a cursor page (see [Cursor pages](#cursor-pages)).

### Filters

`api.Filters(cols...)` allows `?filter[col]=value`.

- One value adds `WHERE col = ?`. Comma-separated values add `WHERE col IN (?, ?, …)`.
- Exactly `true` or `false` become Go booleans (so SQLite, which stores booleans as `0`/`1`, matches). Every other value is passed as a string.
- Values are always **bound parameters**, never pasted into the SQL, so a value cannot inject SQL ([OWASP: SQL injection](https://owasp.org/www-community/attacks/SQL_Injection)).
- If the same filter appears twice in the URL, the last one wins.

### Sorts

`api.Sorts(cols...)` allows `?sort=col,-col`. A leading `-` means descending.

- The **last entry** is the default sort, used when the URL has no `?sort`. In `api.Sorts("title", "created_at", "-id")` the default is newest id first.
- Listing a column in either direction allows both: `"-id"` also allows `?sort=id`.
- `?sort=` replaces the default completely; several columns sort in order (`?sort=status,-id`).
- Without `api.Sorts` no sort is applied and any `?sort` is a `400`.

### Fields

`api.Fields(cols...)` allows `?fields=id,title`: the query selects only those columns (`Select`). This saves work in the database, but your transformer still writes every property of its struct. Columns that were not selected keep Go's [zero value](https://go.dev/ref/spec#The_zero_value):

```json
{ "id": 45, "title": "Task 45", "status": "" }
```

Use `omitempty` (or `omitzero`) [JSON tags](https://pkg.go.dev/encoding/json#Marshal) on the transformer's fields when clients should not see the empty ones.

### Includes

`api.Includes(rels...)` allows `?include=user,comments`. Each name the client sends that matches a relation of the model is **eager-loaded** on `req.Query` with `orm.Query.With`. A name matches a relation by its Go field name (`User`), its snake_case form (`user`, `author_profile` for `AuthorProfile`) or its `json` tag, so the public name of a relation is usually the one you already use in the JSON:

```go title="app/controllers/apiv1/tasks.go"
// models.Task has `User orm.BelongsTo[models.User]`:
// ?include=user loads it, without ?include it stays unloaded.
req, err := api.Query(c, orm.QueryOf[models.Task](t.db),
	api.Includes("user"),
)
if err != nil {
	return err
}

page, err := req.Paginate(c.Context())
```

An allowlisted name that matches no relation (a computed `stats` block, say) is not loaded; it only appears in `req.Includes`, so your handler can act on it. `req.Includes` always lists the names as the client sent them.

<Callout type="warning" title="Allowlist only bounded, safe relations">
An include loads **every** related row of each item on the page: `?include=comments` on 100 tasks fetches all their comments, however many, because a has-many relation is not paginated. And when your response embeds the related model, it is serialized with that model's own `json` tags, so a `User` without `json:"-"` on `PasswordHash` would expose it. Allowlist only relations with a small, bounded number of rows, and map them through a [resource](/docs/rest-apis/overview) that picks the fields to send.
</Callout>

In the transformer, read a relation only when it was loaded: `m.User.Loaded()` reports it, and `m.User.Get()` returns `orm.ErrNotLoaded` otherwise. See [Relations](/docs/database/relations).

### Page size and limits

| Parameter | Rule |
| --- | --- |
| `?page` | missing, `0`, negative or not a number → `1`; above `MaxPage` → `400` |
| `?per_page` | missing or not a number → the default; below 1 → `1`; above the maximum → the maximum (capped, no error) |
| `?filter[col]` | more comma-separated values than `MaxFilterValues` → `400` |

`api.MaxPage(n)` defaults to `api.DefaultMaxPage` (1000) and `api.MaxFilterValues(n)` to `api.DefaultMaxFilterValues` (100). Both ignore `n <= 0` and keep the default. `api.PerPage(def, max)` defaults to 20 and 100; its maximum also replaces the ORM's own cap (`orm.DefaultMaxPerPage`, 100) on the query, so `PerPage(20, 500)` serves up to 500 rows. These bounds exist because `OFFSET 10000000` still makes the database walk ten million rows, and a filter with ten thousand values binds ten thousand parameters: a cheap request should not cost you an expensive query. For deep lists, use a cursor.

## Offset pages

`api.Page(c, page, fn)` answers `200` with an `api.Envelope` built from an `orm.Page[T]`; `fn` is the transformer that turns each model into its wire format.

```json
{
  "data": [{ "id": 45, "title": "Task 45", "status": "todo" }],
  "meta": { "page": 1, "per_page": 10, "total": 45, "last_page": 5 },
  "links": {
    "self": "/api/v1/tasks?page=1&per_page=10",
    "next": "/api/v1/tasks?page=2&per_page=10",
    "prev": null
  }
}
```

How the links are built:

- `self` is the current path and query with `page` set to the current page.
- `next` is `null` on the last page (when `page >= last_page`).
- `prev` is `null` on page 1. Past the end it points to the last real page: `?page=99` of a 5-page list answers an empty `data`, `next: null` and `prev: "…?page=5…"`, so a client that went too far can find its way back.
- Links are relative (path and query, no host): the client already knows the host it called.

## Cursor pages

For a cursor page, call `req.CursorPaginate(ctx, dir)` and answer with `api.Cursor`:

```go title="app/controllers/apiv1/feed.go"
func (f *Feed) Index(c *web.Ctx) error {
	req, err := api.Query(c, orm.QueryOf[models.Task](f.db),
		api.Filters("status"),
		api.PerPage(20, 100),
	)
	if err != nil {
		return err
	}

	page, err := req.CursorPaginate(c.Context(), orm.Asc)
	if err != nil {
		// A tampered cursor is a 400.
		return err
	}

	return api.Cursor(c, page, resources.Task)
}
```

```json
{
  "data": [
    { "id": 1, "title": "Task 01", "status": "doing" },
    { "id": 2, "title": "Task 02", "status": "done" }
  ],
  "meta": { "per_page": 2, "next_cursor": "Mg" },
  "links": {
    "self": "/api/v1/feed?per_page=2",
    "next": "/api/v1/feed?cursor=Mg&per_page=2",
    "prev": null
  }
}
```

- Pass `""` for the first page and `meta.next_cursor` for the next one. On the last page `next_cursor` is absent and `links.next` is `null`.
- The cursor is an opaque string (an encoded primary key). A client must send it back unchanged; anything that does not decode answers `400` with `"detail": "Invalid pagination cursor."`.
- `orm.Asc` walks from the oldest id up, `orm.Desc` from the newest down.
- `links.self` is the request URI as received; `links.prev` is always `null`, because a keyset cursor only moves forward.

The keyset order is the primary key, so a cursor page cannot follow another sort. `req.CursorPaginate` drops the default sort of `api.Sorts` (the endpoint can still offer `?sort` for offset pages), and answers `400` with `Query parameter sort cannot be combined with cursor pagination.` when the client sends `?sort` itself. Calling `req.Query.CursorPaginate(ctx, req.Cursor, req.PerPage, dir)` directly still fails with `orm: CursorPaginate orders by the primary key; remove OrderBy` (a `500`) as soon as `api.Sorts` added an `OrderBy`.

## Plain collections

When a list is small and bounded (the five statuses of a task, a user's two API tokens), skip pagination: `api.Collection(c, items, fn)` answers `{"data": [...]}` without `meta` or `links`.

```json
{ "data": [{ "id": 1, "title": "Task 01", "status": "doing" }] }
```

Single resources have no envelope at all: `c.JSON(200, resources.Task(t))` writes the object itself.

## The envelope types

The envelopes are plain [generic](https://go.dev/doc/tutorial/generics) structs in the `api` package, so you may build one yourself:

```go
type Envelope[R any] struct {
	Data  []R    `json:"data"`
	Meta  *Meta  `json:"meta,omitempty"`
	Links *Links `json:"links,omitempty"`
}

type Meta struct {
	Page       int    `json:"page,omitempty"`
	PerPage    int    `json:"per_page"`
	Total      *int64 `json:"total,omitempty"`
	LastPage   int    `json:"last_page,omitempty"`
	NextCursor string `json:"next_cursor,omitempty"`
}

type Links struct {
	Self string  `json:"self"`
	Next *string `json:"next"`
	Prev *string `json:"prev"`
}
```

`Next` and `Prev` are pointers so that "no page" encodes as `null` instead of `""`. `Total` is a pointer so `0` still appears on an empty offset page.

### Inside a typed handler

A [typed handler](/docs/rest-apis/typed-handlers) returns a value instead of writing the response, so it cannot call `api.Page`. Return your own struct that embeds `api.Meta` — the [OpenAPI document](/docs/rest-apis/openapi) then describes the envelope too. This is how the example app lists tasks:

```go title="app/resources/task.go"
// TaskPageJSON is one page of tasks: data plus pagination meta.
type TaskPageJSON struct {
	Data []TaskJSON `json:"data" validate:"required"`
	Meta api.Meta   `json:"meta" validate:"required"`
}

// TaskPage transforms an offset page of models.
func TaskPage(p orm.Page[models.Task]) TaskPageJSON {
	total := p.Total

	return TaskPageJSON{
		Data: api.Map(p.Items, Task),
		Meta: api.Meta{
			Page:     p.Page,
			PerPage:  p.PerPage,
			Total:    &total,
			LastPage: p.LastPage,
		},
	}
}
```

```go title="app/controllers/apiv1/tasks.go"
func (t *Tasks) Index(
	c *web.Ctx, in requests.ListTasks,
) (resources.TaskPageJSON, error) {
	q := orm.QueryOf[models.Task](t.db)
	if in.Status != "" {
		q = q.Where("status", in.Status)
	}

	req, err := api.Query(c, q,
		api.Sorts("title", "created_at", "-id"),
		api.PerPage(20, 100),
	)
	if err != nil {
		return resources.TaskPageJSON{}, err
	}

	page, err := req.Paginate(c.Context())
	if err != nil {
		return resources.TaskPageJSON{}, err
	}

	return resources.TaskPage(page), nil
}
```

`requests.ListTasks` declares `status`, `sort`, `page` and `per_page` with `validate` tags, so they are validated and documented; `api.Query` still reads the URL itself and enforces the allowlist.

## Errors

Every rejection is a `400` problem+json whose `detail` names what is allowed:

| Request | `detail` |
| --- | --- |
| `?sort=status` | `Unknown sort "status". Allowed: title, created_at, -id.` |
| `?filter[owner]=1` | `Unknown filter "owner". Allowed: status.` |
| `?include=user` without `api.Includes` | `Unknown include "user". Allowed: none.` |
| `?fields=secret` | `Unknown field "secret". Allowed: id, title, status.` |
| `?page=1001` | `Query parameter page must be at most 1000.` |
| `?filter[status]=` with 101 values | `Query parameter filter[status] accepts at most 100 values.` |
| `?cursor=garbage` | `Invalid pagination cursor.` |
| `?sort=title` on `req.CursorPaginate` | `Query parameter sort cannot be combined with cursor pagination.` |

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Unknown sort \"status\". Allowed: title, created_at, -id.",
  "instance": "/api/v1/tasks"
}
```

## Security

- **Allowlists, always.** Filters, sorts, fields and includes accept only the names you list (`TestSecurity_A05_QueryConventionsRejectUnknownColumns`), and filter values are bound parameters.
- **Bounded work.** `MaxPage`, `MaxFilterValues` and the `per_page` cap stop one request from making the database skip millions of rows or bind thousands of parameters (`TestSecurity_A04_QueryBoundsPageAndFilterLists`).
- **Your job:** scope the base query to the caller before `api.Query` (`Where("user_id", u.ID)`), so pages never mix users' rows, and keep private columns out of `api.Fields`. More in the [Security overview](/docs/security/overview).

## Common mistakes

**Calling `req.Query.CursorPaginate` on an endpoint with `api.Sorts`.** The client gets a `500` and the log says `orm: CursorPaginate orders by the primary key; remove OrderBy`. Use `req.CursorPaginate(ctx, dir)`, which leaves the default sort out.

**Expecting an unknown include name to load something.** `api.Includes("owner")` on a model whose relation is `User` loads nothing: `owner` matches no relation, so it only lands in `req.Includes`. Name the include after the relation (`user`), or load it yourself from `req.Includes`.

**Expecting `?fields` to remove properties.** It only narrows the `SELECT`; add `omitempty` to the transformer's fields.

**Forgetting quotes in the shell.** `curl localhost:3000/api/v1/tasks?filter[status]=done` may fail with `no matches found` in zsh. Quote the URL.
