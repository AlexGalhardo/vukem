Authentication answers one question: **who is making this request?** Vukem answers it with guards (one for browsers, one for API clients), a user provider that loads users from your database, and a password hasher. The `vukem install:auth` command writes a complete, tested sign-up, login, email verification and password reset flow into your project, as code you own and can change.

You will learn:

- what guards, user providers and hashers are, and how they fit together;
- how to scaffold login, sign-up, email verification and password reset;
- which attacks each step of those flows stops, and why they behave the way they do;
- how to wire a session guard by hand and protect routes with middleware;
- how passwords are hashed and how to test signed-in pages.

## The idea

Picture the entrance of an office building. A **guard** at the door checks each visitor's badge. The guard does not know everyone by heart: they look the badge up in the **staff list**. When a new employee joins, their secret PIN is not written down; only a **scrambled fingerprint** of it is kept, so a stolen staff list reveals no PINs.

| Office | Vukem | Job |
| --- | --- | --- |
| The guard | a <Term tip="A value that decides whether a request comes from a signed-in user, and which one.">guard</Term> | *how* a request proves who it is: a session cookie (`SessionGuard`) or a bearer token (`TokenGuard`, the JWT guard) |
| The staff list | a user provider | *where* users come from: your `users` table through the ORM (`ORMProvider`) |
| The scrambled PIN | a hasher | turns a password into a one-way hash and checks it later (`hash.Default()`, argon2id) |

Your user model plugs in by implementing a small [interface](https://go.dev/tour/methods/9). In Go, a type implements an interface by having its methods; there is no `implements` keyword.

```go title="github.com/AlexGalhardo/vukem/auth"
type Authenticatable interface {
	// AuthID is the user's primary key as a string.
	AuthID() string
	// AuthPassword is the stored password hash.
	AuthPassword() string
}

type UserProvider[U Authenticatable] interface {
	ByID(ctx context.Context, id string) (U, error)
	// ByCredentials never checks the password; the guard does.
	ByCredentials(
		ctx context.Context,
		creds map[string]string,
	) (U, error)
}
```

`UserProvider[U Authenticatable]` uses [generics](https://go.dev/tour/generics/1): `U` is your own user type, so `auth.User[models.User](c, "web")` hands you a `models.User`, not an untyped value. The `ctx` argument is a [`context.Context`](https://pkg.go.dev/context) that carries the request's deadline and cancellation down to the database.

Three optional interfaces add features when your model has them:

| Interface | Method | Enables |
| --- | --- | --- |
| `auth.Verifiable` | `EmailVerified() bool` | the `auth.Verified` middleware |
| `auth.SessionVersioner` | `AuthSessionVersion() int64` | ending every session of a user at once (password reset, 2FA on) |
| `auth.PasswordUpdater[U]` (on the provider) | `UpdatePassword(ctx, u, hash)` | upgrading old password hashes on login |

## The scaffolded flows, step by step

Each flow is written to stop a specific attack. Knowing the attack explains the behaviour that may otherwise look odd.

### Sign-up never says "this email is taken"

**The attack: account enumeration.** If the form answers "email already registered", anyone can type a list of addresses and learn who uses your app. That list feeds phishing and password-guessing attacks ([OWASP testing guide](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/03-Identity_Management_Testing/04-Testing_for_Account_Enumeration_and_Guessable_User_Account)).

`POST /register` therefore answers the same way for new and existing addresses: a redirect to `/register/check-email`, no validation error, and **no login**.

- A **new** address gets the account and a verification mail.
- An **existing** address gets a notice mail instead ("someone tried to sign up with your address; sign in or reset your password", the `AccountExists` mailable), and nothing is created or changed. The notice goes out at most once per hour per address (a cache counter keyed by a SHA-256 of the address, never the address itself), so the form cannot flood a mailbox.
- Both paths hash the password with argon2id and queue exactly one mail, so they take about the same time.
- If the cache fails on the existing-address path, the notice is skipped and the error logged, never returned: an error page would reveal the account.
- The rate limits (10 per 10 minutes per IP, 5 per hour per address hash) count requests, not accounts, so they answer `429` alike for new and existing addresses.

The validation rules live in `app/requests/auth.go`: a name of 2 to 100 characters, an email of at most 255, a password of **12 to 256** characters, and a matching confirmation.

The trade-off: a user who forgot they have an account learns it from the notice mail (which links to `/login` and `/forgot-password`), not from the form.

<Callout type="info">
The per-address limit means anyone can spend an address's budget and keep it from signing up for an hour. It still reveals nothing about whether the address has an account.
</Callout>

### Signed-in pages need a verified email

**The attack: account pre-registration (squatting).** Someone signs up with *your* address before you do, sets a password they know, and waits for you to start using the account.

The scaffold blocks that in three ways:

1. Signed-in pages (the dashboard, and the 2FA settings, billing and admin pages added by other installers) use `auth.Verified`. An unverified login lands on the verification notice, so the squatter's account is useless.
2. `POST /api/v1/tokens` (from `install:api`) answers `403` with `auth.unverified` to unverified users, and `install:admin` admins need a verified `ADMIN_EMAILS` address.
3. When the real owner tries to sign up, they get the "sign in or reset your password" notice. A password reset then ends every session the squatter opened.

### Email verification needs the account's login

The verification mail holds a <Term tip="A URL with an HMAC signature and an expiry time; changing any part of it breaks the signature.">signed link</Term> to `/email/verify/{id}?email_hash=...` that works for one hour (`Accounts.VerifyTTL`). It is signed with a key derived from `APP_KEY` ([Signed URLs](/docs/security/signed-urls)).

Since v0.27.0 the route runs `auth.Required`, so **opening the link needs the login of the account it verifies**:

| Situation | What happens |
| --- | --- |
| Signed out | redirect to `/login`; the link is kept as the intended URL, and the login (also after a 2FA challenge or a social sign-in) comes back to it |
| Signed in as that account | the signature is checked, the address is verified, the dashboard opens |
| Signed in as another account | `403` (`auth.verification_wrong_account`) |
| The link expired meanwhile | back to the notice with "expired, send a new one" (`auth.verification_expired`) |
| The link was tampered with | `403` and the `url.signature_invalid` security event |
| The email changed since the link was sent | `403`: the link carries a SHA-256 of the address (`email_hash`) |
| Already verified | straight to the dashboard; no session ends |

Why the login? Owning the mailbox is not enough: if a squatter created the account, the real owner clicking the link would otherwise verify the squatter's account. Without that account's password the link verifies nothing.

Verifying **ends every other way into the account** opened before the address was proven: other sessions (by bumping `users.session_version`), remember-me tokens and API tokens. The person who just verified keeps their session (`RefreshSession`). Resending the mail (signed in) shares the mail budget of 3 per minute per IP with the reset form.

### Login: same error, same time, limited guesses

**The attacks: password guessing, credential stuffing and timing leaks.** Robots try common passwords or pairs leaked from other sites ([credential stuffing](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html)), and a login that answers faster for unknown emails reveals which ones exist.

- `Attempt` gives the same `422` error on the `email` field ("These credentials do not match our records.", key `auth.failed`) for an unknown email and a wrong password, in every locale.
- An unknown email still costs a full hash check against a dummy hash, so both failures take the same time.
- Each failure logs the `auth.login_failed` security event.
- Attempts are limited to **5 per minute per email + IP** and **20 per 10 minutes per email from any IP**. The email is trimmed and lower-cased first, so `" Ada@Example.com"` opens no new bucket.
- After success the user goes to the intended URL (checked by `web.SafeRedirect`, so it cannot point to another site) or `/dashboard`.
- "Remember me" issues a long-lived cookie (see [Remember-me](#remember-me)).

### Password reset: single use, short-lived, ends every session

**The attacks: reset-link theft and lingering access.** A reset link in an old mail, or a link guessed by brute force, must not work forever; and whoever stole the old password must lose access once it changes ([OWASP forgot password cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)).

- `POST /forgot-password` answers alike for known and unknown emails ("If the email exists..."), and the mail is queued, so timing reveals nothing.
- The token comes from [`crypto/rand.Text`](https://pkg.go.dev/crypto/rand#Text); only its SHA-256 is stored in `password_resets`, one row per email (a new request replaces the old link).
- It works for one hour (`Accounts.ResetTTL`) and once: the row is deleted in the same transaction that changes the password, so two concurrent resets with one token have a single winner. An invalid, expired or used token gives a `422` on `email` (`auth.reset_invalid`).
- The reset ends **every** session on every session driver (it bumps `session_version` and deletes server-side sessions), deletes remember-me tokens and revokes every API token (`Tokens.RevokeAll`, so the tokens stay listed with `revoked_at`).

If you add a "change password" form, call `Accounts.RevokeOtherSessions(ctx, userID, c.Session().ID())` and then `Web.RefreshSession(c)`, so the current session stays and the others end.

### Logout

`POST /logout` invalidates the session (new id, no data) and deletes the request's remember-me token. It is a `POST`, so a link or image on another site cannot sign your users out; [CSRF](/docs/basics/csrf) protection covers it.

### Messages and translations

Flash messages, controller errors and mail subjects go through `accounts.T(ctx, key)`. The catalogs live in `app/accounts/lang/<locale>/*.json` (keys `auth.*`; `--2fa` and `--social` add `two_factor.json` and `social.json`), in English, Spanish and Brazilian Portuguese.

- `T` uses the request locale that `i18n.Middleware` resolves when the app uses `vukem.WithTranslations`, and English otherwise.
- A key in the app's own catalog wins (`resources/lang/pt-BR.json`, then `pt.json`), so you may reword a message or add a locale without editing the scaffold.
- Field messages of the `z` schemas and the views stay in English.
- Errors from the framework itself (failed login, unverified email, missing token ability, social sign-in, `orm.Unique`) carry their own keys and are translated by the built-in catalogs ([Localization](/docs/digging-deeper/localization)).
- `tests/auth_messages_test.go` checks that every key exists in every locale. Mailables built without a `Subject` keep the English one.

### Upgrading an older scaffold

The scaffold is your code, so upgrading Vukem does not change it. Two releases changed the flows:

- **Before v0.26.0**, sign-up answered `409` for a taken email and logged the user in before verification. Port `Register`, `Verify`, `routes/auth.go` and the `AccountExists` mail, or re-run `install:auth --force` (and `install:admin`, `install:billing`, `install:api` for their verified-email checks).
- **Before v0.27.0**, the verification link worked signed out. Re-run `install:auth --force`, or port `Verify` in `app/controllers/account/verification.go`, the `verification.verify` route (now `required` instead of the signature middleware), the `auth.verification_expired` message, the social callback's intended-URL redirect in `routes/social.go`, and the generated tests. The [upgrade guide](https://github.com/AlexGalhardo/vukem/blob/main/docs/upgrade/1.0.md) has the details.

The `examples/` apps in the repository pin an older Vukem and keep the old flow.

## The session guard

The scaffold's `accounts.New` builds the guards for you. This section shows what it does, so you can wire a guard by hand or change one.

```go title="app/accounts/accounts.go"
users := auth.NewORMProvider[models.User](db)

web := auth.NewSessionGuard(
	"web",                      // the guard's name
	users,                      // where users come from
	hash.Default(),             // argon2id
	auth.NewRememberStore(db),  // nil turns remember-me off
)
```

`NewORMProvider[models.User](db)` loads users by primary key (`ByID`) and by every credential except `password` (`ByCredentials`); column names are validated against the model, so a form field cannot inject SQL. Its `PasswordColumn` field (default `password`) receives upgraded hashes.

### Attempt, Validate, Login and Logout

```go title="app/controllers/account/account.go"
func (h *Handlers) Login(c *web.Ctx) error {
	in, err := web.Parse(c, requests.LoginSchema)
	if err != nil {
		return err
	}

	creds := map[string]string{
		"email":    strings.ToLower(in.Email),
		"password": in.Password,
	}

	// 422 on "email" when the credentials do not match.
	_, err = h.a.Web.Attempt(c, creds, auth.Remember(in.Remember))
	if err != nil {
		return err
	}

	target, _ := c.Session().Pull(auth.IntendedKey).(string)

	return c.Redirect(
		web.SafeRedirect(c.Request(), target, "/dashboard"),
	)
}
```

| Method | What it does |
| --- | --- |
| `Attempt(c, creds, opts...)` | finds the user with `ByCredentials`, checks `creds["password"]` in constant time, then calls `Login`. Failure: the same 422 for unknown users and wrong passwords, reported on `IdentifierField` |
| `Validate(c, creds)` | the same check without logging in (API token issuance, the 2FA step). A stale hash is still upgraded |
| `Login(c, u, opts...)` | regenerates the session id against [session fixation](https://owasp.org/www-community/attacks/Session_fixation), stores the user id under `auth_web`, and the owner `"web:<id>"` under `web.SessionUserKey` so [Sessions](/docs/basics/sessions) can list and revoke the user's sessions |
| `Logout(c)` | clears the session (new id, no data) and deletes the request's remember-me token |
| `User(c)` | the signed-in user, cached for the request, or `auth.ErrUnauthenticated` (401) |
| `Check(c)` | `true` when the session (or a remember-me cookie) names a user |
| `RefreshSession(c)` | reloads the user, records its current session version in this session and re-issues the device's remember-me token |
| `SessionUserID(id)` | the owner string `"<guard>:<id>"` to pass to `session.Manager.RevokeOthers` |

`auth.Remember(true)` is a `LoginOption` for `Attempt` and `Login`. In handlers behind `auth.Required`, read the user with `auth.User[models.User](c, "web")`; outside a `*web.Ctx` (an authorization gate, a view function) use `auth.UserFrom[models.User](ctx, "web")`.

### Ending every session at once

Your model implements `auth.SessionVersioner` with a `session_version` column. The guard records the version at login and signs out any session whose version no longer matches the user's, on **every** session driver (encrypted cookie sessions included, which have no server record to delete). Bumping the number ends them all; it costs nothing per request, since the guard loads the user anyway.

```go title="app/models/user.go"
// Sessions logged in with another version are signed out.
func (u User) AuthSessionVersion() int64 {
	return u.SessionVersion
}
```

Declare it on the value receiver `(u User)`, not `(u *User)`: `NewSessionGuard` panics when only the pointer type implements it, because the check would silently never run. Apps that adopt it later add a `session_version BIGINT DEFAULT 0` column first ([Sessions](/docs/basics/sessions)).

`Accounts.RevokeOtherSessions(ctx, userID, keep)` bumps the version, deletes remember-me tokens and deletes server-side sessions except `keep`. With `keep` set, call `Web.RefreshSession(c)` afterwards so the current session survives the bump.

### Remember-me

| Detail | Value |
| --- | --- |
| Cookie | `remember_<guard>` (`remember_web`), `HttpOnly`, `SameSite=Lax`, `Secure` unless `InsecureCookies` |
| Content | `<id>.<secret>`; only `SHA-256(secret)` is stored, in `remember_tokens` |
| Lifetime | 30 days (`RememberFor`) |
| Use | single use: every use rotates it, even under concurrent replays |
| Bound to | the session version: a password reset or 2FA enable also ends remember-me logins |

A rejected remember cookie logs `auth.remember_rejected`; a session ended by a version change logs `auth.session_revoked`.

### When the database is down

`ByID` must report a missing user as `auth.ErrUserNotFound` (or wrap `orm.ErrNotFound` or `sql.ErrNoRows`). The guard then forgets the session. Any **other** error (the database is down) makes `auth.Required` answer `503` and keeps the session, so an outage neither logs everyone out nor treats them as guests. A custom provider that returns a generic error for "not found" leaves a deleted user's session failing with 503 instead of logging out.

## Protecting routes with middleware

| Middleware | Effect |
| --- | --- |
| `auth.Required(guards...)` | lets the request through when any guard authenticates it, trying them in order |
| `auth.Optional(guards...)` | authenticates when possible and never blocks: pages that show more to members |
| `auth.Guest(guards...)` | sends signed-in users to the route named `home` (or `/`): login and sign-up pages |
| `auth.Verified(guard)` | requires `EmailVerified()`: browsers go to the route named `verification.notice` when it exists, JSON clients (and apps without that route) get `403`. Place it after `Required` |
| `auth.Ability(guard, abilities...)` | `403` unless the request's token grants every ability; see [API tokens](/docs/security/api-tokens) |
| `auth.ProblemJSON` | forces RFC 9457 problem+json errors on a route group; see below |

What `auth.Required` does when nobody is signed in:

- **API guards only** (`TokenGuard`, the [JWT guard](/docs/security/jwt), or any guard implementing `auth.APIGuard`): always `401` problem+json with `WWW-Authenticate: Bearer realm="api"`, whatever `Accept` says. Nobody is redirected.
- **Clients that want JSON, or routes without the session middleware**: `401` with the same header.
- **Browsers**: a redirect to the route named `login` (or `/login`). For `GET` requests that are not htmx requests, the URL is kept under `auth.IntendedKey` so the login can come back to it.
- **A guard whose store fails** (`503`): the list stops there, without trying the next guard. On routes that accept a session and a token, list the session guard first: `auth.Required(webGuard, apiGuard)`.

`auth.ProblemJSON` is for API groups that are not only API guards (a session fallback, a custom check). Mount it **first**: `g.Use(auth.ProblemJSON, auth.Required(apiGuard, webGuard))`. Below it, `Required`, `Ability` and `Verified` never redirect, and every 401 and 403 that middleware renders (theirs, or yours through `web.Fail`) is problem+json, a CSRF or rate-limit 403 included. Middleware mounted before it is not affected, and handlers keep negotiating with the client's `Accept` header.

Every guard that authenticates a request also records `auth.Principal(ctx)` (guard name, user id, ok), for code that keys data by caller without knowing the guard, such as `api.Idempotency`. Combine the two values length-prefixed or hashed, since either may contain any character.

## Password hashing

A password must never be stored as written. Vukem stores a slow, salted, one-way hash, so a stolen database does not reveal passwords and each guess costs the attacker real computing time ([OWASP password storage cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)).

| Constructor | Algorithm | Notes |
| --- | --- | --- |
| `hash.Default()` | argon2id, m=64 MiB, t=1, p=4, 16-byte salt, 32-byte key | the OWASP recommendation ([RFC 9106](https://www.rfc-editor.org/rfc/rfc9106)) |
| `hash.Argon2id(p)` | argon2id with your parameters | start from `hash.DefaultArgon2Params()`, which returns a copy |
| `hash.Bcrypt(cost)` | bcrypt, cost 4 to 31 (12 is a good default) | inputs over 72 bytes fail with `hash.ErrPasswordTooLong` instead of being silently truncated |
| `hash.Fake()` | fast argon2id | tests only; the scaffold uses it when `app.Kind == vukem.KindTest` |

Every `Hasher` has `Make(password)`, `Verify(hash, password)` and `NeedsRehash(hash)`. The package-level `hash.Verify` reads both formats; anything else gives `hash.ErrUnknownFormat`. An argon2id hash is a self-describing PHC string:

```text
$argon2id$v=19$m=65536,t=1,p=4$t5MujQfI67zBSxy+ZK96NQ$gvUmrB9...
```

When `NeedsRehash` is true after a successful login (a bcrypt hash from an old system, or weaker argon2 parameters) and the provider implements `PasswordUpdater`, the guard stores a fresh hash. A database moves from bcrypt to argon2id one login at a time.

## Security

| Threat | Defence | Learn more |
| --- | --- | --- |
| Password guessing, credential stuffing | rate limits per email + IP and per account; 12-character minimum | [OWASP authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) |
| Account enumeration | same answer and timing for sign-up, login and reset | [OWASP A07](https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/) |
| Stolen database | argon2id passwords; hashed reset, remember-me and API tokens | [password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) |
| Session fixation and hijacking | new session id on login; `HttpOnly`, `Secure`, `SameSite` cookies; session versions | [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) |
| Account squatting | verified email required; verification needs the login; proving the email ends older access | [OWASP A07](https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/) |
| Open redirect after login | `web.SafeRedirect` keeps the intended URL on your site | [OWASP A01](https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/) |

What stays your job: serve the app over HTTPS, keep the queue running, and call `RevokeOtherSessions` from any new form that changes credentials. The full list is on the [Security overview](/docs/security/overview).

## Testing

`vukemtest` clients can skip the login form:

```go title="tests/dashboard_test.go"
func TestDashboard(t *testing.T) {
	app := vukemtest.New(t, bootstrap.New)
	user := createVerifiedUser(t, app)

	// Stores what Login stores, the session version included.
	app.Client(t).
		ActingAs("web", user).
		Get("/dashboard").
		AssertOK()

	// Guests are sent to the login page.
	app.Client(t).Get("/dashboard").AssertRedirect("/login")
}
```

`createVerifiedUser` stands for your own helper (a [factory](/docs/database/factories-seeders)). `.WithSession(values)` adds other session values, and `.WithToken(plain)` sends a bearer token. `auth.SessionValues(guard, user)` returns the values `Login` stores, for custom test setups. The generated `tests/auth_test.go` covers every flow on this page; read it as an example.

## Common mistakes

**Building your own "email taken" message.** Wrong: returning `409 Conflict` from `Register` when the email exists. Right: keep the scaffold's single answer; the owner learns it from the notice mail.

**A custom `ByID` that hides "not found".** Wrong: `return User{}, errors.New("no user")`. Every request of a deleted user then fails with `503 Service Unavailable` instead of logging out. Right: `return User{}, auth.ErrUserNotFound`.

**A pointer receiver on `AuthSessionVersion`.** Wrong: `func (u *User) AuthSessionVersion() int64`. The app panics at boot when it builds the guard. Right: `func (u User) AuthSessionVersion() int64`.

**Token guard before session guard on mixed routes.** Wrong: `auth.Required(apiGuard, webGuard)`. A browser with a valid session and a stray `Bearer` header gets `503` while the token store is down. Right: `auth.Required(webGuard, apiGuard)`.

**Leaving `QUEUE_CONNECTION=sync` in production.** Sign-up and reset then take longer for existing accounts (they send a mail inline), which reveals them. Right: `QUEUE_CONNECTION=database`.
