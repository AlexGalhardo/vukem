---
title: Admin panel
description: Generate an HTMX admin panel from your ORM models, with search, sort, filters, forms from z schemas, policies on every action, a feature flags page and an audit log.
---

Every app ends up needing a back office: a place where staff list records, fix a typo in a post or delete spam. Writing those screens by hand is slow and easy to get wrong, because each one needs authentication, permission checks, CSRF protection and safe queries. The `admin` package builds them for you from your models: lists with search, sort, filters and pagination, detail pages, create and edit forms, deletes behind a confirmation page, a [feature flags](/docs/digging-deeper/feature-flags) page and an audit log of every change.

You will learn:

- how to install the panel and add a model to it;
- how a resource turns a model and a `z` schema into lists and forms;
- who may do what, and how the panel fails closed;
- how the audit log and the flags page work;
- how to change the look by overriding templates;
- how to test the panel.

## The idea

Think of the panel as the staff-only door at the back of a shop. A guard at the door checks who you are (**authentication**), a manager decides whether staff may come in at all (the **panel ability**), and each shelf has its own rule about who may touch it (a **policy** per model). Every time someone moves something, it is written in a logbook (the **audit log**).

The panel is server-rendered HTML ([`html/template`](https://pkg.go.dev/html/template)) with [htmx](https://htmx.org) for searching and paging without a full reload. Everything it needs, templates, CSS and htmx itself, is embedded in the Go binary with [`embed`](https://pkg.go.dev/embed): no CDN, and no inline scripts or styles, so it runs under a strict Content Security Policy.

The package is part of the core module and uses the standard library only.

Throughout this page you build one example: the admin side of a blog with posts.

## Quick start

<Steps>
<Step title="1. Install authentication and the panel">

```bash
vukem install:auth
vukem install:admin
```

`install:admin` needs `install:auth` (it checks for `app/accounts/accounts.go`) and a web project with sessions (`routes/web.go`). It writes:

| File | What it holds |
| --- | --- |
| `routes/admin.go` | the panel, mounted at `/admin`, with its own `authz.Gate` |
| `app/admin/admin.go` | `Admins`: who counts as an admin, read from `ADMIN_EMAILS` |
| `app/admin/registry.go` | `Resources()` and `Policies(admins)`, filled by `make:admin-resource` |
| `database/migrations/<timestamp>_create_admin_audit_logs_table.go` | the audit log table |
| `tests/admin_test.go` | access tests for the panel |

It also registers the migration and the route file and adds `ADMIN_EMAILS` to `.env.example`. `--force` overwrites existing files.

</Step>
<Step title="2. Add a model">

```bash
vukem make:admin-resource Post
```

The command checks that `app/models` declares `type Post struct` (otherwise it tells you to run `vukem make:model Post`). It writes `app/admin/post.go`, with the resource and a `PostPolicy` that allows admins every action, and `tests/admin_post_test.go`, then registers both in `app/admin/registry.go`. When `app/requests` declares `var PostSchema`, the resource uses it for its forms; otherwise it starts with an empty `z.Shape` for you to fill.

</Step>
<Step title="3. Migrate and name the admins">

```bash title=".env"
ADMIN_EMAILS=you@example.com,editor@example.com
```

```bash
vukem migrate
vukem serve
```

Open `http://localhost:3000/admin`. Guests are sent to the login page; after you sign in with a listed, **verified** address you see the dashboard with a card per resource and its record count.

</Step>
</Steps>

`ADMIN_EMAILS` is a comma-separated list, compared without case. When it is empty, nobody is an admin. A listed address only counts once the account's email is verified: otherwise anyone could sign up first with the admin's address and walk in.

## The wiring

This is what `install:admin` writes in `routes/admin.go`, trimmed to the important lines:

```go title="routes/admin.go" nocompile
admins := admin.NewAdmins(app.Source.Get("ADMIN_EMAILS"))

// The panel has its own gate, so its policies never mix with the
// app's.
gate := authz.New(func(ctx context.Context) (*models.User, error) {
	u, err := auth.UserFrom[models.User](ctx, acc.Web.Name())
	return &u, err
})

isAdmin := func(_ context.Context, u *models.User) bool {
	return admins.Has(u)
}
gate.Define(vadmin.AbilityAdmin, isAdmin)
gate.Define(vadmin.AbilityAudit, isAdmin)
gate.Define(vadmin.AbilityFlags, isAdmin)

if err := gate.Register(admin.Policies(admins)...); err != nil {
	return err
}

ff, err := app.Flags()
if err != nil {
	return err
}

panel, err := vadmin.New(vadmin.Config{
	DB:         acc.DB,
	Guard:      acc.Web,
	Authorizer: gate,
	Title:      app.Config.Name + " admin",
	Flags:      ff,
})
if err != nil {
	return err
}

if err := panel.Register(admin.Resources()...); err != nil {
	return err
}

return panel.Mount(r)
```

`vadmin` is the framework's `admin` package, renamed on import because your own package is also called `admin`. The three steps are always the same:

1. `admin.New(cfg)` validates the configuration and returns an empty `*admin.Panel`.
2. `panel.Register(resources...)` checks and adds each resource. Mistakes come back here, at boot.
3. `panel.Mount(r)` adds every route to the [router](/docs/basics/routing).

### Config

| Field | Default | Meaning |
| --- | --- | --- |
| `DB` | required | the database holding the records and the audit log |
| `Guard` | required | an `auth.Checker` that authenticates admins, usually the `web` session guard |
| `Authorizer` | the router's `Services.Authorizer` | decides the panel and policy abilities, usually an `authz.Gate`; with none at all, everything is denied |
| `Prefix` | `/admin` | the URL prefix; slashes are trimmed, and `/` is refused |
| `Ability` | `admin` | the gate ability required on every page |
| `Title` | `Admin` | the header text |
| `Views` | embedded templates | an `fs.FS` that overrides templates by path |
| `Flags` | nil | a `*flags.Flags` that adds the flags page |
| `TwoFactor` | nil | `func(ctx context.Context) (bool, error)`: when set, 2FA is mandatory; it reports whether the signed-in admin has 2FA enabled (see [Hardening](#hardening)) |
| `MaxSessionAge` | 0 (off) | the oldest a session may be to use the panel, counted from its creation |
| `IdleTimeout` | 0 (off) | how long a session may go without a guarded admin request |
| `AllowCIDRs` | empty (any IP) | `[]netip.Prefix`: only client IPs inside one of them reach the panel |
| `DenyStatus` | 0 (403) | status for IPs outside `AllowCIDRs`: `403` or `404` |
| `TwoFactorRedirect` | empty (403) | local path an admin without 2FA is redirected to |
| `TwoFactorFlash` | empty | message flashed under `admin.TwoFactorFlashKey` with that redirect (needs `TwoFactorRedirect`) |
| `Now` | `time.Now` | the clock for `MaxSessionAge` and `IdleTimeout` (tests) |

`admin.New` fails with `admin: Config.DB is required`, `admin: Config.Guard is required (the panel never runs without authentication)` or `admin: Config.Prefix cannot be the site root`; a negative `MaxSessionAge` or `IdleTimeout`, an invalid prefix in `AllowCIDRs`, a `DenyStatus` other than 403 or 404, a `TwoFactorRedirect` that is not a local path, or a `TwoFactorFlash` without `TwoFactorRedirect`, fails it too.

## Resources

A resource shows one model in the panel. The generated `app/admin/post.go` looks like this:

```go title="app/admin/post.go"
// Post is the admin resource for models.Post at /admin/posts.
func Post() *vadmin.Resource[models.Post] {
	return vadmin.NewResource[models.Post](requests.PostSchema).
		Search("title", "body").
		Filter("status", "draft", "published").
		List("id", "title", "status", "created_at")
}
```

The schema is the same [`z`](/docs/basics/validation) schema your app's forms use:

```go title="app/requests/post.go"
type PostInput struct {
	Title  string `form:"title"`
	Body   string `form:"body"`
	Status string `form:"status"`
}

var PostSchema = z.Struct[PostInput](z.Shape{
	"title":  z.String().Trim().Min(3).Max(120),
	"body":   z.String().Max(5000).Optional(),
	"status": z.Enum("draft", "published"),
})
```

`admin.NewResource[T](schema)` takes the model type `T` explicitly; Go [infers](https://go.dev/ref/spec#Type_inference) the input type from the `z.StructSchema`. Under the hood:

- **Columns** come from the ORM metadata of `T`, the same as [ORM](/docs/database/orm) queries use.
- **Form fields** come from the schema keys. Each key is written to the model column with the same name (or the snake_case of the input field's name).
- **Only schema keys are ever written.** This is the panel's mass-assignment protection: a crafted form field that is not in the schema is ignored.

### Form controls

The control for each field follows the schema:

| Schema | Control |
| --- | --- |
| `z.Enum(...)` or `OneOf(...)` | select |
| `z.Bool()` | checkbox (with a hidden `false`, so unticking saves) |
| `z.Int()`, `z.Float()` and other numbers | number input |
| `z.String().Email()` | email input |
| `z.String().URL()` | url input |
| a date-time format, or a `time.Time` / `orm.NullTime` column | `datetime-local` input |
| `z.String().Max(n)` with `n` up to 255 | text input |
| any other string | textarea |
| a sensitive column | empty password input |

`Input(key, kind)` overrides the control with one of `admin.InputText`, `InputTextarea`, `InputNumber`, `InputEmail`, `InputURL`, `InputPassword`, `InputCheckbox`, `InputSelect`, `InputDate` or `InputDateTime`.

When validation fails, the form is shown again with status **422** and the messages next to each field. A unique-index conflict shows "This record conflicts with an existing one."

### Options

Options chain: each returns the resource.

| Option | Effect |
| --- | --- |
| `Slug(s)` | URL segment (default: the table name in kebab-case, such as `blog-posts`); lowercase letters, digits and `-` |
| `Labels(singular, plural)` | names shown in the UI |
| `Label(col, text)` | the label of one column |
| `List(cols...)` | list columns, in order (default: every column that is not hidden or sensitive) |
| `Column(label, fn)` | a computed column, `func(T) string`; its result is HTML-escaped |
| `Search(cols...)` | a search box over string columns, nullable ones (`sql.NullString`, `sql.Null[string]`) included |
| `Sortable(cols...)` | columns the list may be sorted by (default: the listed ones) |
| `Filter(col, options...)` | an exact-match filter on a string, integer or boolean column (or its `sql.Null*` / `sql.Null[T]` form): a select with the options, a text box without; boolean columns get yes/no. Rows where the column is NULL never match a filter value |
| `PerPage(n)` | page size, 1 to 200 (default 20) |
| `Hidden(cols...)` | never shown; hidden schema keys are never written |
| `ReadOnly(cols...)` | shown disabled on the edit form, never written |
| `Sensitive(cols...)` | secret columns, on top of the ones detected by name (see Security) |
| `Input(key, kind)` | override a form control |
| `BeforeSave(fn)` | runs before every create and update |
| `AfterSave(fn)` | runs after every create and update, with the transaction, the previous record and the virtual field values |
| `Virtual(key, value)` | a schema key with no model column, handled by `AfterSave` |

Search is a case-insensitive `LIKE` (`ILIKE` on PostgreSQL) with bound parameters; `%` and `_` in the search text match literally.

`BeforeSave(func(ctx context.Context, rec *T) error)` runs after validation, inside the same database transaction as the write. Use it to hash a password or set an owner. Returning an error aborts the write; returning `z` issues (for example `z.FieldError("title", "Taken.")`) shows them on the form.

```go title="app/admin/post.go"
func Post() *vadmin.Resource[models.Post] {
	return vadmin.NewResource[models.Post](requests.PostSchema).
		Column("Words", func(p models.Post) string {
			return strconv.Itoa(len(strings.Fields(p.Body)))
		}).
		BeforeSave(func(ctx context.Context, p *models.Post) error {
			// New posts belong to the admin who wrote them.
			if p.AuthorID == 0 {
				u, err := auth.UserFrom[models.User](ctx, "web")
				if err != nil {
					return err
				}
				p.AuthorID = u.ID
			}
			return nil
		})
}
```

### Concurrent edits

An update locks the stored row (`SELECT ... FOR UPDATE`) inside the save transaction and writes only the columns the form changed, compared with the row as the panel loaded it. A column the form left alone keeps whatever another session wrote in the meantime, so saving a title never reverts a body, a counter or a provenance column that changed after the form was opened.

If a column the form changed was also changed by another writer after the panel loaded the row, the save is refused with the same "This record conflicts with an existing one." form error that a unique violation shows, and nothing is written. Reload the record and submit again. `BeforeSave` runs before the lock, so a column it sets counts as changed; `AfterSave` and the audit entry see the merged record, and the audit diff lists only what this save changed.

### Side effects: `AfterSave` and virtual fields

`BeforeSave` gets only the record. When a save must write other tables or fire an event, use `AfterSave(func(ctx context.Context, s admin.Saved[T]) error)`. It runs after the record is written, inside the panel transaction and before the audit entry, with:

| Field | What it holds |
| --- | --- |
| `s.Tx` | The panel transaction (`*database.Tx`): write related rows through it; `s.Tx.AfterCommit(fn)` runs `fn` only once the save is committed |
| `s.Action` | `admin.ActionCreate` or `admin.ActionUpdate` |
| `s.Record` | The record as written |
| `s.Before` | A copy of the record before the form was applied; `nil` on create |
| `s.Virtual` | The parsed values of the submitted virtual fields, by schema key |

Returning an error rolls the whole save back, audit entry included. Write through `s.Tx`, never through the app's `*database.DB`: on SQLite a second writer waits for the panel transaction and deadlocks, and on PostgreSQL the write would escape the rollback.

A schema key normally has to match a model column. `Virtual(key, value)` declares one that does not: the form shows it, validation runs, its value reaches `s.Virtual`, and nothing writes it to the record. `value` renders the current state on the edit form, so a checkbox does not silently flip on the next save:

```go title="app/admin/user.go"
vadmin.NewResource[models.User](requests.AdminUserSchema). // has a Banned bool field
	Virtual("banned", func(u *models.User) any { return u.BannedAt.Valid }).
	AfterSave(func(ctx context.Context, s vadmin.Saved[models.User]) error {
		banned, _ := s.Virtual["banned"].(bool)
		if banned == s.Before.BannedAt.Valid {
			return nil
		}
		// accounts.SetBanned updates users.banned_at through s.Tx, records an
		// account event and revokes the user's tokens.
		if err := accounts.SetBanned(ctx, s.Tx, s.Record, banned); err != nil {
			return err
		}
		s.Tx.AfterCommit(func(ctx context.Context) { notifyBanned(ctx, s.Record.ID, banned) })
		return nil
	})
```

Changes the hook makes to `s.Record` and writes through `s.Tx` appear in the audit diff. A schema key without a column that `Virtual` does not declare is still a `Panel.Register` error, so a typo cannot hide.

### Mistakes caught at boot

`panel.Register` returns every mistake, prefixed with `admin: resource <slug>:`, so a broken resource never reaches production:

- a schema key that matches no column (`schema key "titel" matches no column of Posts`);
- a schema key for the primary key or a timestamp (`schema key "id" writes the protected column "id"`);
- a sensitive column in `List`, `Search`, `Sortable` or `Filter` (`sensitive column "api_token" cannot be listed`);
- a search on a column that is not a string, or a filter on a type that cannot be filtered;
- an unknown column in an option (`unknown column "titel"`), an invalid slug, a page size outside 1 to 200, an unknown input type or an `Input` for a key that is not in the schema;
- two resources with the same slug (`admin: duplicate resource "posts"`).

## Routes and abilities

Every route needs the guard, the panel ability (`admin` by default) and then the ability in the last column. Policy abilities are checked on the model type, `(*T)(nil)`, or on the record itself, `*T`, as [authorization](/docs/security/authorization) policies expect.

| Method | Path | Name | Ability |
| --- | --- | --- | --- |
| GET | `/admin` | `admin.dashboard` | the panel ability |
| GET | `/admin/_audit` | `admin.audit` | `viewAuditLogs` |
| GET | `/admin/_flags` (only with registered flags) | `admin.flags` | `manageFlags` |
| POST | `/admin/_flags/{name}` | `admin.flags.update` | `manageFlags` |
| GET | `/admin/{slug}` | `admin.{slug}.index` | `viewAny` on the type |
| GET | `/admin/{slug}/create` | `admin.{slug}.create` | `create` on the type |
| POST | `/admin/{slug}` | `admin.{slug}.store` | `create` on the type |
| GET | `/admin/{slug}/{id}` | `admin.{slug}.show` | `view` on the record |
| GET | `/admin/{slug}/{id}/edit` | `admin.{slug}.edit` | `update` on the record |
| POST | `/admin/{slug}/{id}` | `admin.{slug}.update` | `update` on the record |
| GET | `/admin/{slug}/{id}/delete` | `admin.{slug}.delete` | `delete` on the record (confirmation page) |
| POST | `/admin/{slug}/{id}/delete` | `admin.{slug}.destroy` | `delete` on the record |
| GET | `/admin/{slug}/{id}/actions/{name}` | none | the action's `Name` on the record (confirmation page) |
| POST | `/admin/{slug}/{id}/actions/{name}` | none | the action's `Name` on the record |
| GET / POST | `/admin/{slug}/_bulk/{name}` (`Bulk` actions only) | none | the action's `Name` on every selected record |

The ability names are constants: `admin.AbilityAdmin`, `AbilityAudit`, `AbilityFlags`, `AbilityViewAny`, `AbilityView`, `AbilityCreate`, `AbilityUpdate` and `AbilityDelete`. The flags routes exist only when `Config.Flags` is set and at least one flag is registered, so registering your first flag in an app scaffolded with `install:admin` adds `/admin/_flags` (and an entry to a route-inventory test, if you have one). `/admin/_assets/admin.css` and `/admin/_assets/htmx.min.js` are public and cached for an hour.

The navigation only shows the resources the user may `viewAny`, and the audit and flags links only to users with those abilities. The dashboard counts records of the resources the user may list.

Lists answer htmx partial requests (search, sort, pagination) with only the list block, and send `Vary: HX-Request` so caches keep the two versions apart. After a save, the panel redirects to the record when the user may `view` it, otherwise to the list, and shows a flash message such as "Post saved." (session key `admin.FlashKey`, `admin.success`).

### Composite primary keys

A model with `PrimaryKeys() []string` (`orm.CompositeKeyer`) is a resource too. The `{id}` segment is those values in order, joined with `-`: user 1 and item 10 is `/admin/ratings/1-10`. Detail, edit, delete and bulk actions filter on every key column, so the URL does not resolve by the first column alone. A `-` or `~` inside a value is escaped (`-` becomes `~`, a `~` becomes `~~`). The wrong number of segments, or a segment that does not match the column type, is 404. A schema key still cannot write a key column.

## Custom actions

Moderation needs more than create, edit and delete: approve a suggestion, reject it with a reason, approve twenty at once. `Resource.Actions` adds such operations:

```go title="app/admin/admin.go"
admin.NewResource[models.Suggestion](requests.SuggestionSchema).Actions(
	admin.Action[models.Suggestion]{
		Name: "approve",
		Bulk: true, // also on the rows selected in the list
		Run: func(ctx context.Context, tx *database.Tx,
			s *models.Suggestion, _ string) error {
			s.Status = "approved"
			return nil
		},
	},
	admin.Action[models.Suggestion]{
		Name:   "reject",
		Label:  "Reject with reason",
		Reason: true,
		Run: func(ctx context.Context, tx *database.Tx,
			s *models.Suggestion, reason string) error {
			s.Status, s.RejectReason = "rejected", reason
			return nil
		},
	},
)
```

| Field | Meaning |
| --- | --- |
| `Name` | the policy ability, the URL segment and the audit action: lower camel (`[a-z][a-zA-Z0-9]*`), at most 16 characters, not `viewAny`, `view`, `create`, `update`, `delete` or `edit` |
| `Label` | the button text (default: `Name` humanized, "Approve") |
| `Reason` | the confirmation page asks for a reason: required, at most `admin.MaxReason` (1000) characters, passed to `Run` and stored in the audit entry under `admin.ReasonKey` (`_reason`) |
| `Bulk` | adds a checkbox per row and an "Approve selected" button to the list |
| `Run` | changes the record (the panel saves changed fields with `orm.Update` afterwards) and may write anything else through `tx` |

What happens on a run:

1. The button opens a confirmation page (`GET`); the action itself is a CSRF-checked `POST`.
2. The user needs the policy method named after the action on the record: `Approve(ctx, user, *Suggestion) bool` for `approve`. A policy without it denies with **403**, like every other admin ability.
3. `Run`, the save and one audit entry per record share **one transaction**: an error from any of them rolls everything back.
4. The panel redirects to the record (row action) or the list (bulk action) with a flash message.

A bulk action takes 1 to `admin.MaxBulk` (100) selected ids. Each record is loaded and authorized first; a bad id, a missing record or one record the user may not act on fails the whole selection with nothing changed.

The record page shows a button for each action the user may run on that record. To assign records to a moderator, add an `assignee_id` column to the form, or set it from an action such as `Name: "assignToMe"`.

## The audit log

Every create, every update that changed something and every delete writes an `admin.AuditLog` row **in the same transaction** as the change. If the log row fails, the change is rolled back.

| Field | Column | Meaning |
| --- | --- | --- |
| `ActorID` | `actor_id` | the `AuthID()` of the user who made the change |
| `Resource` | `resource` | the resource slug (`posts`), or `_flags` |
| `RecordID` | `record_id` | the primary key of the record |
| `Action` | `action` | `admin.ActionCreate`, `ActionUpdate`, `ActionDelete` or a custom action's `Name` |
| `Changes` | `changes` | JSON: column → `admin.Change` with `before` and `after` |
| `CreatedAt` | `created_at` | when it happened |

For a sensitive column, the `Change` is only `{"redacted": true}`: the log records that it changed, never the value. The table is `admin.AuditTable` (`admin_audit_logs`), created by `admin.Migration("<timestamp>_create_admin_audit_logs_table")`, which `install:admin` registers for you.

Browse the log at `/admin/_audit`, newest first, 50 entries per page. `?resource=posts` narrows it to one resource (only registered slugs and `_flags` are accepted). Custom actions appear with their `Name` as the action. When both sides of a change are JSON objects (a JSON column), the page lists only the keys that differ, as `column.key` and recursively, instead of two whole documents.

## The feature flags page

With `Config.Flags` set and at least one flag registered (the `install:admin` scaffold passes `app.Flags()`), the panel lists every registered [feature flag](/docs/digging-deeper/feature-flags) at `/admin/_flags`: name, description, kind, default (the code default or `FLAG_<NAME>`), current global value and whether a value is stored.

- **Boolean** flags toggle with one button. **Int** and **string** flags take a value in a text box.
- **Reset to default** deletes the stored value.
- **Locked** flags are shown read-only. A crafted write to one is refused with **403** ("This flag is locked in code.") and logged as a `flags.locked_write` security event.
- An unknown flag name answers **404**, an invalid value **422** ("Invalid value for this flag.").
- When the flag store is down, the page answers **503** instead of showing defaults that would invite wrong toggles.

Without registered flags, `/admin/_flags` and its POST route do not exist (404) and the menu has no link.

The page changes **global** values only; per-user and per-tenant values are written from code with `flags.Put`.

Every change is recorded twice (a save that leaves the value as it was, or a reset to the value already in effect, records nothing and flashes "unchanged"):

1. a `flags.changed` audit event in the log (`web.AuditEvent`), with `actor_id`, `flag`, `changed`, `old` and `new`;
2. an audit-log row with resource `_flags` (`admin.FlagsResource`), the flag name as record id and a `value` change. Browse them at `/admin/_audit?resource=_flags`.

String values may hold anything, so both records keep only their length and a SHA-256 prefix, such as `10 bytes, sha256:1a2b3c4d`, never the value in clear.

<Callout type="warning" title="Flag write and audit row are not atomic">
The flag store is pluggable, so its write and the audit row cannot share a transaction. If the row fails after the flag changed, the change is logged at ERROR (redacted the same way) and the page shows a warning flash. The flag stays changed.
</Callout>

An app that ran `install:admin` before v0.27.0 wires the page by hand in `routes/admin.go`: define the ability on its gate and pass the flags.

```go title="routes/admin.go"
gate.Define(vadmin.AbilityFlags, isAdmin)

ff, err := app.Flags()
if err != nil {
	return err
}

panel, err := vadmin.New(vadmin.Config{
	DB:         acc.DB,
	Guard:      acc.Web,
	Authorizer: gate,
	Flags:      ff,
})
```

## Custom pages

A page that is not a model resource (an ingestion queue, a status board) can live inside the panel with `Panel.AddPage`. It gets the same layout, navigation, title and guard as the resources, so it never drifts from them:

```go
err := panel.AddPage("ingestion", "Ingestion", func(c *web.Ctx) (template.HTML, error) {
	var buf bytes.Buffer
	if err := ingestionTmpl.Execute(&buf, loadQueue(c.Context())); err != nil {
		return "", err
	}
	return template.HTML(buf.String()), nil
})
```

The page is served at `<Prefix>/ingestion` for GET, listed in the sidebar after the resources, and runs behind `Panel.Guard()` (login, panel ability, 2FA, IP and session limits). The returned HTML is trusted, so escape user data (`html/template` does). Slugs share the namespace of the resources and must match `[a-z0-9][a-z0-9-]*`. Call `AddPage` before `Mount`. For POST routes, register them on the router behind `Panel.Guard()`.

## Customizing the look

`Config.Views` takes any [`fs.FS`](https://pkg.go.dev/io/fs#FS). A file in it replaces the embedded template with the same path; every other template keeps the original. The paths are `layouts/admin.html`, `index.html`, `show.html`, `form.html`, `delete.html`, `dashboard.html`, `audit.html`, `flags.html`, `action.html`, `page.html` and `partials/pager.html`.

`admin.Templates()` returns the embedded originals, so you can copy one and edit it:

```go title="routes/admin.go"
panel, err := vadmin.New(vadmin.Config{
	DB:         acc.DB,
	Guard:      acc.Web,
	Authorizer: gate,
	Views:      os.DirFS("resources/views/admin"),
})
```

Keep the overrides free of inline `<script>` and `style` attributes, or the strict CSP blocks them.

## Security

| Default | What it means |
| --- | --- |
| **Fail closed** | Every route needs the guard, the panel ability and the policy ability. A missing ability, policy or authorizer answers **403** and logs an `authz.denied` security event (with `area=admin`). Guests are redirected to the route named `login`; JSON requests get **401**. |
| **CSRF** | The panel adds `csrf.Middleware` (with the session-token fallback) to its routes, and its forms carry the token. |
| **Mass assignment** | Only schema keys are read from the form and written. Every primary-key column (one or several), timestamps, hidden and read-only columns never are. |
| **Injection** | Sort, filter and search columns are allowlists; anything else is ignored. Values are bound parameters. |
| **Secrets** | Columns tagged `json:"-"`, columns whose name contains `password`, `passwd`, `secret`, `token`, `api_key`, `apikey`, `private_key`, `recovery`, `otp` or `totp` anywhere (except the counters `tokens_used`, `tokens_count`/`_total`/`_remaining`/`_limit`, `max_tokens*`, `*_token_count` and names containing `footprint`), and columns marked `Sensitive` are never displayed, listed, searched, sorted or filtered. On a form they are empty password inputs that keep the stored value when left blank. The audit log records only that they changed. |
| **Headers** | Pages send `Cache-Control: no-store` and `X-Frame-Options: DENY`, plus a strict CSP when the app set none: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`. |

### Hardening

Four opt-in controls for the panel, all fail closed:

```go
panel, err := admin.New(admin.Config{
	DB: db, Guard: acc.Web, Authorizer: gate,
	// 2FA is mandatory: the state lives in your users table.
	TwoFactor: func(ctx context.Context) (bool, error) {
		u, err := auth.UserFrom[models.User](ctx, "web")
		if err != nil {
			return false, err
		}
		return u.TwoFactorEnabled, nil
	},
	MaxSessionAge: 12 * time.Hour,
	IdleTimeout:   30 * time.Minute,
	AllowCIDRs:    []netip.Prefix{netip.MustParsePrefix("10.0.0.0/8")},
})
```

| Option | Behaviour |
| --- | --- |
| `TwoFactor` | `false` answers **403** and logs an `admin.2fa_required` security event. An error is a 403 too, and is logged; the client never sees it. Set `TwoFactorRedirect` to send admins without 2FA to your setup page instead. |
| `TwoFactorRedirect` | A local path such as `/settings/2fa`: an admin whose `TwoFactor` is `false` gets a **303** there instead of the 403 (the security event is still logged). A failing lookup stays 403. `admin.New` rejects anything that is not a local path. |
| `MaxSessionAge` | A session older than the cap (from `session.CreatedAt`, which login keeps, so the age is never shorter than the time since login) is invalidated, signing the user out of every guard, and the browser is redirected to `login`; an `admin.session_expired` event is logged. The rest of the app keeps its own `SESSION_LIFETIME`. A remember-me cookie logs the user back in with a new session, so turn remember-me off for admins when the cap must force a password. |
| `IdleTimeout` | A session that has not hit a guarded admin route for this long is invalidated the same way, with an `admin.session_idle` event. The stamp is `admin.idle_at` in the session, updated only by those routes, so using the rest of the app does not keep the panel open, unless you add `panel.TrackIdle()` (below). |
| `AllowCIDRs` | Requests from other IPs get **403** and an `admin.ip_denied` event, before any login redirect, so the panel never advertises its login. The IP is `web.Ctx.IP`: behind a proxy, set `TRUSTED_PROXIES` ([HTTP context](/docs/basics/http-context)) or every request looks like the proxy's address. The embedded CSS and JS stay public. |
| `DenyStatus` | The status `AllowCIDRs` answers: `403` (the default) or `404`, which hides that the panel exists at all. Anything else fails `admin.New`. |

`panel.Mount` is the only place that installs this stack. A route you register beside it, such as `POST /admin/users/{id}/ban`, does not get `AllowCIDRs`, the session caps, two-factor or the panel ability unless you add `panel.Guard()`:

```go
panel, err := admin.New(cfg)
// ...
if err := panel.Mount(r); err != nil {
    return err
}

r.Post("/admin/users/{id}/ban", users.Ban).Use(panel.Guard())
```

`Guard` is that middleware: IP allow-list, `MaxSessionAge`, `IdleTimeout`, the auth guard, CSRF, the no-store headers, two-factor and the panel ability. It does not check a resource policy; `users.Ban` still calls `c.Authorize`. Sessions have to be on the router already (`vukem.DefaultMiddleware`). The embedded CSS and JS stay outside the guard.

To give an admin one idle clock across the whole app, add `panel.TrackIdle()` router-wide. For a session that has used the panel, every request refreshes `admin.idle_at` and an idle session is ended wherever it shows up, so a moderator who browses public pages stays signed in and one who walks away is signed out. Sessions that never reached the panel are not touched (no session write, no cookie). Without `IdleTimeout` it does nothing.

```go
r.Use(panel.TrackIdle())
```

`TrackIdle` only follows sessions that already used the panel. When every request of an admin or moderator must count, wherever they browse, use `panel.Clock()` instead. It checks each request with the panel's `Guard` and `Ability`: for a user who holds the ability, the request refreshes the shared `admin.idle_at` clock, and `MaxSessionAge` counts from the first such request (session key `admin.clock_at`), not from the session's creation. A session past either limit is invalidated with the same `admin.session_idle` or `admin.session_expired` event, and the request goes on as a guest. Guests and users without the ability are not touched.

```go title="routes/web.go"
r.Use(panel.Clock())
```

With `TwoFactorRedirect`, set `TwoFactorFlash` to tell the admin why they landed on the setup page. The message is flashed under `admin.TwoFactorFlashKey` (`"admin.2fa_required"`), so the page reads it like any other flash:

```go title="app/admin/admin.go"
cfg.TwoFactorRedirect = "/profile#two-factor"
cfg.TwoFactorFlash = "Turn on two-factor authentication to use the admin panel."
```

What stays your job: deciding who is an admin (`app/admin/admin.go`), narrowing each policy (an editor may update posts but not delete them), and keeping the admin accounts protected with [two-factor authentication](/docs/security/two-factor). See the [security overview](/docs/security/overview).

## Testing

The generated `tests/admin_test.go` boots the app with an admin listed in `ADMIN_EMAILS` and checks who gets in:

```go title="tests/admin_test.go"
func TestAdminPanelAccess(t *testing.T) {
	t.Parallel()

	app := newAdminApp(t)

	app.Client(t).Get("/admin").AssertRedirect("/login")
	adminClient(t, app, "user@example.com").
		Get("/admin").
		AssertForbidden()

	c := adminClient(t, app, adminEmail)
	c.Get("/admin").AssertOK().AssertSee("Dashboard")
	c.Get("/admin/_audit").AssertOK().AssertSee("Audit log")
	c.Get("/admin/_flags").AssertOK().AssertSee("Feature flags")
}
```

`adminClient` creates a user with a verified email and returns a client logged in as that user with `ActingAs("web", u)`. It also sends `Sec-Fetch-Site: same-origin`, so the panel's CSRF check accepts its POST requests. Each `make:admin-resource` adds a test for its resource:

```go title="tests/admin_post_test.go"
func TestAdminPostResource(t *testing.T) {
	t.Parallel()

	app := newAdminApp(t)
	c := adminClient(t, app, adminEmail)

	c.Get("/admin").AssertOK().AssertSee(`href="/admin/posts"`)
	c.Get("/admin/posts").AssertOK()
	c.Get("/admin/posts/create").AssertOK()

	adminClient(t, app, "user@example.com").
		Get("/admin/posts").
		AssertForbidden()
}
```

## Common mistakes

**A resource without a policy.** The resource is registered, but its list answers 403 for everyone and it is missing from the navigation. A missing policy denies. Register one with `gate.Register(authz.For[*models.Post](PostPolicy{Admins: admins}))`; `make:admin-resource` does it for you.

**Listing a secret column.** `List("id", "email", "api_token")` stops the boot with `admin: resource accounts: sensitive column "api_token" cannot be listed`. Leave it out of the list.

**A schema key with no column.** `"titel": z.String()` stops the boot with `schema key "titel" matches no column of Posts`. The key must match a column name.

**Expecting an unverified admin to get in.** An address in `ADMIN_EMAILS` whose account is not verified answers 403. Verify the email first.
