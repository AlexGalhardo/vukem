Billing is how your app takes money: a visitor picks a plan, pays, and gets access while the subscription stays paid. Vukem talks to [Stripe](https://docs.stripe.com) for the payment itself, so card numbers never touch your server. You get two layers: the `contrib/stripe` module (a Stripe API client and webhook receiver), and the `vukem install:billing` command, which writes a complete subscription system into your project.

You will learn:

- how a Stripe subscription flows from the "Subscribe" button to your database
- how to add plans, Checkout and the Billing Portal with `vukem install:billing`
- how webhooks keep subscriptions in sync, and why the success page grants nothing
- how to protect routes with `Subscribed()` and `OnPlan("pro")`
- how to call any Stripe endpoint with retries, idempotency keys and typed errors
- how to pay sellers in a marketplace with Stripe Connect

## The idea

Think of a gym membership. The front desk (your app) never handles cash. It sends you to the bank counter (Stripe Checkout), and the bank later phones the desk to say "Ana paid" or "Ana's card bounced" (a webhook). The desk only trusts the phone call, never the customer saying "I paid, let me in".

| Stripe word | What it is | Where Vukem keeps it |
| --- | --- | --- |
| Customer (`cus_…`) | The person who pays | `users.stripe_customer_id` |
| Price (`price_…`) | An amount per period, such as $9/month | `STRIPE_PRICE_BASIC`, `STRIPE_PRICE_PRO` |
| <Term tip="A page hosted by Stripe where the customer enters payment details.">Checkout Session</Term> (`cs_…`) | One visit to Stripe's payment page | not stored; created per click |
| Subscription (`sub_…`) | The ongoing agreement and its status | the `subscriptions` table |
| Billing Portal | Stripe's page to change plan, update the card or cancel | not stored; created per click |
| <Term tip="An HTTP request that Stripe sends to your app when something happens.">Webhook</Term> event (`evt_…`) | Stripe telling you something changed | processed once, then forgotten |

The running example on this page is a writing app with two plans, **Basic** and **Pro**. Pro unlocks PDF exports.

## What install:billing adds

Like every `install:*` command, the code is copied into your project. It is yours to read and change. It works for the HTMX starter and the Inertia starters (React, Vue, Svelte); only the billing page differs.

| `database/migrations/<ts>_add_billing_tables.go` | `users.stripe_customer_id` (nullable, unique) and the `subscriptions` table |

Later releases install with `go get github.com/AlexGalhardo/vukem/contrib/stripe@vX.Y.Z` (the tags are listed on [pkg.go.dev](https://pkg.go.dev/github.com/AlexGalhardo/vukem/contrib/stripe?tab=versions)). Pass `--force` to overwrite files that already exist.

### The subscriptions table

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | id | Primary key |
| `user_id` | foreign key | The owner; rows are deleted with the user |
| `stripe_subscription_id` | string, unique | `sub_…` |
| `status` | string | Stripe's status: `active`, `trialing`, `past_due`, `canceled`, `unpaid`, `paused`, … |
| `price_id` | string | The `price_…` of the first item, which maps back to a plan |
| `current_period_end` | timestamp, nullable | When the paid period ends (UTC) |
| `cancel_at_period_end` | boolean | The customer cancelled, but keeps access until the period ends |
| `created_at`, `updated_at` | timestamps | |

`Subscription.Valid()` is true only for `active` and `trialing`. Every other status, including `past_due`, denies access.

### Adding a plan

Add an entry to `plans()` and set `STRIPE_PRICE_<NAME>` (the name in upper case):

```go title="config/billing.go"
func plans() []Plan {
	return []Plan{
		{Name: "basic", Label: "Basic"},
		{Name: "pro", Label: "Pro"},
		// Needs STRIPE_PRICE_TEAM=price_...
		{Name: "team", Label: "Team"},
	}
}
```

`Name` appears in URLs (`/billing/checkout/team`) and in `OnPlan`. `Label` is shown on the page.

## The subscription flow, step by step

These are the routes `routes/billing.go` registers. The three pages require a signed-in user with a verified email (`auth.Required` and `auth.Verified`).

| Route | Name | Behaviour |
| --- | --- | --- |
| `GET /billing` | `billing.show` | Shows the plans and the current subscription |
| `POST /billing/checkout/{plan}` | `billing.checkout` | Sends the user to Stripe Checkout |
| `POST /billing/portal` | `billing.portal` | Sends the user to the Billing Portal (return URL `/billing`) |
| `POST /stripe/webhook` | none | Receives Stripe events; not listed by `vukem route:list` |

When Ana clicks "Subscribe to Pro":

<Steps>
<Step title="Checkout is created">
`POST /billing/checkout/pro` looks up the plan. An unknown plan, or one without a price, answers 404. If Ana already has a valid subscription, she is sent back to `/billing` with "You already have a subscription: manage it in the billing portal." (a 409 for JSON clients): plan changes happen in the portal.
</Step>
<Step title="The customer is created once">
On her first checkout, `Customer` creates a Stripe customer with her email, name and `metadata[user_id]`, and saves the id in `users.stripe_customer_id`. If two clicks race, the first saved id wins and the other is not used.
</Step>
<Step title="Ana pays on Stripe">
The Checkout Session uses `mode=subscription`, `client_reference_id` = her user id, `subscription_data[metadata][user_id]`, a success URL of `APP_URL/billing?checkout=success` and a cancel URL of `APP_URL/billing`. The app answers with a redirect to Stripe.
</Step>
<Step title="Stripe sends webhooks">
Stripe posts `checkout.session.completed` and `customer.subscription.created` to `/stripe/webhook`. The app stores the subscription.
</Step>
<Step title="Ana comes back">
`/billing?checkout=success` shows a thank-you note. It grants nothing: access starts when the webhook arrives.
</Step>
</Steps>

How the redirect leaves the app depends on the client:

| Client | Response |
| --- | --- |
| A classic form post | `303 See Other` with `Location` |
| An Inertia visit | `409` with `X-Inertia-Location` (`inertia.Location`) |
| An htmx request | `HX-Redirect` header and `204 No Content` |
| A JSON client | `200` with `{"url": "https://checkout.stripe.com/…"}` |

The portal route works the same way. A user who never checked out has no customer: she is sent back with "You have no billing account yet: choose a plan first."

Checkout never passes `payment_method_types`. Stripe then offers every payment method you enabled in the Dashboard.

## Webhooks keep subscriptions in sync

A subscription changes many times without your app doing anything: a renewal is paid, a card fails, the customer cancels in the portal. Stripe tells you each time with a webhook. `routes/billing.go` registers `b.HandleWebhook` with `events.Listen`, which is synchronous: if it fails, the endpoint answers 500 and Stripe delivers the event again.

| Event | What `HandleWebhook` does |
| --- | --- |
| `checkout.session.completed`, `checkout.session.async_payment_succeeded` | Ignores sessions not in `subscription` mode. Links the customer to the `client_reference_id` user, then syncs the subscription only when `payment_status` is `paid` or `no_payment_required` |
| `customer.subscription.created`, `.updated`, `.deleted`, `.paused`, `.resumed` | Syncs the subscription |
| `invoice.paid`, `invoice.payment_failed` | Syncs the invoice's subscription (`parent.subscription_details.subscription`, or `subscription` on API versions before 2025-03-31) |
| anything else | Ignored (acknowledged with 200) |

Under the hood:

- **Linking is safe.** The customer is saved on the user only when that user has no customer yet and no other user owns that customer. A forged or replayed session can never move someone else's customer.
- **Delayed payments wait.** Bank debits complete as `unpaid`. Access starts with `checkout.session.async_payment_succeeded`.
- **Every sync re-reads Stripe.** `SyncSubscription` fetches the subscription with `GetSubscription` instead of trusting the event body, because events can arrive out of order and only the latest state counts. It then updates the row by `stripe_subscription_id` or inserts it, in a transaction.
- **Unknown customers are skipped.** A subscription whose customer matches no user is logged ("stripe subscription of an unknown customer") and acknowledged.
- **Duplicates are dropped.** Each event id is processed once. The ids live in the app cache, so use a shared store (`CACHE_STORE=database` or Redis) when several instances run.

In the Stripe Dashboard (Developers → Webhooks), point an endpoint at `https://example.com/stripe/webhook` and subscribe it to the events in the table.

## Protecting routes

`Subscribed()` lets through users with a valid subscription. `OnPlan(plans...)` also requires one of the named plans. Put them after `auth.Required`:

```go title="routes/web.go"
b, err := billing.New(app)
if err != nil {
	return err
}

r.Get("/documents", documents).
	Use(auth.Required(acc.Web), b.Subscribed())
r.Get("/documents/{id}/pdf", exportPDF).
	Use(auth.Required(acc.Web), b.OnPlan("pro"))
```

Everyone else is redirected to `/billing` with the flash "Choose a plan to continue.", or gets `402 Payment Required` problem+json ("A subscription is required.") when the client wants JSON.

The middleware fails closed: a request with no signed-in user, a plan name that does not exist or has no price, and a database error all deny. A database error is also logged as `billing: load subscription`.

`Current(ctx, userID)` returns the subscription that grants access, else the latest one, so your own handlers can show "Your Pro plan renews on June 1".

## When Stripe is not configured

| Environment | Missing `STRIPE_KEY`, `STRIPE_WEBHOOK_SECRET` or a price |
| --- | --- |
| Production | The app refuses to boot: `billing: STRIPE_KEY is not set` (every missing setting is listed) |
| Development, test | A warning ("billing is not configured"); checkout and portal answer `503` "Billing is not configured." |
| Without `STRIPE_WEBHOOK_SECRET` | `POST /stripe/webhook` answers `503` for every request |

A secret key (`sk_…`) works but logs: `STRIPE_KEY is a secret key: use a restricted key (rk_) with only the billing permissions`.

## The Stripe client

`contrib/stripe` is a separate module built on the Go standard library (no stripe-go). Use it directly for one-off payments, refunds or any endpoint the scaffold does not cover.

```bash
go get github.com/AlexGalhardo/vukem/contrib/stripe@v0.3.0
```

```go title="app/billing/client.go"
package billing

import (
	"github.com/AlexGalhardo/vukem/contrib/stripe"
	"github.com/AlexGalhardo/vukem/config"
)

// NewClient builds the client from a config.Secret, so the key is
// revealed only here.
func NewClient(key config.Secret) (*stripe.Client, error) {
	return stripe.New(key.Reveal(), stripe.WithRetries(2))
}
```

`stripe.New` accepts keys that start with `sk_` or `rk_`; anything else fails with `stripe: key must start with sk_ or rk_`.

| Option | Default | What it does |
| --- | --- | --- |
| `stripe.WithRetries(n)` | `2` | Retries after a 409, 429, 5xx or network error |
| `stripe.WithHTTPClient(h)` | 30-second timeout | The [`*http.Client`](https://pkg.go.dev/net/http#Client) to use |
| `stripe.WithBaseURL(u)` | `https://api.stripe.com` | Another host (tests, proxies) |

### Parameters

`stripe.Params` is a `map[string]any`. Nested maps and slices are encoded the Stripe way, with brackets:

```go
cs, err := sc.CreateCheckoutSession(ctx, stripe.Params{
	"mode":     "payment",
	"customer": "cus_123",
	"line_items": []stripe.Params{
		{"price": "price_pdf_pack", "quantity": 1},
	},
	"success_url": "https://example.com/thanks",
})
```

The client sends `line_items[0][price]=price_pdf_pack&line_items[0][quantity]=1&…`. Any map with string keys (`stripe.Params`, `map[string]any`, `map[string]string`, ...) and any slice (`[]stripe.Params`, `[]map[string]any`, `[]string`, `[]int`, `[]any`, ...) is encoded at any depth, together with strings, booleans, numbers (named types such as `type Cents int64` too; floats without exponent) and `fmt.Stringer` values. A `nil` value, also a nil pointer, is left out. A `[]byte` is sent as a string. Anything else (a struct, a func, a map with non-string keys, NaN or ±Inf, nesting deeper than 32 levels such as a cyclic map) fails the call with `stripe: encode <path>: param "<key>": unsupported type ...` before any request is sent.

API v2 paths (`/v2/...`) send the params as JSON instead; there, a `nil` value becomes JSON `null`.

### What every request does

1. Sends `Authorization: Bearer <key>` and pins `Stripe-Version: 2026-08-26.dahlia` (`stripe.APIVersion`), so a Dashboard upgrade never changes your responses.
2. Gives every POST (and every v2 DELETE) an `Idempotency-Key`. Without your own key, it generates one per call, which protects the client's own retries.
3. Retries on 409, 429, 5xx and network errors, up to `WithRetries` times. It waits `Retry-After` when Stripe sends it, else 0.5 s, 1 s, 2 s… (at most 10 s). `Stripe-Should-Retry: true` or `false` overrides the decision. A cancelled [`context.Context`](https://pkg.go.dev/context) stops the waiting.
4. Reads at most 16 MiB of response and decodes the JSON into the typed result.

A generated key does not survive a crash or a retried queue job. When an operation must never run twice, pass a key tied to your business operation:

```go
// "order-42" ties every retry of this payment together, even across
// processes and job retries.
pi, err := sc.CreatePaymentIntent(ctx, stripe.Params{
	"amount":   1900,
	"currency": "usd",
}, "order-42")
```

`Call` and the Connect methods take `stripe.IdempotencyKey("order-42-transfer")` as an option. Keys longer than 255 bytes, or with spaces or non-ASCII characters, fail with `stripe.ErrInvalidRequestOption` before anything is sent.

### Errors

A Stripe error is a `*stripe.Error` with `Status`, `Type`, `Code`, `DeclineCode`, `Message`, `Param` and `RequestID`. Compare it with [`errors.Is`](https://pkg.go.dev/errors#Is):

```go
pi, err := sc.CreatePaymentIntent(ctx, params, "order-42")
if errors.Is(err, stripe.ErrCardDeclined) {
	var se *stripe.Error
	errors.As(err, &se)
	// se.DeclineCode is "insufficient_funds", se.RequestID "req_..."
	return showDeclined(c, se.Message)
}
```

```text
stripe: 402 card_error (card_declined): Your card was declined.
```

| Sentinel | Matches |
| --- | --- |
| `stripe.ErrCardDeclined` | `card_error` with code `card_declined` |
| `stripe.ErrInvalid` | any `invalid_request_error` |
| `stripe.ErrNotFound` | an `invalid_request_error` with status 404 (v1 `resource_missing`, v2 `not_found`) |
| `stripe.ErrRateLimited` | `rate_limit_error` (and v2 `rate_limit`) |
| `stripe.ErrAuth` | `authentication_error` |
| `stripe.ErrInvalidRequestOption` | a bad option, path or id, caught before the request |

When the type is missing or unknown (some v2 errors), it is derived from the status: 400 and 404 become `invalid_request_error`, 401 `authentication_error`, 402 `card_error`, 429 `rate_limit_error`.

### Resources

| Area | Methods |
| --- | --- |
| Customers | `CreateCustomer`, `GetCustomer`, `UpdateCustomer` |
| Checkout | `CreateCheckoutSession`, `GetCheckoutSession` |
| Subscriptions | `GetSubscription`, `UpdateSubscription` (for example `cancel_at_period_end`), `CancelSubscription` (immediately) |
| Billing Portal | `CreatePortalSession(ctx, customer, returnURL)` |
| Payments | `CreatePaymentIntent(ctx, params, idemKey)`, `GetPaymentIntent` |
| Refunds | `CreateRefund`, `GetRefund` (`re_…` or `pyr_…`) |
| Connect | see [Stripe Connect](#stripe-connect-marketplaces) |
| Anything else | `Call(ctx, method, path, params, &out, opts...)` |

`Call` decodes into `out` (a struct, a `*json.RawMessage`, or `nil` to discard). The path must start with `/v1/` or `/v2/` and must not contain `..`, `%2e`, `?`, `#`, `\`, spaces or control characters:

```go
var balance json.RawMessage
err := sc.Call(ctx, http.MethodGet, "/v1/balance", nil, &balance)
```

When you pass `expand[]`, fields such as `customer`, `subscription` and `payment_intent` still decode as the id string. Decode into your own struct to read the expanded object. `List[T]` holds a page of a list endpoint (`Data`, `HasMore`).

The client never prints the key: `fmt.Println(sc)` shows `stripe.Client{key: rk_test_…1234}`.

## Receiving webhooks yourself

The scaffold wires this for you. For your own endpoint, `stripe.WebhookHandler` returns an [`http.Handler`](https://pkg.go.dev/net/http#Handler):

```go title="routes/stripe.go"
c, err := app.Cache()
if err != nil {
	return err
}

hook, err := stripe.WebhookHandler(stripe.WebhookConfig{
	Secret: cfg.WebhookSecret.Reveal(),
	Store:  c.Store(),
	Bus:    app.Events,
	Log:    app.Log,
})
if err != nil {
	return err
}

events.Listen(app.Events,
	func(ctx context.Context, r stripe.Received) error {
		if r.Event.Type != "checkout.session.completed" {
			return nil
		}
		cs, err := stripe.Decode[stripe.CheckoutSession](r.Event)
		if err != nil {
			return err
		}
		return fulfil(ctx, cs)
	})
```

Mount it ahead of the session and CSRF middleware, as the scaffold does with `r.UseServer`. Stripe is a server, not a browser: it sends no cookies, and the signature is its authentication.

| Field | Default | What it does |
| --- | --- | --- |
| `Secret` | required (or `Secrets`) | The endpoint signing secret (`whsec_…`) |
| `Secrets` | none | More accepted secrets, such as the Connect endpoint's |
| `Store` | required | A [`cache.Store`](/docs/digging-deeper/cache) that remembers event ids |
| `Bus` | required | Where `stripe.Received` is dispatched (`app.Events`) |
| `Tolerance` | `5m` (`stripe.DefaultTolerance`) | How old (or how far in the future) a signature may be |
| `MaxBody` | 1 MiB | Larger bodies are refused |
| `Log` | `slog.Default()` | Logs rejected webhooks and failed listeners |
| `Now` | `time.Now` | The clock (tests) |

Missing fields fail with `stripe: webhook needs Secret (or Secrets), Store and Bus`; an empty string in `Secrets` fails with `stripe: webhook Secrets has an empty secret`.

What happens for each request:

| Situation | Response |
| --- | --- |
| Not a POST | `405` |
| Body over `MaxBody` | `413` |
| Signature missing, forged, for another secret or outside the tolerance | `400` "invalid signature", logged as `stripe.webhook_rejected` |
| The store fails | `503`, so Stripe retries |
| The event was already processed | `200`, listeners not called |
| The same event is being processed right now | `409`, so Stripe retries later |
| A listener returns an error | the claim is released, `500`, Stripe redelivers |
| Success | `200`; the id is remembered for 30 days |

The signature check follows [Stripe's scheme](https://docs.stripe.com/webhooks#verify-manually): an HMAC-SHA256 of `t.payload` compared in constant time, accepting any of several `v1` signatures (Stripe sends more than one while you roll a secret). `stripe.ConstructEvent(payload, header, secret, tolerance, now)` does only the check, and returns `stripe.ErrSignature` on failure.

Register listeners with `events.Listen` or `events.On`, not the async variants: an async listener's error never reaches Stripe, so a failed event would not be redelivered.

## Stripe Connect (marketplaces)

A marketplace takes the buyer's payment and pays part of it to a seller. Stripe calls the seller a **connected account**. The client covers [Accounts v2](https://docs.stripe.com/connect/accounts-v2), Stripe's current API for connected accounts, plus the v1 transfers, refunds and reversals that pay sellers and take money back.

<Steps>
<Step title="Create the seller's account">

```go title="app/sellers/onboard.go"
caps := stripe.Params{
	"stripe_balance": stripe.Params{
		"stripe_transfers": stripe.Params{"requested": true},
	},
}
acct, err := sc.CreateAccountV2(ctx, stripe.Params{
	"contact_email": seller.Email,
	"dashboard":     "express",
	"identity":      stripe.Params{"country": "br"},
	"defaults": stripe.Params{
		"responsibilities": stripe.Params{
			"fees_collector":   "application",
			"losses_collector": "application",
		},
	},
	"configuration": stripe.Params{
		"recipient": stripe.Params{"capabilities": caps},
	},
	"include": []string{"configuration.recipient", "requirements"},
}, stripe.IdempotencyKey("seller-7-account"))
```

The idempotency key is tied to the seller, so a retried signup never creates two accounts.

</Step>
<Step title="Send the seller to onboarding">

```go title="app/sellers/onboard.go"
link, err := sc.CreateAccountLinkV2(ctx, stripe.Params{
	"account": acct.ID,
	"use_case": stripe.Params{
		"type": "account_onboarding",
		"account_onboarding": stripe.Params{
			"configurations": []string{"recipient"},
			"refresh_url":    appURL + "/seller/onboarding",
			"return_url":     appURL + "/seller",
		},
	},
})
// Redirect only the signed-in seller to link.URL.
```

A link is single-use and short-lived: `refresh_url` should create a new one. `configurations` is required on the pinned API version.

</Step>
<Step title="Check that the seller can be paid">

```go
acct, err = sc.GetAccountV2(ctx, acct.ID,
	[]string{"configuration.recipient"})
rcp := acct.Configuration.Recipient
ready := rcp != nil &&
	rcp.Capabilities.StripeBalance.StripeTransfers.Status == "active"
```

v2 returns a configuration only when you `include` it, so a `nil` field means "not included". Statuses are `active`, `pending`, `restricted`, `rejected` and `unsupported` (empty when never requested); `StatusDetails` says what resolves them.

</Step>
<Step title="Pay the seller, and claw back on refunds">

```go
tr, err := sc.CreateTransfer(ctx, stripe.Params{
	"amount":         9000,
	"currency":       "brl",
	"destination":    acct.ID,
	"transfer_group": "order-42",
}, stripe.IdempotencyKey("order-42-transfer"))

// On a refund: reverse the seller's share, then refund the buyer.
_, err = sc.CreateTransferReversal(ctx, tr.ID,
	stripe.Params{"amount": 9000},
	stripe.IdempotencyKey("order-42-reversal"))
_, err = sc.CreateRefund(ctx, stripe.Params{
	"payment_intent": piID,
	"amount":         10000,
}, stripe.IdempotencyKey("order-42-refund"))
```

</Step>
</Steps>

More Connect details:

- `UpdateAccountV2` changes an account; a `nil` metadata value removes that key. `Call` reaches any other `/v2/...` endpoint.
- `CreateLoginLink(ctx, "acct_…")` opens the seller's Express dashboard. `GetTransfer`, `GetRefund` and `GetTransferReversal` read back what you created; ids are checked (`tr_…`, `trr_…`, `re_…`) before the request.
- The v1 methods `CreateAccount`, `GetAccount` and `CreateAccountLink` still work for platforms that use them; Stripe still needs v1 for OAuth, Treasury and card issuing. A v2 account id works with every v1 endpoint.
- Destination charges are plain params: `application_fee_amount` and `transfer_data[destination]` on a PaymentIntent, `reverse_transfer` and `refund_application_fee` on a refund.
- `sc.ForAccount("acct_…")` returns a copy of the client, and `stripe.OnAccount("acct_…")` scopes one request, to act **as** the seller (direct charges and their refunds). The platform-only methods (accounts, account and login links, transfers and reversals) refuse that scope with `stripe.ErrInvalidRequestOption`, so they never run on the wrong account.
- Connect events are signed with a different secret than platform events, even on the same URL. Add it to `WebhookConfig.Secrets` and read the seller from `Event.Account` (empty for platform events).

The [Marketplace showcase app](/docs/showcase#marketplace-inertia-and-react) uses Connect in production.

## Configuration

| Name | Type | Default | What it does |
| --- | --- | --- | --- |
| `STRIPE_KEY` | env, secret | empty | A restricted key (`rk_…`) with write access to Customers, Checkout Sessions and Customer portal, and read access to Subscriptions |
| `STRIPE_WEBHOOK_SECRET` | env, secret | empty | The endpoint signing secret (`whsec_…`) |
| `STRIPE_PRICE_<PLAN>` | env | empty | A recurring price id (`price_…`) per plan in `config/billing.go` |
| `APP_URL` | env | — | Base of the Checkout success and cancel URLs and the portal return URL |
| `CACHE_STORE` | env | memory | Where processed event ids live; use `database` or Redis with several instances |
| `STRIPE_API_BASE` | env | empty | Points the client at a fake API; read only when the app runs as a test |

`STRIPE_KEY` and `STRIPE_WEBHOOK_SECRET` are read as `config.Secret`, so they are redacted when printed.

## Security

- **Access comes from webhooks only.** The success page grants nothing, so a user who types `?checkout=success` gets nothing.
- **Webhooks are signed and fresh.** Forged, unsigned and replayed (older than 5 minutes) requests answer 400; each event runs once.
- **The webhook skips CSRF on purpose** and stays authenticated by its signature. Vukem checks this wiring in `TestSecurity_A08_BillingWebhookOutsideCSRFButSigned`.
- **Least privilege.** Use a restricted key; the scaffold warns on a secret key.
- **The key goes only to Stripe.** `STRIPE_API_BASE` is ignored outside tests, and the client never prints the key.
- **Fail closed.** Missing settings stop production; database errors deny access.

See [docs/security.md](https://github.com/AlexGalhardo/vukem/blob/main/docs/security.md) and [Stripe's integration security guide](https://docs.stripe.com/security/guide).

## Testing

The generated tests boot the app against an [`httptest`](https://pkg.go.dev/net/http/httptest) fake of the Stripe API, and sign webhooks with `stripe.SignForTest`:

```go title="tests/billing_test.go"
app := vukemtest.New(t, bootstrap.New, vukemtest.Options{
	Env: map[string]string{
		"STRIPE_KEY":            "rk_test_fake",
		"STRIPE_WEBHOOK_SECRET": "whsec_test",
		"STRIPE_API_BASE":       fake.URL,
		"STRIPE_PRICE_BASIC":    "price_basic",
		"STRIPE_PRICE_PRO":      "price_pro",
	},
})

payload, _ := json.Marshal(map[string]any{
	"id":      "evt_1",
	"type":    "customer.subscription.updated",
	"created": time.Now().Unix(),
	"data": map[string]any{
		"object": map[string]any{"id": "sub_1"},
	},
})
sig := stripe.SignForTest(payload, "whsec_test", time.Now())

// The fake serves sub_1 for a customer already linked to a user.

app.Client(t).
	WithHeader("Stripe-Signature", sig).
	Do(http.MethodPost, billing.WebhookPath,
		bytes.NewReader(payload), "application/json").
	AssertOK()

vukemtest.AssertDatabaseHas(t, app, "subscriptions",
	map[string]any{"stripe_subscription_id": "sub_1"})
```

They cover checkout (the customer is created once, the session parameters, the success page granting nothing), the webhook sync (unpaid, async success, `past_due`, cancellation), a duplicate event processed once, forged, replayed and unsigned webhooks rejected with 400, the middleware, the portal and an unconfigured app answering 503. Run them with `go test ./tests/...`.

## Common mistakes

**Granting access on the success page.** Wrong: setting `is_pro = true` in the handler of `/billing?checkout=success`. Anyone can open that URL. Right: grant access in a webhook listener, as `HandleWebhook` does.

**Routing the webhook like a page.** Wrong: `r.Post("/stripe/webhook", h)` after `DefaultMiddleware`. The request then goes through the session and CSRF middleware, which are built for browsers, and Stripe gets a session cookie it never sends back. Right: `r.UseServer(b.Webhook())` as the scaffold does, or list the path in `MiddlewareOptions.CSRFBypass` and `SessionBypass`.

**A wrong signing secret.** The secret of `stripe listen` differs from the Dashboard endpoint's. With the wrong one, every delivery logs `stripe webhook rejected` with `stripe: invalid webhook signature: no matching signature`, and Stripe shows 400s.

**Memory cache with several instances.** Each instance has its own memory, so a redelivered event may run twice. Right: `CACHE_STORE=database` or Redis.

**Passing `payment_method_types`.** It overrides the Dashboard settings and hides payment methods your customers want. Leave it out.
