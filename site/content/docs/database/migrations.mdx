---

Your tables change as the app grows: today posts have a title and a body, next month they need a slug, later a `published_at` date. A **migration** is one such change, written in Go and stored in the project, so every copy of the app (your laptop, a teammate's, CI, production) builds the exact same schema by running `vukem migrate`.

You will learn:

- how `vukem make:migration` creates a migration and registers it;
- how to create and change tables with the schema builder, and what SQL each method produces per database;
- how foreign keys, indexes, partial indexes and CHECK constraints work;
- what `migrate`, `rollback`, `reset`, `fresh` and `status` do, and how batches and checksums keep you safe;
- how to test migrations and avoid the classic mistakes.

The running example is the blog: tables for users, posts, comments, tags and the `post_tag` pivot.

## The idea

A migration is like a numbered page in a building's renovation log: "page 1: build the walls", "page 2: add a window". Anyone who reads the log from the first page builds the same house. The database keeps a bookmark (the `migrations` table) saying which pages it already applied, so `vukem migrate` only applies the new ones.

Each migration has three parts:

| Field | What it is |
| --- | --- |
| `ID` | A unique, sortable name: `20261016184615_create_posts_table`. The timestamp prefix decides the order |
| `Up` | The change: create a table, add a column |
| `Down` | The undo: drop that table, remove that column. Optional, but `rollback` needs it |

`Up` and `Down` receive a `*schema.Schema`, the **schema builder**: Go methods such as `s.Create("posts", ...)` that generate the right SQL for SQLite, PostgreSQL or MySQL. You write the migration once; the dialect decides the column types.

There is no hidden registration (no `init()` functions): every migration is listed in one function, `migrations.All()`, which `bootstrap/app.go` passes to the app.

## Quick start

<Steps>
<Step title="1. Generate the migration">

```bash
vukem make:migration create_tags_table
```

The command writes `database/migrations/20261017090000_create_tags_table.go` (the timestamp is the current UTC time) and appends it to `database/migrations/registry.go`.

</Step>
<Step title="2. Describe the table">

```go title="database/migrations/20261017090000_create_tags_table.go"
package migrations

import "github.com/AlexGalhardo/vukem/schema"

func m20261017090000CreateTagsTable() schema.Migration {
	return schema.Migration{
		ID: "20261017090000_create_tags_table",
		Up: func(s *schema.Schema) error {
			return s.Create("tags", func(t *schema.Table) {
				t.ID()
				t.String("name", 50).Unique()
				t.Timestamps()
			})
		},
		Down: func(s *schema.Schema) error {
			return s.DropIfExists("tags")
		},
	}
}
```

</Step>
<Step title="3. Run it">

```bash
vukem migrate
```

```text
Migrated: 20261017090000_create_tags_table
```

Running it again prints `Nothing to migrate.`

</Step>
<Step title="4. Check the state">

```bash
vukem migrate:status
```

```text
MIGRATION                                STATUS  BATCH
20261016184613_create_users_table        Ran     1
20261016184615_create_posts_table        Ran     1
20261017090000_create_tags_table         Ran     2
```

</Step>
</Steps>

## Creating migrations

`vukem make:migration <name>` turns the name into snake_case and picks a stub from its shape:

| Name pattern | Stub | Example |
| --- | --- | --- |
| `create_<table>_table` | `s.Create` with `t.ID()` and `t.Timestamps()`; `Down` drops the table | `create_comments_table` |
| `<anything>_to_<table>_table`, `_from_`, `_in_`, `_on_` | `s.Table` in `Up` and `Down`, both empty | `add_slug_to_posts_table` |
| `alter_<table>_table`, `change_...`, `update_...` | the same alter stub | `alter_posts_table` |
| anything else | `Up` and `Down` that return `nil` | `backfill_post_slugs` |

`--force` overwrites an existing file. `vukem make:model Post -m` also creates the `create_posts_table` migration.

The generated function name is `m` + timestamp + the name in PascalCase, and the registry gets one more line:

```go title="database/migrations/registry.go"
package migrations

import "github.com/AlexGalhardo/vukem/schema"

// All lists the migrations in order; vukem make:migration appends here.
func All() []schema.Migration {
	return []schema.Migration{
		m20261016184613CreateUsersTable(),
		m20261016184615CreatePostsTable(),
		m20261016184616CreateCommentsTable(),
		m20261017090000CreateTagsTable(),
	}
}
```

```go title="bootstrap/app.go" nocompile
vukem.WithMigrations(migrations.All()),
```

`schema.NewMigrator` checks the list when the app builds its migrator: every migration needs an `ID` and an `Up` (`schema: migration "" needs an ID and Up`), IDs must be unique (`schema: duplicate migration "..."`), and the list is sorted by ID, so the order in `All()` does not matter.

## Creating tables

Here are the blog's tables. Each is its own migration; only the `Up` bodies are shown.

```go title="database/migrations/20261016184613_create_users_table.go"
return s.Create("users", func(t *schema.Table) {
	t.ID()
	t.String("name")
	t.String("email").Unique()
	t.String("password")
	t.Timestamp("email_verified_at").Nullable()
	t.Timestamps()
})
```

```go title="database/migrations/20261016184615_create_posts_table.go"
return s.Create("posts", func(t *schema.Table) {
	t.ID()
	t.ForeignID("user_id").Constrained().CascadeOnDelete()
	t.String("title")
	t.String("slug").Unique()
	t.Text("body")
	t.Integer("views").Default(0)
	t.Integer("comments_count").Default(0)
	t.Timestamp("published_at").Nullable()
	t.JSON("meta").Nullable()
	t.Timestamps()
	t.SoftDeletes()
	t.Index("user_id", "published_at")
})
```

```go title="database/migrations/20261016184616_create_comments_table.go"
return s.Create("comments", func(t *schema.Table) {
	t.ID()
	t.ForeignID("post_id").Constrained().CascadeOnDelete()
	t.ForeignID("user_id").Constrained().CascadeOnDelete()
	t.Text("body")
	t.Timestamps()
})
```

```go title="database/migrations/20261017090100_create_post_tag_table.go"
return s.Create("post_tag", func(t *schema.Table) {
	t.ForeignID("post_id").Constrained().CascadeOnDelete()
	t.ForeignID("tag_id").Constrained().CascadeOnDelete()
	t.UniqueIndex("post_id", "tag_id")
})
```

Columns are **NOT NULL** unless you add `.Nullable()`. `Create` runs one `CREATE TABLE` and then one `CREATE INDEX` per index.

### Column types

| Method | SQLite | PostgreSQL | MySQL / MariaDB |
| --- | --- | --- | --- |
| `ID()` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BIGINT AUTO_INCREMENT PRIMARY KEY` |
| `String(name, len?)` | `VARCHAR(len)`, 255 by default | same | same |
| `Text(name)` | `TEXT` | `TEXT` | `LONGTEXT` |
| `SmallInteger(name)` | `SMALLINT` | `SMALLINT` | `SMALLINT` |
| `Integer(name)` | `INTEGER` | `INTEGER` | `INT` |
| `BigInteger(name)` | `INTEGER` | `BIGINT` | `BIGINT` |
| `ForeignID(name)` | `INTEGER` | `BIGINT` | `BIGINT` |
| `Boolean(name)` | `BOOLEAN` | `BOOLEAN` | `BOOLEAN` |
| `Decimal(name, p, s)` | `NUMERIC(p, s)` | `NUMERIC(p, s)` | `DECIMAL(p, s)` |
| `Float(name)` | `REAL` | `DOUBLE PRECISION` | `DOUBLE` |
| `Date(name)` | `DATE` | `DATE` | `DATE` |
| `Timestamp(name)` | `TIMESTAMP` | `TIMESTAMPTZ` | `DATETIME(6)` |
| `Timestamps()` | nullable `created_at`, `updated_at` | same | same |
| `SoftDeletes()` | nullable `deleted_at` timestamp | same | same |
| `JSON(name)` | `TEXT` | `JSONB` | `JSON` |
| `UUID(name)` | `TEXT` | `UUID` | `CHAR(36)` |
| `ULID(name)` | `CHAR(26)` | `CHAR(26)` | `CHAR(26)` |
| `Binary(name)` | `BLOB` | `BYTEA` | `LONGBLOB` |
| `Enum(name, values...)` | `TEXT` + `CHECK (name IN (...))` | same | `VARCHAR(255)` + `CHECK` |

`Enum` without values fails with `schema: enum status needs values`. MySQL stores timestamps as `DATETIME(6)`: microseconds, no year-2038 limit, no session time-zone conversion.

### Column modifiers

Every column method returns a `*schema.Column`; modifiers chain:

| Modifier | Effect |
| --- | --- |
| `Nullable()` | Allows `NULL` |
| `Default(v)` | A default value: a Go `string`, `bool`, integer or float becomes a SQL literal (strings are quoted and escaped); `schema.Expr("CURRENT_TIMESTAMP")` is raw SQL |
| `Unique()` | An inline `UNIQUE` constraint |
| `Index()` | A single-column index named `<table>_<column>_index` |
| `Constrained(table?)` | A foreign key to `table(id)` |
| `CascadeOnDelete()` | Deleting the parent deletes this row |
| `NullOnDelete()` | Deleting the parent sets this column to `NULL` (and makes it nullable) |
| `RestrictOnDelete()` | Deleting a parent that is still referenced fails |
| `Primary()` | Makes this column the primary key, e.g. `t.UUID("id").Primary()` (see [Primary keys](#primary-keys)) |
| `StoredAs(expr)` | A stored generated column: `GENERATED ALWAYS AS (expr) STORED` (see [Generated columns](#generated-columns)) |

On MySQL, defaults on `Text`, `JSON` and `Binary` columns become expression defaults (`DEFAULT ('x')`), the only form MySQL 8 accepts there, and `schema.Expr("CURRENT_TIMESTAMP")` on a timestamp becomes `CURRENT_TIMESTAMP(6)` to match `DATETIME(6)`.

### Foreign keys

A <Term tip="A column that stores another table's id; the database refuses values that point nowhere.">foreign key</Term> keeps the data honest: a comment cannot point to a post that does not exist. `ForeignID("post_id")` adds the column; `Constrained()` adds the constraint:

```go
t.ForeignID("post_id").Constrained().CascadeOnDelete()
// post_id BIGINT NOT NULL,
// FOREIGN KEY (post_id) REFERENCES posts (id) ON DELETE CASCADE
```

- Without an argument, `Constrained()` takes the column name without `_id` and pluralises it the way the ORM names model tables: `post_id` → `posts`, `category_id` → `categories`, `address_id` → `addresses`. When the table has another name, pass it: `Constrained("people")`.
- An `ON DELETE` action before `Constrained()` fails: `schema: post_id: call Constrained() before an ON DELETE action`.
- SQLite enforces foreign keys because Vukem turns on `PRAGMA foreign_keys` for every connection.

### Indexes

An <Term tip="A sorted copy of one or more columns that lets the database find rows without reading the whole table.">index</Term> makes lookups fast; a unique index also forbids duplicates.

```go
t.Index("user_id", "published_at")  // posts_user_id_published_at_index
t.UniqueIndex("post_id", "tag_id")  // post_tag_post_id_tag_id_unique
```

Names are derived as `<table>_<col1>_<col2>_index` or `_unique`; `t.DropIndex(name)` takes that name.

#### Partial indexes

A partial index covers only the rows matching an expression. On the blog, a slug must be unique among live posts only, so a deleted post frees its slug:

```go
t.String("slug")
t.UniqueIndex("slug").Where("deleted_at IS NULL")
// CREATE UNIQUE INDEX posts_slug_unique ON posts (slug)
//   WHERE deleted_at IS NULL
```

`.Where(expr)` works in `Create` and `s.Table` on PostgreSQL and SQLite. MySQL and MariaDB have no partial indexes, so there the migration fails instead of creating a full index that would reject valid rows. An empty expression fails too. The expression is raw SQL that you write, never user input.

#### Index methods (PostgreSQL)

PostgreSQL indexes are B-trees unless you pick another method. A `JSON` column is `JSONB` on PostgreSQL, and a GIN index makes containment queries such as `tags @> '["rpg"]'` fast:

```go
t.JSON("tags")
t.Index("tags").Using("gin")
// CREATE INDEX items_tags_index ON items USING gin (tags)
```

`Using` accepts `btree`, `hash`, `gin`, `gist`, `brin` and `spgist`, and combines with `Where`. Any other name fails the migration, and so does `Using` on SQLite, MySQL or MariaDB, which have no such methods. For an operator class (`USING gin (tags jsonb_path_ops)`) or an index on an expression, write the statement with `s.Raw`.

### CHECK constraints

A named CHECK constraint keeps a rule in the database itself, whatever code writes the row:

```go
s.Create("posts", func(t *schema.Table) {
	// ...
	t.Check("posts_views_check", "views >= 0")
})
```

- In `Create`, `t.Check(name, expr)` emits `CONSTRAINT name CHECK (expr)` on every dialect.
- In `s.Table`, it emits `ALTER TABLE ... ADD CONSTRAINT` on PostgreSQL and MySQL. SQLite cannot add constraints to an existing table, so the migration fails with `schema: sqlite cannot add a check to existing table posts; add it in Create` instead of silently skipping the rule.
- `t.DropCheck(name)` is alter-only, unsupported on SQLite, and emits `DROP CONSTRAINT` (MySQL 8.0.19+ or MariaDB 10.2+).
- MySQL scopes constraint names per database, so prefix them with the table name.
- The expression is raw SQL that you write, and should use syntax every target dialect understands.

### Primary keys

`t.ID()` is an auto-increment primary key. For any other key, declare the columns and name them with `t.Primary(cols...)`, or call `Primary()` on a single column:

```go
s.Create("items", func(t *schema.Table) {
	t.UUID("id").Primary() // PRIMARY KEY ("id")
	t.String("title")
})

s.Create("ratings", func(t *schema.Table) {
	t.ForeignID("user_id").Constrained().CascadeOnDelete()
	t.UUID("item_id").Constrained("items")
	t.SmallInteger("score")
	t.Primary("user_id", "item_id") // PRIMARY KEY ("user_id", "item_id")
})
```

- The key is a table constraint, `PRIMARY KEY (...)`, emitted after the columns on every dialect.
- `Primary` is `Create` only, takes at least one declared column and cannot be combined with `ID()` or called twice; each mistake fails the migration before any SQL runs.
- A model for a composite-key table implements `orm.CompositeKeyer`; see [Composite primary keys](/docs/database/orm#composite-primary-keys).

### Generated columns

`StoredAs(expr)` makes the database compute a column from the others and store it:

```go
s.Create("ratings", func(t *schema.Table) {
	// ...
	t.SmallInteger("story")
	t.SmallInteger("art")
	t.Decimal("overall", 4, 2).StoredAs("(story + art) / 2.0")
})
```

- It emits `GENERATED ALWAYS AS (expr) STORED` on SQLite, PostgreSQL and MySQL. The expression is raw SQL that you write, never user input.
- A generated column cannot have a `Default`, and SQLite cannot add a stored generated column to an existing table, so both fail the migration.
- The database rejects writes to the column, so tag the model field `orm:"readonly"`: the ORM reads it but never writes it. See [Naming conventions](/docs/database/orm#naming-conventions).

## Changing tables

`s.Table(name, fn)` alters an existing table. Generate the migration with a name that matches the alter pattern:

```bash
vukem make:migration add_reading_minutes_to_posts_table
```

```go title="database/migrations/20261018100000_add_reading_minutes_to_posts_table.go"
func m20261018100000AddReadingMinutesToPostsTable() schema.Migration {
	return schema.Migration{
		ID: "20261018100000_add_reading_minutes_to_posts_table",
		Up: func(s *schema.Schema) error {
			return s.Table("posts", func(t *schema.Table) {
				t.Integer("reading_minutes").Default(0)
				t.RenameColumn("body", "content")
				t.Index("reading_minutes")
			})
		},
		Down: func(s *schema.Schema) error {
			return s.Table("posts", func(t *schema.Table) {
				t.DropIndex("posts_reading_minutes_index")
				t.RenameColumn("content", "body")
				t.DropColumn("reading_minutes")
			})
		},
	}
}
```

Inside `s.Table` the statements run in a fixed order, whatever order you wrote them in:

1. `ADD COLUMN` for each new column (a new `Constrained()` column carries its `REFERENCES` inline; on MySQL it becomes an `ADD FOREIGN KEY` clause of the same statement).
2. `DROP CONSTRAINT` for each `DropCheck`.
3. `RENAME COLUMN` for each `RenameColumn(from, to)`.
4. `DROP INDEX` for each `DropIndex(name)`.
5. `DROP COLUMN` for each `DropColumn(names...)`.
6. `CREATE INDEX` for each new index.
7. `ADD CONSTRAINT` for each new `Check`.

- `t.ID()` inside `s.Table` fails: `schema: cannot add a primary key column to existing table posts`.
- SQLite can only drop a column that has no index, `UNIQUE` constraint or foreign key; drop the index first. Vukem does not rebuild tables for you.

### The other `Schema` methods

| Method | What it does |
| --- | --- |
| `s.Drop(table)` / `s.DropIfExists(table)` | Drops a table (the second ignores a missing one) |
| `s.Rename(from, to)` | Renames a table |
| `s.HasTable(table)` | `(bool, error)`: whether the table exists |
| `s.HasColumn(table, column)` | `(bool, error)`: whether the column exists; `false` for a missing table |
| `s.Raw(sql, args...)` | Runs any SQL: data fixes, views, triggers |
| `s.Dialect()` | `"sqlite"`, `"postgres"` or `"mysql"`, for dialect-specific SQL |

Every table and column name is checked against `^[A-Za-z_][A-Za-z0-9_]*$` (`schema: invalid table name "..."`) and quoted, so names never come from input. When a statement fails, the error includes the SQL that failed.

A **data migration** fixes rows instead of the schema:

```go
Up: func(s *schema.Schema) error {
	return s.Raw(
		"UPDATE posts SET reading_minutes = 1 WHERE reading_minutes = 0",
	)
},
```

With arguments, write `?` placeholders: `s.Raw` rewrites them for the dialect (`$1`, `$2` on PostgreSQL) with `database.RebindChecked`, so the same data migration runs on SQLite, MySQL and PostgreSQL:

```go
Up: func(s *schema.Schema) error {
	return s.Raw("UPDATE posts SET status = ? WHERE status = ?",
		"draft", "")
},
```

A statement that mixes `?` with `$1`, or ends inside a string literal, fails with `database: query mixes ? placeholders with $n parameters` or `database: query ends inside an unterminated literal, identifier or comment`. Without arguments the statement runs exactly as written, so PostgreSQL's jsonb `?` operator in DDL keeps working. Only the statement text, as written, goes into the checksum, not the arguments.

## Running migrations

The migrate commands run inside your app's own binary (`cmd/app`), so they use your `DATABASE_URL` and your registered migrations.

| Command | What it does |
| --- | --- |
| `vukem migrate` | Runs every pending migration, in ID order, as one new batch |
| `vukem migrate:rollback` | Reverts the last batch, newest first |
| `vukem migrate:rollback --step 2` | Reverts the last 2 migrations, whatever their batch |
| `vukem migrate:reset` | Reverts every applied migration |
| `vukem migrate:fresh` | Drops **every table** and runs all migrations again |
| `vukem migrate:status` | Lists every migration with its state and batch |
| `vukem migrate:status --json` | The same as JSON |
| `vukem db:wipe` | Drops every table without migrating |

```text
$ vukem migrate:rollback
Rolled back: 20261018100000_add_reading_minutes_to_posts_table
```

<Callout type="warning" title="fresh, reset and wipe destroy data">
`migrate:fresh` and `db:wipe` drop every table in the database, including tables no migration created. `migrate:reset` runs every `Down`. All three refuse to run with `APP_ENV=production` unless you pass `--force`: `refusing to run a destructive command in production without --force`.
</Callout>

### Under the hood

- The first command creates the tracking table: `migrations (id VARCHAR(255) PRIMARY KEY, batch INTEGER, checksum VARCHAR(64), ran_at TIMESTAMP)`.
- **Batches.** Every `vukem migrate` gets the next batch number. `rollback` without `--step` reverts exactly the migrations of the highest batch, so "undo my last migrate" works even when it was several migrations.
- **One transaction per migration.** Each `Up` (and its row in `migrations`) runs in its own transaction. If migration 3 of 5 fails, migrations 1 and 2 stay applied, migration 3 is rolled back, and `migrate` stops with `schema: migrate <id>: <error>`. MySQL commits DDL implicitly, so there a failed migration may stay half applied: keep MySQL migrations small. `NoTransaction` migrations skip the transaction (see [Migrations outside a transaction](#migrations-outside-a-transaction)).
- **One runner at a time.** `migrate`, `rollback`, `reset` and `fresh` take a lock before reading the `migrations` table and hold it until they finish: a PostgreSQL advisory lock (`pg_try_advisory_lock`, polled every 50 ms up to 1 s until `ctx` ends, so a waiting runner holds no snapshot and cannot stall a `CREATE INDEX CONCURRENTLY` run by the holder) or a MySQL/MariaDB named lock (`GET_LOCK('vukem:migrations')`), on a dedicated connection. A second process waits, then finds nothing pending. If the lock cannot be taken, nothing runs and the error starts with `schema: lock migrations:`. SQLite takes no lock: migrate from one process.
- **Rollback** needs `Down`: `schema: migration <id> has no Down`. A migration recorded in the database but missing from code cannot be reverted: `schema: migration <id> is recorded but missing from code`.
- **`fresh`** drops every table (with `CASCADE` on PostgreSQL, foreign keys switched off on SQLite and MySQL) and then runs `Up` for everything.

### Migrations outside a transaction

Some statements refuse to run inside a transaction: PostgreSQL's `CREATE INDEX CONCURRENTLY`, which builds an index without blocking writes on a busy table, or SQLite's `VACUUM`. Set `NoTransaction` on such a migration:

```go title="database/migrations/20261029120000_index_ratings_item_id.go" nocompile
var IndexRatingsItemID = schema.Migration{
	ID:            "20261029120000_index_ratings_item_id",
	NoTransaction: true,
	Up: func(s *schema.Schema) error {
		return s.Raw("CREATE INDEX CONCURRENTLY IF NOT EXISTS " +
			"ratings_item_id_idx ON ratings (item_id)")
	},
	Down: func(s *schema.Schema) error {
		return s.Raw("DROP INDEX CONCURRENTLY IF EXISTS ratings_item_id_idx")
	},
}
```

`Up` runs on the database directly, and the migration is recorded only after it succeeds. Without the transaction, a failure half-way leaves what already ran: keep one statement per `NoTransaction` migration and write it to be re-run (`IF NOT EXISTS`), so the next `vukem migrate` can finish the job. A failed `CREATE INDEX CONCURRENTLY` (a unique violation, a timeout, a cancel) leaves an `INVALID` index behind, and the retry's `IF NOT EXISTS` would skip it, leaving an index PostgreSQL never uses. So after a `NoTransaction` migration on PostgreSQL, `migrate` checks the current schema and, if an `INVALID` index is left that no one is building, fails without recording the migration:

```text
schema: migrate 20261029120000_index_ratings_item_id:
  INVALID index ratings_item_id_idx left by a failed CREATE INDEX CONCURRENTLY:
  run DROP INDEX CONCURRENTLY on it, fix the cause and migrate again
```

Drop the index, fix what made the build fail (for a unique index, remove the duplicates) and run `vukem migrate` again.

### Checksums: catching edited migrations

When a migration runs, Vukem stores the SHA-256 of the SQL its `Up` generates for your dialect. `migrate:status` regenerates that SQL (without running it) and compares:

| Status | Meaning |
| --- | --- |
| `Pending` | Not applied yet |
| `Ran` | Applied, and the SQL still matches |
| `Ran (CHANGED since applied)` | Someone edited the migration after it ran: this database and a fresh one now differ |
| `Ran (missing from code)` | Recorded in the database, but no migration has this ID any more |

`vukem migrate:status --json` prints one object per migration (shown indented):

```json
[
  {
    "id": "20261016184613_create_users_table",
    "ran": true,
    "batch": 1,
    "ran_at": "2026-10-18T00:38:26Z"
  },
  {"id": "20261018100000_add_reading_minutes_to_posts_table", "ran": false}
]
```

With `--json`, each entry also carries `"changed": true` or `"missing": true` when they apply. While the checksum is computed, statements are recorded instead of executed, so `s.HasTable` and `s.HasColumn` return `false`; keep the SQL a migration generates independent of the current database where you can.

### From code

`app.Migrator()` returns a `*schema.Migrator` over `app.DB()` with the registered migrations:

| Method | Returns |
| --- | --- |
| `Up(ctx)` | The IDs that ran |
| `Rollback(ctx, steps)` | The IDs reverted, newest first (`steps` 0 = last batch) |
| `Reset(ctx)` | The IDs reverted |
| `Fresh(ctx)` | The IDs that ran after dropping everything |
| `Status(ctx)` | `[]schema.Status`: `ID`, `Ran`, `Batch`, `RanAt`, `Changed`, `Missing` |
| `Checksum(mig)` | The SHA-256 of a migration's SQL for this dialect |

`schema.NewMigrator(db, migrations)` builds one for any `*database.DB`, and `schema.DropAll(ctx, db)` is what `db:wipe` runs.

## Deploying migrations

Run `vukem migrate` once per deploy, before the new code serves traffic: as a release command on [Railway](/docs/deployment/docker-and-railway), or a step in your pipeline. On PostgreSQL and MySQL, two runners that start together (a rolling deploy that migrates at boot) are serialized by the migration lock; on SQLite, only one process should migrate at a time.

Because the old code keeps running while the new schema arrives, change tables in steps that both versions understand: add a nullable column first, deploy code that writes it, then make it required in a later migration.

## Security

- Table and column names are validated identifiers and always quoted.
- `Default` values are written as escaped SQL literals.
- Partial-index expressions, CHECK expressions, `schema.Expr` and `s.Raw` are raw SQL: write them yourself, never build them from input.
- `migrate:fresh`, `migrate:reset` and `db:wipe` need `--force` in production.
- Run migrations with a database user allowed to change the schema, and the app with a user that cannot, when your platform allows it.

## Testing

`vukemtest.New` runs every registered migration on a fresh in-memory SQLite database for each test, and fails the test when one fails. A migration bug therefore shows up in the first test of the suite.

```go title="tests/migrations_test.go"
func TestMigrationsRollBackCleanly(t *testing.T) {
	app := vukemtest.New(t, bootstrap.New)

	m, err := app.Migrator()
	if err != nil {
		t.Fatal(err)
	}

	if _, err := m.Reset(t.Context()); err != nil {
		t.Fatalf("reset: %v", err)
	}

	if _, err := m.Up(t.Context()); err != nil {
		t.Fatalf("migrate again: %v", err)
	}
}
```

- `vukemtest.Options{SkipMigrations: true}` starts with an empty database.
- `app.RefreshDatabase(t)` drops every table and migrates again.
- SQLite reads an unknown double-quoted identifier as a string, so `t.Index("mispelled")` passes on SQLite and fails on PostgreSQL and MySQL. If you deploy on those, run the tests against them in CI too, with `vukemtest.Options{Env: map[string]string{"DATABASE_URL": url}}`.

## Common mistakes

**Editing a migration that already ran.** The database does not re-run it; `migrate:status` shows `Ran (CHANGED since applied)` and production keeps the old schema. Write a new migration instead.

**Adding a required column to a table with rows.**

```go
// Wrong: existing rows have no value, so the database refuses.
t.String("subtitle")

// Right: give it a default, or make it nullable.
t.String("subtitle").Default("")
t.String("subtitle").Nullable()
```

On SQLite the error reads `Cannot add a NOT NULL column with default value NULL`.

**`ON DELETE` before `Constrained`.**

```go
// Wrong: schema: post_id: call Constrained() before an ON DELETE action
t.ForeignID("post_id").CascadeOnDelete().Constrained()

// Right
t.ForeignID("post_id").Constrained().CascadeOnDelete()
```

**A `Down` that does not undo `Up`.** `rollback` then leaves the schema in a state no migration describes. Test `Reset` followed by `Up`, as above.
