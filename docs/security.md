# Security

What Vukem does **by default** to protect applications, mapped to the [OWASP Top 10:2025](https://top10.owasp.org/2025/), and what remains the application's responsibility. Reporting vulnerabilities in Vukem itself: [SECURITY.md](../.github/SECURITY.md).

## Principles

1. **Secure by default, explicit to loosen.** Unsafe behaviour needs an opt-out with a visible name (`InsecureSkipX`, `AddInsecureBypassPattern`), never a missing opt-in.
2. **Fail closed.** If a check cannot be performed (store down, key missing, policy not registered), the request is denied.
3. **Refuse to boot when misconfigured.** Missing `APP_KEY` in production, debug in production, wildcard CORS with credentials: boot error, not a warning.
4. **Stdlib crypto only.** `crypto/*` and `golang.org/x/crypto`; no custom algorithms.
5. **Small dependency surface** so supply-chain risk stays auditable.

## Key rotation

`APP_KEY` derives (HKDF, one label per purpose) every key the framework uses: `app.Crypt` (encrypted cookies, `orm.Encrypted` columns, queued mail payloads), cookie sessions (and so the CSRF token and flash data they carry), the maintenance bypass cookie, and the keys apps derive with `app.DeriveKey` (signed URLs, social login state). Remember-me tokens, API tokens and refresh tokens are stored as hashes and JWT keys are configured separately, so they do not depend on `APP_KEY`.

1. **Rotate.** Locally, `vukem key:rotate` writes a new `APP_KEY` to `.env` and moves the old one to the front of `APP_PREVIOUS_KEYS` (no key is printed). In production, generate a key (`vukem key:generate --show` or `./app key:generate`), then set `APP_PREVIOUS_KEYS=<old APP_KEY>[,<older>...]` and `APP_KEY=<new key>` in the secret store, and deploy every instance with both: an instance with only the old key cannot open what the others now write.
2. **Overlap window.** Values sealed or signed with a previous key keep working: `app.Crypt` tokens, cookie sessions (re-sealed with the new key on the next request that reads them), the maintenance bypass cookie (re-issued), and signed URLs and social state for apps that pass `app.DerivePreviousKeys(purpose, 32)` to `signed.Signer.WithPreviousKeys` / `social.Social.WithPreviousKeys` (the `install:auth` scaffolds do). Everything new uses `APP_KEY`.
3. **Drain.** Before removing the old key, wait for the longest lifetime of what it signed: `SESSION_LIFETIME` (cookie sessions not used since the rotation are not re-sealed), the TTL of signed links already sent (links signed without a TTL never expire, so they stop working), queued and failed mail jobs, 12 hours for maintenance bypass cookies, and the `MaxAge` of encrypted cookies. Re-seal `orm.Encrypted` columns with `orm.Reseal[T]` or the app command `crypt:reseal` (`vukem.ResealCommand(orm.Reseal[models.User], ...)`): it rewrites only values sealed with a previous key, compare-and-set so a concurrent save is never overwritten, and a value no key opens stops it with `crypt.ErrInvalid` (`TestSecurity_A04_ResealRotatesEncryptedColumns`, `TestResealSkipsConcurrentWrites`, `TestResealFailsClosed`); saving a row also re-seals its columns and re-seal other stored `app.Crypt` tokens with `NeedsRotation` / `Rotate`.
4. **Remove** the old key from `APP_PREVIOUS_KEYS`. Whatever is still sealed with it fails closed: the session is empty (the user is signed out), signed links answer 403, mail jobs fail instead of sending, and encrypted columns return `crypt.ErrInvalid`.

A previous key still verifies cookie sessions and signed URLs, so whoever holds it can forge them for the whole window. After a leak, do not keep the leaked key in `APP_PREVIOUS_KEYS` in production: accept that sessions and links are invalidated, and re-encrypt stored data in a short maintenance window (or a one-off job) that has the leaked key, then drop it.

## Security headers (defaults)

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | starter: `default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'nonce-…'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` (HTTPS only) |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

All configurable in `config/http.go` (`MiddlewareOptions.SecureHeaders`, `APIMiddlewareOptions.SecureHeaders`). The API stack (`vukem.APIMiddleware`) sends the same set, CSP included: on a JSON response the CSP and `X-Frame-Options` are inert, and they protect any HTML an API route might return. `SecureHeaders` runs before `Maintenance` on both stacks, so the maintenance 503 carries these headers too (`TestSecurity_A05_MaintenanceResponseCarriesSecurityHeaders`).

## Verification

- Every default above names the test that asserts it (`TestSecurity_<Category>_<Behaviour>` where the row is security-specific, e.g. `TestSecurity_A01_StaticRejectsTraversal`) or the mechanism that enforces it (lint rule, CI job, release config), so `go test -run TestSecurity ./...` is the security regression suite.
- Fuzz targets for parsers that see untrusted input (router patterns and request paths, `.env`, JSON and form binding, multipart, tus headers, upload names, cookie sessions, JWTs, `crypt` tokens, storage paths, locale tags, webhook and Stripe signatures, GraphQL documents) run for an hour each every week ([`fuzz.yml`](../.github/workflows/fuzz.yml)).
- CI: `gosec` (via golangci-lint), `govulncheck`, CodeQL, OpenSSF Scorecard.
- BETA gate `B.5.2`: [security review](security-review.md) against this document and ASVS 5.0 Level 2, with findings, residual risks and fuzzing results.
